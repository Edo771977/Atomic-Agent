## Evidence receipts

Each project appends evidence snapshots to `<stateDir>/receipts/<project-key>/receipts.ndjson`. The folder key is shared with the protected decision record. Runs in a session worktree archive their receipts under the original project folder. The signing key is generated on first use in the operating system credential store. Public keys remain in `<stateDir>/signing/` so historical signatures survive key replacement. If the keychain is unavailable, the writer records the evidence as unsigned. Verification only reads public keys.

The archive includes artifact manifests, check-run records, gate verdicts and milestone reports. A saved gate verdict names the gate, version, verdict, decision source and the same content fingerprint as the decision record. New receipts carry the bound project ID, or null for an embedded project. If the folder already holds a project, an unbound session skips receipt writes. Historical receipts without a project ID still verify. The milestone card counts attributed manifests and checks for the current runs and the report for the current gate version. Earlier checks and manifests without run IDs are still available to the full verifier. Embedded milestone evidence carries the chat ID for attribution and stays visible if that chat later binds to the folder project and the evidence still belongs to the current work. The card requests verification on demand. It uses only public keys and reuses results for unchanged receipt rows. The scan reads up to the latest 2 MiB and 512 rows, marking counts partial if it cannot reach a row before the current work. `edit`, `cheaper` and `quality` also record the resulting content fingerprint as `resultHash`. Approval over a review includes the person's bounded note. A saved milestone report records its state, criterion results and attachment SHA-256 fingerprints. The `criterionHash`, `whyHash` and `reservationHash` fingerprints support integrity checks. Anyone who guesses the original text can confirm their guess against the hash. Prompts, raw model output and attachment bytes are excluded. An unavailable attachment fingerprint is recorded as null and logged. Incognito chats produce no receipts. A receipt write failure leaves the saved project decision or report in place.

Signatures support retrospective verification. A process running as the same user with access to the OS credential store can sign replacement evidence. See the [CLI guide](../cli/README.md) for statuses and trust limits.

## Ownership and dependencies

SessionState holds turns, loaded descriptors and transient recalled context; SessionStore persists the chat and turn ownership. Retention owns bounded cleanup of eligible inactive sessions; [session pins](session-pins.ts) from `tasks.sqlite` and `webhook-sessions.json` are never pruned. A missing pin file pins nothing, but one that exists and cannot be read or parsed throws `SessionPinsReadError`, and the runtime skips that boot's prune with a warning instead of pruning with an empty keep-list. The skip repeats every boot until the file reads, so the warning and `atomic-agent doctor` (check `session-pins`) name the file and its fix (`describeSessionPinsFix`). A corrupt `webhook-sessions.json` is moved aside to `.corrupt-<time>` by the webhook store at boot (its bindings are unusable anyway), so the next boot prunes again; a corrupt `tasks.sqlite` is never touched. Runtime controls execution and memory stores own durable facts, so a session snapshot must not be treated as either executor or memory database.

The optional version-1 [cloud context journal](cloud-context.ts) records the exact model-visible history and state updates in the existing session JSON. It has stable transcript-based call IDs, a processed transcript boundary and a boundary hash; old sessions initialize it on their first cloud build. Assembly extends it without mutation, runtime persists it before inference, and preview never commits. Current recalled inputs remain transient, but messages already shown to a cloud model remain journaled. Complete output increases stored session size; retention still applies to whole inactive sessions. Switching to local leaves the journal intact and uses the local projection; previously clipped local records cannot be reconstructed.

[Search over past chats](session-search.ts) (ATO-1149) is an FTS5 index of the chat lines `listChatLines` reads, in the same file. It is filled at search time, not on writes: each search reads changed transcripts without the write lock and writes them 25 sessions per transaction, up to 500 per search. Every channel is indexed with a `source` label and task sessions rank lower; incognito chats, Fusion workers and sessions stamped `metadata.internal` / `metadata.subagent` are never indexed (`classifySessionForSearch`).

[Turn progress](turn-progress.ts) (ATO-1109): `executeTurn` marks a turn's progress when it starts and checkpoints the transcript with the marker after every completed step (`SessionStore.checkpointTurn`, one row write guarded on the turn's own mark). A turn that ends on its own clears the marker; one that ends `cancelled`, or whose process died (the boot sweep ends the row and keeps the marker), keeps it so the work can be continued. The task runner continues tasks cut off by a crash or a restart; nothing continues a turn a person stopped. A chat turn a restart cut off ([interrupted-chat-turn.ts](interrupted-chat-turn.ts), ATO-448) is never continued on its own and is offered only when the operator started it (the marker's `options.origin` is `tui`, `cli`, `http` or `sidecar`; a legacy marker without one, only when `interactive`), never a Telegram, Discord or scheduler turn whose words `/resume` would replay as the operator's: opening its session in the TUI shows a one-line offer, and `/resume` (`AgentRuntime.interruptedTurns`, the same entry point for the desktop or an HTTP client) sends one continuing turn, starting with a note that tools may or may not have completed and side effects must be checked before they are repeated. A cut-off Fusion orchestrator turn with a resumable run written during it gets that run's `/fusion resume` message instead, so the workers' checkpoints are used rather than a fresh fan-out. Taking it marks the turn "resume queued" in memory, so it is offered once; the continuing turn replaces the marker when it starts, and a resume dropped before that (queue cleared, run stopped, session switched) is offered again. `/resume` and `/fusion resume` share one queued mark per Fusion run (the second says it is already queued): a second resume of a run that has since completed would reach `fusion.delegate` as `resume-unknown`, whose answer tells the orchestrator to plan the work again.

[Archived chats](session-archived.ts) (ATO-1150): `metadata.archived: true` marks a chat the operator put away, with `metadata.archivedSetAt` stamping every archive and unarchive. `SessionStore.setSessionArchived` sets it (like `renameSession`, read and written in one `BEGIN IMMEDIATE` transaction as an update only, so a row deleted meanwhile is not re-inserted); `save`, `finishTurn` and `checkpointTurn` keep the stored flag over a copy with no stamp or an older one, as for a renamed title. `SessionSummary.archived` carries it to the lists; `listSummaryPage({ excludeArchived: true, keepId })` leaves archived rows out in SQL (the open chat `keepId` stays), so the terminal's rail and picker page past a run of archived chats instead of filtering a fetched page. Not the turn archive (`turn-archive.ts`), which is storage for compacted turns.

[Incognito chats](incognito.ts) (ATO-586): `incognito` on the state, fixed at creation (`run --incognito`, TUI `/incognito`, HTTP `incognito: true` on a new chat; on an existing ordinary chat it is refused with 400, and an existing incognito chat stays incognito whatever later requests say). [Fusion project store](project-store.ts) (issue #109): a fusion project lives with its folder, not in a chat. The governing rule: `<folder>/.atomic/project/project.json` is author content, what the person approves and may edit by hand (the brief's text and criteria, the plan's rows and detail, the milestones' ids, titles and kinds), plus a readable mirror of the rest that is never read back; everything the runtime owns (milestone states, runs, outcomes, review blocks, criteria facts, pictures, corrections, `verdictResets`, `evidenceRetired`, the plan's untrusted flag, versions) and every person decision is authoritative in the project's record in the state dir. The file carries `schemaVersion` (2), `id`, `name`, `revision`, `createdAt`, `updatedAt` and `project` (the mirror: `projectContent`, with no person decision in it; pictures as paths relative to the state dir); `BRIEF.md`, `PLAN.md` and `STATUS.md` beside it are generated from the resolved project after every write and never read back. A write runs under `project.json.lock` ([project-lock.ts](project-lock.ts): owner pid, host, time and token; stale when its time is in the future, its owner on this host is gone, or older than 30 s; taken over by a rename that removes only the file it judged; released only while still its owner's), compares the revision it read (another chat's write since is `conflict`), writes the file through a temp file and a rename, then the record. Version 1 opens through the single in-memory v1-to-v2 migration (the version alone changes), and the next write saves version 2; version 3 or any unsupported version is refused with what to do and never overwritten; unparseable JSON or a project `normalizeProject` drops is `damaged`, reported, not opened, never overwritten. Unknown top-level fields are kept verbatim; unknown fields inside `project` are dropped, so a later field of the project itself comes with a schema version bump and readers for earlier supported versions. Nothing secret is written, and the folder's `.gitignore` is not touched: the store is meant to be committable.

[The project's record](project-decisions.ts) (`ProjectRecordStore`, the one seam to swap) is `<stateDir>/project-decisions/<key>.json`, owner-only: the project as Atomic Agent last wrote it, its `changedOutside` labels and the person's decisions (gate, version, verdict, the hash of the content the gate covered: the brief's author content, the plan's rows and milestones, or the milestone as recorded), under one compare-and-set on its `seq`. There is one record per folder: its name comes from the folder's real path alone (symlinks resolved, the disk's own spelling, so two folders differing by case on a case-sensitive volume stay two; case is folded on Windows and macOS only for a path that does not resolve), and it holds the folder and the folder's project id. The id in `project.json` is content: it never selects a record, a write puts the record's id back, and the record store refuses another id. A copied or moved folder, or another project's `project.json` put in a folder, therefore brings no approvals, runs or evidence; such a folder opens its author content as a draft (`freshFromContent`: brief and plan drafts, every milestone `planned` with no runs, all gates waiting) and takes a new id on its first write; a record file at a folder's name that belongs to another folder is never replaced. A bind or case-folding mount can give one folder two identities; it then starts over and borrows nothing. Records of the earlier layout (one per folder and id) are read for a folder with none of its own: the newest seq wins, the others are ignored and named (`projects list` prints them). The record's compare-and-set runs under a lock beside it in the same trust-config directory (`<key>.json.lock`); the folder's lock covers only the folder's files, since a command in the folder can remove it. A project copied to another machine therefore travels with its content; its execution state and gates start over there. `resolveProject` takes nothing from the file but its author content, and an author edit only as an untrusted draft through the director's own rules (`applyProjectUpdate` with `draftedAfterUntrusted`): it reopens the gate it changed at a higher version (a card shown before cannot approve it), and is listed in `changedOutside`, which belongs to the record: every write carries the record's labels and those of an outside edit the writer's base had taken, a director's redraft included, and only the person's decision at that gate clears its label; while a gate is listed its brief or plan draft reads as drafted after untrusted content, whoever wrote the last draft, so the card warns; an edit the rules refuse at that moment (a milestone result waits for the person) is not taken, and the next write puts the file back. The gate view carries `changedOutside: true` with a hint and `run --auto-approve-project` stops there (the person's `--approve <version>` decides it). Setting a state, a run or a fact in the file does nothing. A record of another version, of the wrong shape or that cannot be read is reported (`record-unavailable`): the project does not open, nothing is approved, nothing overwrites it. Pictures are kept only inside `<stateDir>/fusion-runs`. The same gate decided twice at the same version and content is `already-decided` ("That gate was already decided (in another chat); reload the project"), which `runtime.projectDecision` also returns when the gate moved because another chat decided it. Why the record is outside the folder: workers and their shell commands write in the folder; the record's directory, and the registry's, are trust config (`config/config-file.ts`), so a file tool's write asks as `trust_config` and a shell command naming them as `state_secret`.

[Session reference](session-project-store.ts): a session keeps `projectRef` (folder, id, the revision and record seq read) and its `project` is read from the store on `SessionStore.load` (the runtime's store passes `projectStore`) and before every turn (`prepareTurn`); with a reference the project is never saved in the session row, and `projectProblem` (transient) says why it did not open (damaged, unsupported, an unusable record, a reference to a folder other than the chat's: the project is the chat folder's, so its `projects.constraints` still apply); a load never throws for it. A chat follows its folder when the file there carries another id. Director updates (`foldProjectUpdate`) apply to the project as recorded now and are written back; a store refusal refuses the update with its reason. A project-flow turn in a folder that holds a project binds the chat to it, so several chats share one project and its one-open-milestone rule. Migration: a session saved with an embedded project writes it to the folder (content) and a record (its state and decisions as they were, so approved gates stay approved and evidence stays) on first load; the embedded copy stays in the row until the next save, and a folder that already holds another project or cannot be written keeps the project embedded. The remaining trust boundary: migration trusts the sessions database, which is not trust config, so a model able to write `sessions.sqlite` could plant an embedded project with approvals before its first load; that is no worse than before the store, when the database held every project. An incognito chat (ATO-586) never touches the store, the registry or a record: its project stays in the session. The folder is the worktree's original folder for a worktree chat. [The registry](project-registry.ts) (`<stateDir>/projects/registry.json`, paths only) lists the folders whose project a chat opened, for `atomic-agent projects list`. File tools writing into `.atomic/` ask as `trust_config` (`tools/os/fs/fs-approval-scope.ts`); the shell is not covered, by design harmless.

[Attention zone](project-attention.ts) (issue #121): `projectAttentionZone` puts a listed project in one zone, top to bottom: `needs-you` (a gate waits, one changed outside included), `problem` (a failed milestone, or a project that cannot be opened), `in-progress` (a milestone runs, or activity within `IDLE_AFTER_DAYS`, 7, and not done), `idle`, `done` (every milestone reviewed, or cancelled); `compareProjectAttention` orders by zone, then the most recent activity. `projects list` rows carry it as `zone`.

[Client project instructions](session-project.ts) (ATO-42; same file as the Fusion project, separate state under `metadata.project`): a client's project (the desktop groups chats into projects with shared instructions) is owned by the client. Its instructions arrive with each turn (`project_instructions`, `project_name` on `POST /v1/chat/completions`) and `runTurn` stamps them on the session's `metadata.project` inside the turn lock; null clears them, an absent field keeps them. The prompt renders them like a folder's AGENTS.md: a `project` cloud context section and a capped `### project` block ahead of the local conversation.

[Stored read taint](stored-read-taint.ts) (issue #74): `save`, `finishTurn` and `checkpointTurn` intersect the row's stored `providerReadTaint` stamp into the state they write (an unreadable stored stamp is kept, since reading it fails closed), so a copy read before a tool tainted the row never writes the restriction away. Its meaning is the runtime's ([provider policy](../llm/docs/provider-policy.md#read-taint)).

## Project schema v2 additions

The optional author fields are bounded by [PROJECT_LIMITS](project-limits.ts), with the same normalization on session and project-store reads:

- `brief.deliverable`: `code`, `document`, `spreadsheet`, `research`, `files` or `game`; absence means `code`. It adds no routing or execution behavior, and `brief.game` keeps its existing meaning.
- `brief.decisions`: up to 20 `{ id, text }` entries, with unique criterion-shaped ids and short text. They are part of the brief fingerprint: editing their text reopens the brief gate. `plan.rows[].decisions` lists up to 20 such ids; those references belong to the plan fingerprint. Enforcement (issue #112): a brief approval records its decisions as `approvedDecisions` (record only, like `approvedCriteria`; an older store reads its approved brief's), and the plan check `decision-coverage` refuses the plan while an active one is cited by no task. Each milestone records `decisionsCited` (record only, runtime-set): the approved plan's citations of its tasks with their text, taken when a plan is approved (every milestone not done or reviewed), at a run when missing, and from the approved rows before a brief or plan draft replaces them; a draft's or a file edit's rows never set it. A brief approval that changes the text (beyond case and whitespace) of a decision in a milestone's `decisionsCited` (a milestone recorded before it: the plan's rows, only while the plan is approved) starts it over when it holds a verdict, a run or evidence: `planned`, its evidence in `history` with cause `brief` and `decisions` (the old text), by the same `supersede` as a changed criterion, named in the draft plan's `verdictResets`; an added or removed decision resets nothing.
- `backlog`: up to 32 open or promoted `{ id, title, note?, condition?, source, fromPerson?, createdAt, origin? }` proposals (128 stored in all, dropped ones included: `backlogStored`). Sources are `person`, `director`, `worker` or `reviewer` (labels, not provenance); a director update never names `person` (nothing proves the message was the person's): it sets `fromPerson` with `director`, shown "director (from your message)"; `person` only reads from a hand edit. `createdAt` is a finite nonnegative epoch time, and `origin` optionally names `milestoneId` and `taskId`. Titles use the title bound; notes and conditions use the short-text bound. Backlog edits are outside all gate fingerprints and reopen no gate. Behavior (issue #111, [project-backlog.ts](project-backlog.ts)): the director's `backlog_add` update (`project.backlog.add`) appends an item with the id the fold allocates (past every `b<n>` the backlog or the record has held), refused without a brief, after a cancel, past the cap, for an id already used by an item or a call, an empty title or an origin the plan does not hold; a `worker` or `reviewer` item names the plan task whose milestone ran. `applyBacklogDecision` is the person's call (promote, drop, or `open` to take one back; refused after a cancel), reached only through `runtime.projectBacklogDecision` (CLI, HTTP, sidecar). Each call is bound to the item's text: `backlogCalls[id].hash` (title, note, condition; record only) — an item changed outside Atomic Agent since reads open, the #80 rule, and the plan gate flags it, as it flags a promoted item removed from the file (`staleBacklogCalls`). Coverage (issue #146): `plan.rows[].backlog` lists up to 32 backlog ids a task takes in (author content, in the plan fingerprint); the plan check `backlog-coverage` refuses the plan while a promoted item not taken in is cited by no task of a milestone not started (`backlogCheckOptions`, from the record's calls; none for an approved plan, so an item promoted while a plan runs, or waiting in an older store, is the next draft's). A plan approval records `backlogCalls[id].plannedIn` with `cited` only for waiting items such a task cites, and each milestone not started records what its tasks cite (`backlogCited`, record only). `backlogTakenIn`: such an item stays taken in only while the current plan cites it on a task of a milestone not started, or a started milestone was approved with it; otherwise `promotedForPlan` lists it again. A call from #111's rule (`plannedIn` without `cited`) stands as recorded. A complete project reports `promotedNotDone` (promoted items no run took in) besides `openBacklog`. At the plan gate the person may send `edit` with `edits.backlogStatus` (`deferred` or `active` per waiting promoted item): recorded as `backlogCalls[id].deferred` (record only, read back only on a promoted call), the item stays promoted but leaves the coverage until set active; a new call on the item clears it; no director update or automatic approval carries it; the plan's version bumps. The plan gate shows the waiting items (deferred ones marked) and `--auto-approve-project` stops for them. Open items with a `condition` are seeds, shown at plan and milestone gates; `projectExpectation` reports `complete` with `openBacklog` while items stay open.

`decisionStatus` (`active`, `informational`, `deferred`, `retired`; absent means active) and `backlogStates` (`promoted`, `dropped`; absent means open) live only in the folder-bound record. A decision's status is set only by the person, at the plan gate: `edit` with `edits.decisionStatus` (`active`, `deferred` or `informational` for an id of the approved brief; `retired` is not offered), recorded as that gate's decision with the new state, the plan's version bumped so an older card cannot approve; no director update carries it. A status belongs to the decision it was set on: a brief approval drops it when its id leaves the approved decisions or its text changes beyond case and whitespace (the id-reuse rule of #80), so a reused id starts active. The author file cannot set them, including by adding status fields inside an entry or when opening without a record. New brief and plan drafts preserve these recorded calls. Stored malformed brief decisions and backlog entries are dropped and their lists/text are bounded; plan references and check specs are validated strictly. Drafts refuse malformed author decisions and plan references.

Use milestone kinds `draft`, `review` and `final` for non-code deliveries. Saved milestones with `base`, `ui`, `logic`, `polish` or `other` continue to load.

Plan rows also accept optional `checks`, sharing the contract parser with `fusion.delegate`; ownership is implicit in the row. Their full content, including negative controls, is covered by the plan fingerprint. Runtime-derived `plan.checkResults` are saved in the record, omitted from `project.json`, and recomputed from rows and the last approved criteria on load and approval. A new plan saves results even if it has no checks; an older plan without results continues to load. `plan.referenceCheck` (issue #120) is the runtime's record of the references check (`{verdict, detail, taskIds, basis}`), kept in the state dir's record only (omitted from `project.json`, and one written there is dropped when the file is read); it cannot be recomputed on load (it reads the folder), so a record whose `basis` no longer matches the rows' ids, titles and checks reads as `references: warn: Not re-checked`, and a malformed one is dropped. `plan.review` (issue #118) is the plan reviewer's record (`{outcome, reviewer, results, reason?, round, sentBack, basis, costUsd, decided?, heldAtTurnEnd?}`; the model's verdicts only, the facts floor is recomputed when it is used), set by `project.plan` on the plan update with `holdForReview` when it sent the draft back (the draft then opens no gate until the turn ends, `releaseHeldPlan`); a person's decision at any gate marks it `decided`, which starts the next draft's round count over. `plan.reviewOverride` (`{note, at, blocks, basis?}`) is the person's `approveOverReview` over its open fails, valid while the plan holds the review of that basis; both live in the state dir's record only, never in `project.json` (a copy written there is dropped on read), and a review whose `basis` no longer matches the rows and milestone order reads as stale and blocks nothing. Failures use the existing `review-open` approval refusal. The [Fusion guide](../tools/fusion/README.md#planned-verification) describes analysis and delegation. [Schema migration tests](project-store-schema.test.ts) cover v1 and embedded-session migration without data loss and refusal to overwrite v3; [field tests](project-schema-v2-fields.test.ts) cover file edits across the record boundary.

## Project lesson files

[The lesson reader](project-lessons.ts) validates UTF-8 Markdown in direct children of the project's lesson directory. Save one lesson per file. For example, save this as .atomic/project/lessons/local-storage.md.

~~~markdown
---
id: local-storage
title: Use SQLite for local storage
source: correction
from: milestone m2, run r7
touches: [src/storage, package.json]
status: proposed
always: false
---
## Deciso
Keep the database local.

## Provato e scartato
A remote database added an unnecessary service dependency.

## Attenzione
Check the migration against a copy of the database.
~~~

The front matter accepts one unindented key per line between exact delimiter lines. All keys shown are required except for `from`. The accepted sources are `correction`, `milestone-failure`, `person` and `director`. The declared status is `proposed`, `active` or `retired`. Use bare `true` and `false` for `always`. Text values can be plain, single-quoted (double a literal apostrophe), or double-quoted using JSON string escapes. Blank lines and comments are allowed. A hash starts a comment at the start of a value or after whitespace. Quote literal hashes, quotes and colons followed by whitespace. `touches` accepts only an inline list of paths, including an empty list. Quote an item containing a comma. Multiline values, nested mappings, anchors, tags and trailing list commas are unsupported.

Use the three level-two Markdown headings once each. Their English equivalents are **Decided**, **Tried and ruled out**, and **Watch out**. The section bodies may be empty.

[Project limits](project-limits.ts) cap the directory at 128 Markdown entries, each at 16 KiB. IDs match the filename stem exactly and use up to 64 lowercase ASCII letters, digits or hyphens. Titles and provenance are capped at 160 and 300 characters respectively. Each lesson can list up to 32 paths of 1,024 characters each. Paths are interpreted relative to the project with either slash convention. Absolute paths, drive qualifiers, path components with ambiguous Windows trailing dots or spaces, and paths that escape above the project are refused. The reader treats paths as metadata and never opens them.

Invalid files are skipped whole and reported. All files with the same parsed ID are skipped. Symbolic links in the lesson path and symbolic-link lesson entries are refused. An absent lesson directory gives an empty list. A directory over the entry limit gives one directory-level problem and an empty list.

The Markdown is author content. Phase 1 always returns `approvedByPerson: false`, even for `status: active`. Approval belongs in the person's protected project decision record in a later phase. For now the reader supports local inspection and neither supplies prompts nor affects plan gates. It reads and writes no personal memory, including for folders with `projects.constraints`.
