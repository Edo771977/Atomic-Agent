## Ownership and dependencies

SessionState holds turns, loaded descriptors and transient recalled context; SessionStore persists the chat and turn ownership. Retention owns bounded cleanup of eligible inactive sessions; [session pins](session-pins.ts) from `tasks.sqlite` and `webhook-sessions.json` are never pruned. A missing pin file pins nothing, but one that exists and cannot be read or parsed throws `SessionPinsReadError`, and the runtime skips that boot's prune with a warning instead of pruning with an empty keep-list. The skip repeats every boot until the file reads, so the warning and `atomic-agent doctor` (check `session-pins`) name the file and its fix (`describeSessionPinsFix`). A corrupt `webhook-sessions.json` is moved aside to `.corrupt-<time>` by the webhook store at boot (its bindings are unusable anyway), so the next boot prunes again; a corrupt `tasks.sqlite` is never touched. Runtime controls execution and memory stores own durable facts, so a session snapshot must not be treated as either executor or memory database.

The optional version-1 [cloud context journal](cloud-context.ts) records the exact model-visible history and state updates in the existing session JSON. It has stable transcript-based call IDs, a processed transcript boundary and a boundary hash; old sessions initialize it on their first cloud build. Assembly extends it without mutation, runtime persists it before inference, and preview never commits. Current recalled inputs remain transient, but messages already shown to a cloud model remain journaled. Complete output increases stored session size; retention still applies to whole inactive sessions. Switching to local leaves the journal intact and uses the local projection; previously clipped local records cannot be reconstructed.

[Search over past chats](session-search.ts) (ATO-1149) is an FTS5 index of the chat lines `listChatLines` reads, in the same file. It is filled at search time, not on writes: each search reads changed transcripts without the write lock and writes them 25 sessions per transaction, up to 500 per search. Every channel is indexed with a `source` label and task sessions rank lower; incognito chats, Fusion workers and sessions stamped `metadata.internal` / `metadata.subagent` are never indexed (`classifySessionForSearch`).

[Turn progress](turn-progress.ts) (ATO-1109): `executeTurn` marks a turn's progress when it starts and checkpoints the transcript with the marker after every completed step (`SessionStore.checkpointTurn`, one row write guarded on the turn's own mark). A turn that ends on its own clears the marker; one that ends `cancelled`, or whose process died (the boot sweep ends the row and keeps the marker), keeps it so the work can be continued. The task runner continues tasks cut off by a crash or a restart; nothing continues a turn a person stopped. A chat turn a restart cut off ([interrupted-chat-turn.ts](interrupted-chat-turn.ts), ATO-448) is never continued on its own and is offered only when the operator started it (the marker's `options.origin` is `tui`, `cli`, `http` or `sidecar`; a legacy marker without one, only when `interactive`), never a Telegram, Discord or scheduler turn whose words `/resume` would replay as the operator's: opening its session in the TUI shows a one-line offer, and `/resume` (`AgentRuntime.interruptedTurns`, the same entry point for the desktop or an HTTP client) sends one continuing turn, starting with a note that tools may or may not have completed and side effects must be checked before they are repeated. A cut-off Fusion orchestrator turn with a resumable run written during it gets that run's `/fusion resume` message instead, so the workers' checkpoints are used rather than a fresh fan-out. Taking it marks the turn "resume queued" in memory, so it is offered once; the continuing turn replaces the marker when it starts, and a resume dropped before that (queue cleared, run stopped, session switched) is offered again. `/resume` and `/fusion resume` share one queued mark per Fusion run (the second says it is already queued): a second resume of a run that has since completed would reach `fusion.delegate` as `resume-unknown`, whose answer tells the orchestrator to plan the work again.

[Archived chats](session-archived.ts) (ATO-1150): `metadata.archived: true` marks a chat the operator put away, with `metadata.archivedSetAt` stamping every archive and unarchive. `SessionStore.setSessionArchived` sets it (like `renameSession`, read and written in one `BEGIN IMMEDIATE` transaction as an update only, so a row deleted meanwhile is not re-inserted); `save`, `finishTurn` and `checkpointTurn` keep the stored flag over a copy with no stamp or an older one, as for a renamed title. `SessionSummary.archived` carries it to the lists; `listSummaryPage({ excludeArchived: true, keepId })` leaves archived rows out in SQL (the open chat `keepId` stays), so the terminal's rail and picker page past a run of archived chats instead of filtering a fetched page. Not the turn archive (`turn-archive.ts`), which is storage for compacted turns.

[Chat export](chat-export.ts) (ATO-1054): one chat as Markdown (messages, replies, one line per tool step, delivered files; no reasoning or raw tool output), and HTML ([renderChatHtml](chat-export.ts), raw HTML shown as text, CSP blocks loads) or DOCX ([chat-export-docx.ts](chat-export-docx.ts), minimal OOXML zipped with JSZip) built from that Markdown. Every exported line (title, messages, tool-step lines) goes through the shared credential detector (`maskSecrets` in [secret-detector.ts](../error-reporting/secret-detector.ts), plus exact known values) before it is written. Both callers, `atomic-agent export` and `GET /api/sessions/{id}/export`, pass the same set tool output is masked with ([runtimeKnownSecrets](../runtime/runtime-known-secrets.ts): the `.env` values and the keys and secret headers stored in config.json); without one the renderer falls back to the secret-named values of `process.env`.

[Fusion team choice](session-fusion-team.ts) (issue #37): `metadata.fusionDirector` and `metadata.fusionWorker` hold the session's director and preferred worker as `{member, providerId, model, chosenAt}`, and `metadata.fusionReviewer` its reviewer the same way or `{member: "none"}` for no review (issue #71); the readers drop a stamp whose halves disagree with `member`. Written per session (never into the global config) and read by `runtime/session-director.ts`.

[Fusion project](session-project.ts) (issue #39): `SessionState.project` holds the brief, the plan's assignment rows and the milestones, and `gate`, what waits on the person (`none`, `brief`, `plan`, `milestone:<id>`). Pure transitions: `applyProjectUpdate` folds director (and dispatch `milestone_run`) updates, which never carry a status, so the model cannot approve and every brief or plan edit is a draft with a bumped version; `applyProjectDecision` applies the person's verdict at the current gate against `gateVersion` (stale or other-gate decisions are refused). Versions only grow: a cancel records `versionFloor`, and a new project's brief and plan start above it, so a card shown for the cancelled project cannot approve one the person has not seen. Approving the brief lets the director draft the plan; approving the plan approves the first milestone; approving a done milestone marks it `reviewed` and approves the next; while a milestone gate is open the director's brief and plan updates are refused (`awaiting-person`, issue #74), approving never approves a milestone while another is `approved` or `in_progress` (a re-plan approved during a run leaves the next one planned) or past an unreviewed done or failed one, a report for another milestone is refused while one's gate is open (`awaiting-person`), (a plan approval over one, from an older store, opens that milestone's gate); a re-plan keeps a finished or running milestone's summary, corrections, `attachments` and `criteriaFacts`; a `done` report needs a run since the milestone was (re)approved or last reported failed (it must be `in_progress`, or already `done`), else it is refused (`milestone-not-run`, issue #74); approving a failed one re-approves it; a hard cap never refuses a milestone decision (issue #74): the result is decided (done `reviewed`, failed `planned`) and, while a milestone remains to run, the plan goes back to draft at a plan gate where the person sees the violation and can pick cheaper, quality or edit; `edit` at a milestone gate is the person's correction (`edits.note`): the milestone goes back to `approved` with the note on its `corrections` for the director. `normalizeProject` drops a malformed stored project whole and clips text and lists to `PROJECT_LIMITS`. Success criteria carry ids (issue #40, `ProjectCriterion { id, text }`, `criteriaById`): unique, at most 32 characters of `[a-z0-9-]`; plain text gets the first free `c<n>` (`n` its position), so an older store reads back as `c1..cN` and round-trips, and a revision in plain text keeps the id of unchanged text. A milestone may carry `attachments` (at most 8 `{ path, caption, criteria? }`): a report's are checked when folded by `validateMilestoneAttachments` (pure; the step passes `stateDir`): an absolute `.jpg`/`.jpeg`/`.png` directly inside `<stateDir>/fusion-runs/<runId>/shots/` of a run on that milestone's `runIds`, criteria naming the brief's ids; anything else refuses the report, and a new report replaces the pictures. `criteriaFacts` (`{ id, state: passed | failed | unverified, why? }`) are the runtime's: `project.milestone` reads them from the milestone's runs and they ride on its done report, cleaned by the fold (one per id, clipped, malformed dropped). Stored attachments and facts read back leniently (a malformed entry is dropped, not the project); readers render a picture only through their own safe file read. Surfaces draw [ProjectGateView](project-gate-view.ts) (types only, the one shape every surface imports; `tools/fusion/project-gate-view.ts` builds it with per-row `selectableWorkers`/`selectableReviewers`, live violations and `allowedVerdicts`) and decide through `AgentRuntime.projectDecision`. The runtime never continues the director's work by itself: after a decision that closed a gate on director work, the surface that decided (TUI, CLI `--approve`/`--auto-approve-project`, HTTP client, sidecar, Telegram) sends [projectContinueMessage](project-continue.ts) as the next user turn.

[Session titles](session-title.ts): the namer writes `metadata.title` once, after the first answered turn, and never renames. The operator can ([session-title-user.ts](session-title-user.ts), `SessionStore.renameSession`): that title carries `metadata.titleSetByUserAt`, and `save`/`finishTurn` keep it over any copy without the stamp or with an older one, so a stale snapshot cannot undo a rename.

[Incognito chats](incognito.ts) (ATO-586): `incognito` on the state, fixed at creation (`run --incognito`, TUI `/incognito`, HTTP `incognito: true` on a new chat; on an existing ordinary chat it is refused with 400, and an existing incognito chat stays incognito whatever later requests say). No memory is written from one (removals refuse too), no list or search shows it, and its fusion workers are incognito too; it is deleted with its archived turns, trace, tasks and fusion run checkpoints when closed (`runtime/incognito-sessions.ts`; the HTTP server closes the ones its chat completions opened when it closes), or at the next boot once its owning process is gone (`SessionStore.sweepOrphanIncognito`). While a store has an incognito chat open its connection runs with `secure_delete` on (freed pages are zeroed), and deleting one checkpoints the WAL (`wal_checkpoint(TRUNCATE)`). That checkpoint is best effort: while another connection (another agent process, a backup tool) holds a read snapshot it returns busy and the WAL keeps the frames with the chat's text until a later checkpoint passes them; with no such reader the text stays in neither file; filesystem-level copies (journaling, SSD remapping, backups) are outside what SQLite can reach.

[Dataset export](dataset-export/export-dataset.ts) (ATO-1104) backs `atag data export-dataset`: it pages through the session list newest first, turns each chat's `listChatLines` into one chat fine-tuning record (user messages and closing answers only, see [build-dataset-record.ts](dataset-export/build-dataset-record.ts)) and scrubs every message with [scrub-dataset-text.ts](dataset-export/scrub-dataset-text.ts): the shared credential detector, the looser report shapes, emails and home folders, each counted. It only reads the store and writes one local file.

[Next-step suggestion](session-next-step.ts) (ATO-1093): with `tui.nextStepSuggestions` on (ATO-1096, default off), one side call of at most 40 output tokens after each answered turn writes `metadata.nextStep` `{ text, afterTurn, at }`; `readSessionNextStep` shows it only while `afterTurn` equals `turnCount` and no turn is running. Fired from the runtime like the namer ([runtime-next-step.ts](../runtime/composition/runtime-next-step.ts)): never awaited, never after a budget stop, not for scheduler or fusion turns.

[Session worktrees](session-worktree.ts) (ATO-576, `/new worktree`): opt-in, git repos only. The session gets its own worktree and branch under `<stateDir>/worktrees`; the binding is `SessionState.worktree`. [Cleanup](session-worktree-cleanup.ts) removes only idle, merged, clean worktrees, never with `--force`; an ignored file such as `.env` keeps the worktree, only caches like `node_modules` do not.

[Client project instructions](session-project.ts) (ATO-42; same file as the Fusion project, separate state under `metadata.project`): a client's project (the desktop groups chats into projects with shared instructions) is owned by the client. Its instructions arrive with each turn (`project_instructions`, `project_name` on `POST /v1/chat/completions`) and `runTurn` stamps them on the session's `metadata.project` inside the turn lock; null clears them, an absent field keeps them. The prompt renders them like a folder's AGENTS.md: a `project` cloud context section and a capped `### project` block ahead of the local conversation.

[Stored read taint](stored-read-taint.ts) (issue #74): `save`, `finishTurn` and `checkpointTurn` intersect the row's stored `providerReadTaint` stamp into the state they write (an unreadable stored stamp is kept, since reading it fails closed), so a copy read before a tool tainted the row never writes the restriction away. Its meaning is the runtime's ([provider policy](../llm/docs/provider-policy.md#read-taint)).
