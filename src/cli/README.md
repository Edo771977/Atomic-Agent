# CLI frontend

Status: current
Owner: src/cli/

Owns command parsing and terminal entry points. User turns enter runtime.runTurn; preserve exit semantics, state-dir selection and separation from release scripts.

Entry point: [index.ts](index.ts). Read the root instruction route and the underlying domain instructions before cross-domain changes.

Skill list/show/enable/disable accept `--workspace <dir>` for cloud project scope; `skill project on|off --workspace <dir>` controls all project sources. Without the flag enable/disable remain global. See [cloud skill controls](../skills/docs/cloud-workspace.md).

`run` reads stdin through one line queue ([stdin-line-queue.ts](stdin-line-queue.ts)): every line is kept in arrival order, a line written while a turn runs becomes the next message, and an approval prompt takes its answer from the same queue. A driver can pipe the task, a `y` and the next message at once. The prompt takes only a line shaped like an answer (`y`, `yes`, `n`, `no`, `s`, `a`, or an empty line); any other line denies and stays queued as the next message, so piping "task" and "continue" without an answer loses nothing. EOF before an answer denies, and a prompt that fails denies without stopping later input (ATO-781, ATO-802). Because a piped multi-line prompt still runs one turn per line, the first time a second piped line becomes its own turn `run` prints a one-line notice to stderr; a terminal session gets no notice (ATO-910). An `ask_user` question ([cli-user-question.ts](cli-user-question.ts), ATO-489) prints its numbered options and takes the next line as the answer: a number, several (`1,3`) when it allows more than one, or the person's own words when it allows them; an answer it does not take is asked again (three tries), an empty line or EOF skips it. The tool is offered only when stdin is a terminal and `--no-approval` is not set: a piped driver's next line is its next message, not an answer.

Fusion project gates (issue #39, [run-project-gate.ts](run-project-gate.ts)): after a turn that left the chat's project waiting on the person (brief, plan or a finished milestone), `run` prints the gate ([formatProjectGateText](../session/project-gate-text.ts): brief, untrusted-draft warning, rows with worker, reviewer, estimate and basis, totals, violations, milestones, allowed verdicts), the session id and the command that approves it, and exits 3 without reading further input. `run --session <id>` continues a stored chat (to ask the director for changes); `--approve <version>` (needs `--session`) approves the open gate only at the version printed with it, prints what it approved and sends the continuing message as the next turn; bare `--approve` prints the gate with its version and exits 3, asking to repeat it with the version; nothing waiting, or a refusal (a hard cap, a gate that changed since that version: "not approved: the plan changed since version <v>; current is <c>"), exits 1 with the reason. `--auto-approve-project` approves every gate at its current version as it opens and prints each approval with its version, except a failed milestone, where it stops with exit 3 because a retry, correction or cancel is the person's call; it is never the default, so an unattended run always stops at a gate.

`config get --with-sha256` prints `{"sha256": "<hex>", "config": {...}}`: the normalised config and the lowercase sha256 of the raw `config.json` bytes it was parsed from, from one read (the empty-string hash when the file is missing). `config set - --expect-sha256 <hex>` writes the stdin payload only while the file still hashes to `<hex>`; otherwise it writes nothing, prints exactly `config changed since it was read` to stderr and exits 3. Without the flag `set -` is unchanged. This is the compare-and-swap the desktop uses since it shares the terminal agent's state dir (ATO-416); see [config-sha256.ts](config-sha256.ts).

Before any command runs, the entry reads `network.offline` from config.json without writing it ([offline-from-config.ts](offline-from-config.ts)) and turns offline mode on when it asks for it, so commands that build no runtime (`update`, the skill and plugin hubs) are refused remote hosts too. A missing or malformed file counts as off (ATO-1084, [offline mode](../llm/docs/offline-network.md)).

On a Windows console, startup switches the code page to UTF-8 (65001) so non-ASCII text and the output of console programs the agent runs are not garbled, and restores the original page on exit. It skips a non-TTY stdout (the desktop app reads through pipes), a console already on UTF-8, and macOS and Linux; a failing `chcp` never stops startup. See [windows-console-utf8.ts](windows-console-utf8.ts) (ATO-221). Typed input does not depend on the code page: on a Windows console Node reads the TTY through the console's UTF-16 API, so `Ã¨`-style mojibake in a trace viewed with Windows PowerShell 5.1's `Get-Content` is the viewer reading BOM-less UTF-8 as ANSI, not corrupt input. `doctor` on Windows adds a `console-code-page` line ([doctor-console-code-page.ts](doctor-console-code-page.ts)): ok on 65001, a warning naming another page, and the `Get-Content -Encoding UTF8` hint for traces.

`doctor [--fix] [--undo] [--json]` (ATO-577) runs a registry of checks ([doctor-checks.ts](doctor-checks.ts)): config.json parses and passes the schema, it is readable by its owner only, and every enabled stdio MCP server's command is installed; each `projects.constraints` folder gets a `project-constraints` line (allowed providers and egress classes, and that shell commands and stdio MCP servers' own network are not policed), and an unknown key inside an entry or an allowed provider that is not configured is a warning naming it (the same notice the load prints); a session pin file (`tasks.sqlite`, `webhook-sessions.json`) that exists but cannot be read is a `session-pins` warning with its fix, since retention skips its prune every start until it reads. The `sqlite` check opens an in-memory better-sqlite3 database and, when the native binding cannot load, fails with the loader's fix. A check may offer a bounded fix: an unknown `llm.activeTextProvider` becomes the first configured provider (another schema error in the file stays a reported failure), a missing MCP command turns that server off, a loose file mode becomes 600. Broken JSON and other schema errors are reported, never guessed at. `--fix` copies config.json to `<stateDir>/doctor-backups/config-<time>.json` before it edits the tree; `--undo` restores the newest copy and removes it. The state dir comes from `ATOMIC_AGENT_STATE_DIR` without loading the config, so the command runs when the config is the broken thing. Exit 1 while any check fails. Once the config is valid it also checks the local engine (installed, model on disk, enough memory, server running or its port free; external mode: the server answers) or, when a cloud provider is active, its key with one test token (Anthropic: one `GET /v1/models`) ([doctor-engine-checks.ts](doctor-engine-checks.ts)); these say the command that fixes them. The key line names where the key came from (`apiKey in config.json`, or the variable from `<stateDir>/.env` or from this shell's environment) with its length only, never a value or prefix; a `key-source` warning says when this shell's value overrides a different one in `.env`, and a malformed candidate (a placeholder such as `...`) is reported as not sent rather than as rejected.

`data backup|restore|move|reset|path` (ATO-579, [data-command.ts](data-command.ts), [data-archive.ts](data-archive.ts)) acts on the state dir the terminal and the desktop share. `backup <file.tar.gz>` writes an owner-only archive with a manifest; each `*.sqlite` goes in as a snapshot through SQLite's backup API, and `models/` (unless `--with-models`), `browser-profile/` (cookies), WAL/SHM, locks and runtime records stay out. `restore <file> --yes` unpacks into a sibling folder, refuses an archive without the manifest, carries this machine's `models/` over when the backup has none, then swaps folders and keeps the old one as `<stateDir>.before-restore-<time>`. `move <dir>` moves the folder (copy and remove across disks) and leaves a symlink (a junction on Windows) at the old path, so both apps keep finding it. `reset --keep-models --yes` moves everything but `models/` to `<stateDir>.reset-<time>`. Nothing is deleted; close every Atomic Agent first.

`overnight "<task>" [--budget <usd>] [--hours <h>] [--dir <path>] [--notify telegram] [--detach] [--no-approval]` (ATO-1113, [overnight-command.ts](overnight-command.ts)) creates one durable one-shot task (origin `cli`, one attempt) with the task's `maxCostUsd` and `maxDurationMs` (ATO-1108) and runs it. No `--budget` leaves the cap to `agent.task.maxCostUsd`; no `--hours` means 8. `--dir` becomes the runtime's working dir, so the run's session and every tool work there. Foreground prints one line per step to stderr ([overnight-progress.ts](overnight-progress.ts)) and a summary to stdout. Exit 0 when the agent finished on its own; 2 when a limit ended the run (the row is `completed` with a `stopCause`, or `blocked` with `budget_spent:` / `time_spent:`), and the summary then says `overnight stopped (<cause>)`; 1 when it failed or was cancelled (ATO-1323). An approval request is denied and counted, since nobody answers it; `--no-approval` boots at the top level. `--detach` re-runs the same command as a detached child (cwd = `--dir`, output to `<stateDir>/logs/overnight-<id>.log`) under a task id it prints first. A `task cancel` from another terminal is seen within 5 s and aborts the turn. The task carries `agent.task.maxSteps` as its step ceiling, so the per-leg `agent.maxSteps` does not end the run. Ctrl+C (SIGINT) cancels the task; SIGTERM and SIGHUP (shutdown, logout) stop the run the way a runtime shutdown does and leave the task pending to resume. Step lines count what the task spent before this run toward the cap.

`export <sessionId>|--last [--format md|html|docx] [--out <file> [--force]] [--no-tools]` ([export-command.ts](export-command.ts), ATO-1054) writes one chat through [exportChat](../session/chat-export-render.ts), masking the same known secrets tool output is masked with. Markdown and HTML go to stdout unless `--out`; DOCX goes to `--out` or a file named after the chat; an existing file needs `--force`. `--last` is the newest chat someone wrote in; an incognito chat is refused (exit 1). Exit 0, 1 when it failed, 2 on a usage error.

`fusion report [--days N] [--model X] [--json]` ([fusion-command.ts](fusion-command.ts)) prints the fusion outcome log aggregated per worker model and orchestrator provider (format and fields: [fusion README](../tools/fusion/README.md)); `/fusion report` in the TUI prints the same text. Exit 0, 1 when the report cannot be produced, 2 on a usage error; `--model` matches a model or provider id case-insensitively.

`fusion recover <journal> --project <dir> [--status|--dry-run|--rollback] [--json]` ([recovery command](fusion-recovery-command.ts)) inspects an interrupted candidate promotion. The default and `--status` are read-only; `--dry-run` validates backups and reports the proposed reverse steps without writing. Only `--rollback` restores entries that still match the delivered bytes/type/mode and preserves later user edits as conflicts. The selected project, version-2 journal, paths, backup hashes and process owner are validated before mutation. A live owner, unknown/legacy journal, corrupt backup or unsafe path refuses recovery. Committed delivery cannot be rolled back. A completed rollback keeps its terminal journal and backups; repeating it preserves subsequent edits. Nothing runs automatically at startup. Exit 0 for status/complete recovery, 1 for failure/conflicts, 2 for usage; `--json` returns state, owner, planned/restored paths and conflicts. See the [fusion recovery limits](../tools/fusion/README.md).

`models recommend --role worker [--json]` ([models-recommend.ts](models-recommend.ts)) names the model for fusion's workers instead of the three tiers: among the models this machine carries, by catalog fusion-worker rating (`good` > `ok` > unrated > `poor`), then room for `localModels.managed.parallel` worker slots, then rank, and prints why. `--json` keeps the default fields and adds `role` and `worker` (`{model, rating, ratingNote, slots, slotsWanted, needGb, why}`, `null` when nothing fits). Without `--role` (or `--role default`) the output is unchanged; another value exits 2.

## Fusion setup

`setup fusion [--yes] [--dry-run] [--judge] [--isolation] [--orchestrator <id>] [--orchestrator-model <id>] [--budget <usd>]` ([setup-command.ts](setup-command.ts)) switches to Fusion in one step. [setup-fusion-detect.ts](setup-fusion-detect.ts) reads config.json without creating it (an invalid file is named with "Fix or move <path>", exit 1), loads `.env`, asks `providers status`' check about Claude Code (no turn), and lists models on disk; an external llama-server gets a 1.5 s `/health` probe. The pure [planner](../llm/run-mode/fusion-setup-plan.ts) ranks the orchestrators that can answer: the stored fusion orchestrator unless it is definitely not ready (an inconclusive check, such as the CLI check timing out, keeps it with a warning; a replaced one is named with the reason), then the active text provider when it is a cloud one, then a signed-in subscription CLI (a configured entry, else a new keyless `claude-cli` entry), then other keyed cloud providers with Best/Balanced [tier](../llm/provider/presets/model-tiers.ts) models before Cheap ones. Last comes a cloud [preset](../llm/provider/presets/provider-presets.ts) whose key variable is set (shell or `.env`, e.g. `ANTHROPIC_API_KEY`) while no entry reads it: the facts carry the variable's name only, and setup adds the entry the TUI's preset wizard would save (`presetEntryFields`: its URL, `apiKeyEnvVar`, and the key header and headers of an `openai-compatible` one; Anthropic's is a native `kind: "anthropic"` entry). Its model is the preset's default chat model; a preset without one needs `--orchestrator-model <id>` (one value applies to the preset `--orchestrator` names, else only when a single such preset was found, and is checked against the listed models when the endpoint answered), and a terminal run lists the chat models the preset's `/v1/models` serves (asked with that key, embedding/speech/moderation/image ids dropped) and asks. That list is asked only when setup could choose the preset: `--orchestrator` names it, or no configured orchestrator is ready; otherwise no request goes out, `--dry-run` included. When the pick is Claude Code although `ANTHROPIC_API_KEY` was found, the plan says so and names `--orchestrator anthropic`. An unknown `--orchestrator` says to add it in the TUI (Esc → Manage › LLM › Cloud → n) or put its key in `<stateDir>/.env`. A key alone does not outrank a subscription: it may be there for a cheap or embedding model. Each leg shows its provider, model (`defaultChatModel`), tier when listed, and per-token or flat-rate billing; a Cheap tier orchestrator gets a warning. With more than one ready, a terminal run lists them and asks for a number (Enter keeps the first); `--yes`, `--dry-run` and a non-terminal print the others, and `--orchestrator <id>` picks one without asking ([setup-terminal-prompt.ts](setup-terminal-prompt.ts) reads both questions from one line reader). The worker is the first `llama-server` entry, served by the managed engine with its model on disk, or by an external server that answers. Otherwise it exits 1 with the next step: the `.env` variable or Manage › LLM › Cloud for a key, the Claude Code sign-in or install command, `models use <id>` for a model already on disk, or `models pull <id> --background` for the machine's balanced catalog pick.

It prints each change (`(unset) → value`), asks (a non-terminal needs `--yes`), and writes through [applyFusionSetupInConfig](../config/fusion-setup-commands.ts): one validated write of the new entry, `llm.activeTextProvider`, `llm.runMode.mode` and the fusion block. The legs are always pinned; the rest is filled only where unset, so a value you wrote is kept, and so is an enum value a newer build wrote ("kept (set by a newer version)"): `autoReplan: 1`, and on a priced orchestrator `escalation: "advisor"` and `turnBudgetUsd: 1` (the advisor's dollar cap needs a price; on a subscription leg only the counted caps hold a turn). A note explains the turn cap: once a turn's spend reaches it, no new delegation or worker starts and the orchestrator reports what is done and what is left in one short final reply (up to 4096 tokens); a reply already running when the cap is reached, and that final reply, are charged on top, so a turn can end a little over the cap ([request budgets](../runtime/docs/request-budgets.md)); 0 means no cap. `config set` cannot address the fusion block, so `--budget <usd>` sets it (over a stored value too; `--budget 0` for none). `judge` and `isolation` (a global setting) stay off unless `--judge`/`--isolation` is passed; the output says so. A re-run that changes nothing prints "already set up" and exits 0. `--dry-run` writes nothing.

## Desktop state merge

`import atomic-desktop --source <dir> [--json]` merges the desktop app's former state dir (`~/.atomic-agent-desktop`) into the current one (`ATOMIC_AGENT_STATE_DIR`, default `~/.atomic-agent`) when the desktop moves onto the shared dir (ATO-416). The desktop runs it once and moves the plain files (config.json, .env, skills, traces, models) itself; this command handles only the databases:

- sessions and tasks keep their ids and are inserted only where the id is absent, so the target wins. A live turn arrives ended as interrupted, a running task arrives pending, and neither carries an owner mark.
- memory notes are added through `MemoryStore` unless the same text is already stored; profile facts through `ProfileStore` unless the target has any row for the key.
- lessons, procedures, votes, note links and embeddings are not copied; the embedding backfill or `memory reindex` rebuilds vectors.

Each source database is read from a private snapshot (a byte copy after a clean close, otherwise SQLite's online backup over a read-only connection), so the source is never written and nothing is deleted. Writes are short transactions that wait on the target's locks, so a TUI or `serve` may keep the target open. A re-run imports nothing new. `--json` prints one object, `{ok, sessions:{imported,skipped}, tasks, notes, profileFacts, warnings, error?}`; exit 0 only when every part imported. Implementation: [atomic-desktop importer](../import/atomic-desktop/atomic-desktop-importer.ts).

Checks: `npx vitest run src/cli` when tests are present; `npm run lint`; `npm run docs:check`.

`serve` watches its own memory ([serve-memory-guard.ts](serve-memory-guard.ts), ATO-1111). Every minute it samples RSS and the V8 heap; every ten minutes, and whenever severity rises, it writes one numbers-only `[atomic-agent] memory <ok|warn|exit> rss_mb=… heap_mb=… heap_limit_mb=… total_mb=…` line to stderr. Past the exit line (heap 85% of its ceiling or RSS 50% of the machine with no turn running; 93% / 65% even with one running) it ends through the normal teardown and exits with code 86, which the desktop tags `exit_status=memory_guard` and restarts. A daemon (`--no-parent-exit`, or no parent at boot) has nothing to restart it, so there the exit line is only reported and serve keeps running. `ATOMIC_AGENT_MEMORY_GUARD=0` turns it off.

## Handoff

`handoff --from claude-code|codex [--session latest|<id>] [--cwd <dir>] [--note <text>] [--list] [--json] [--no-open]` continues a Claude Code or Codex session that stopped mid-task (ATO-1154). It reads their transcript through the import readers ([handoff source](../import/handoff/handoff-source.ts)), saves it as a NEW native chat with a fresh `s-` id ([handoff session](../import/handoff/handoff-session.ts)), closes trailing tool calls that never got a result, and opens the TUI on it with `--session <id> --send <continuation message>`. `latest` is the newest session that ran in the current folder, else the newest anywhere. `--list --json` prints `{from, sourceDir, sessions:[{agent,id,mtimeMs,cwd,title,messageCount}]}`; `--json` without `--list` saves the chat without opening it and prints `{ok, sessionId, title, workingDir, from, sourceSessionId, turns, closedCalls, prompt}` (the desktop uses both).

Before saving, the carried history is fitted into a local model's window (ATO-1155, [fit-context](../import/handoff/fit-context.ts)): when it is larger than half the window (`--context <tokens>`, default the managed model's pinned `contextSize`, else 32768; `0` skips this), the head becomes an extractive checkpoint (`SessionCompaction`, `kind: "extractive"`, no model call) cut at a safe boundary, the newest records stay verbatim, and very long tool outputs in that tail are clipped in the middle. `--json` reports it under `context`.

## Model fit-test

`models tasks collect [--last <n>] [--out <file>] [--json]` writes the user's last tasks as a fit-test set (ATO-1089, [models-tasks-command.ts](models-tasks-command.ts)); the rules for what is kept live in [the fit-test guide](../fit-test/README.md). `models fit-test --tasks <file> --models <a,b> --judge-url <url>` runs that set on up to three local models and prints score, time and peak memory per model (ATO-1090, [models-fit-test-command.ts](models-fit-test-command.ts)). Swapping the user's models out and back in, and the restore record the next `models` command or TUI start acts on after a run killed outright, live in [models-fit-test-restore.ts](models-fit-test-restore.ts).
