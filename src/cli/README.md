# CLI frontend

Status: current
Owner: src/cli/

`atomic-agent project verify [folder] [--json]` checks the archived evidence receipts for a project. With no folder it uses the current directory. Each line identifies a receipt by its position and reports `valid`, `hash-mismatch` (edited payload), `bad-signature` (invalid signature or malformed receipt), `unknown-key` (missing public key), `unsigned` (installation signing key unavailable), or `unknown-kind` (receipt type unsupported by this version). The summary counts each status for artifact manifests, check-run records, gate verdicts and milestone reports. With `--json`, the output is an array in archive order with `kind`, `status` and `projectId` on each entry. The project ID is shown in both modes when recorded and the payload is valid or unsigned. An unrecognized or unreadable kind is `null`. Exit 0 means every receipt present verified, including an empty archive. Exit 1 indicates at least one problem or an unreadable archive. An unreadable archive emits a JSON object with an `error` field when `--json` is set. Exit 2 indicates incorrect usage.

Verification covers the saved delivery manifests, check execution records, gate verdicts and milestone reports. It cannot tell whether receipts were removed or whether the current workspace files match the saved evidence. The protected project decision record remains the boundary against model edits. A process running as the same user with keychain access can sign replacement evidence.

Owns command parsing and terminal entry points. User turns enter runtime.runTurn; preserve exit semantics, state-dir selection and separation from release scripts.

Entry point: [index.ts](index.ts). Read the root instruction route and the underlying domain instructions before cross-domain changes.

Skill list/show/enable/disable accept `--workspace <dir>` for cloud project scope; `skill project on|off --workspace <dir>` controls all project sources. Without the flag enable/disable remain global. See [cloud skill controls](../skills/docs/cloud-workspace.md).

`skill eval <skill> [--tasks <tasks.yaml>] | --all [--check-tasks] [--repeat <n>] [--only with|without] [--max-steps <n>] [--no-approval] [--json] [--keep-workdir] [--judge-url <url>] [--judge-model <id>]` (ATO-1098, [skill-eval-command.ts](skill-eval-command.ts)) runs each task once with the skill in the catalog and once with it hidden, on a fresh temp working folder per run, checks the answers and saves the comparison to `<stateDir>/skill-evals/<skill>/<runId>.json`. The skill is hidden in memory only; `config.json` is not written. Memory is read-only for every run (`memoryReadOnly`), so one variant cannot leave notes or lessons for the other. Approval requests are denied and counted, since nobody answers them; `--no-approval` boots at the top level. `judge` checks are graded by one of the person's own models (ATO-1101): `ATOMIC_AGENT_JUDGE_URL` + `_MODEL`, else `skills.eval.judgeProvider`, else the active cloud provider; with none of them (a local model active) a tasks file with judge checks stops before anything runs. The judge's tokens and cost are printed on their own line and saved as `judgeUsage`. Exit 0 when every planned run finished, 1 when stopped early or on an error, 2 on bad arguments or a missing judge. Without `--tasks` only a packaged starter's `evals/tasks.yaml` is used (ATO-1163); an installed skill's tasks file runs only when named with `--tasks`. `--all` evaluates every starter that has one and `--check-tasks` only prints where it is. Format and result file: [Skill Lab](../skills/eval/README.md).

`run` reads stdin through one line queue ([stdin-line-queue.ts](stdin-line-queue.ts)): every line is kept in arrival order, a line written while a turn runs becomes the next message, and an approval prompt takes its answer from the same queue. A driver can pipe the task, a `y` and the next message at once. The prompt takes only a line shaped like an answer (`y`, `yes`, `n`, `no`, `s`, `a`, or an empty line); any other line stays queued as the next message, so piping "task" and "continue" without an answer loses nothing. Nobody could be asked when stdin ends before an answer, when a non-terminal stdin's next line is not an answer, or when the prompt fails: the call is not run and reads `approval unavailable (non-interactive run)` on stderr and in the tool result, an `automatic` denial the model is told nobody decided, never that the user declined it (issue #95). An explicit `n`/`no`/Enter, and a non-answer typed at a terminal, are the person's refusal as before (ATO-781, ATO-802). `--allow-command "<command>"` (repeatable; [run-allowed-command.ts](run-allowed-command.ts), issue #95) pre-approves exactly that one command for a non-interactive run, such as the project's agreed test command: the value is printable ASCII split on spaces and may hold no quotes, globs or other shell or cmd.exe syntax (anything else exits 2); a request with any word outside printable ASCII never matches, and Windows folds only the letters A-Z (no Unicode folding, so U+212A KELVIN SIGN is not `k`). Only a direct exec is pre-approved: a request runs without a prompt only when no shell reads it and no glob was expanded (`literalExec` from `os.shell.run`, which also marks the common one-string form `{cmd: "node --test sales.test.cjs"}` when it is plain words of `[A-Za-z0-9_./:=@+,-]` separated by single spaces: matched, it runs directly through the pin; not matched, it still runs through the shell as before; never a `background: true` call, whose job outlives the turn; or a `verify.run` command check with one directly executed command, no `env`, no `stdin` at all (undefined or empty: data counts as much as a script) and no file it writes, `verifyPlainCommand`), it names no file it would write, its argv (`commandArgv`) equals the value's words element by element, argv[0] included: exactly the value's first word, so `./node`, `/tmp/x/node` or `NODE` is not `node` (on Windows argv[0] alone is compared ignoring case, and a path is still refused when the value has none), it is classed `shell` (never a dangerous command) and it runs in `--cwd` or below, compared as real paths (a link out of the folder is outside it, and a folder that cannot be resolved is never matched). A line the model sends through a shell is never pre-approved, whatever its first words: a redirect, `&`, a `#` comment or a substitution there runs more than the words say (issue #95 review); and the approval pins what runs ([run-allowed-executable.ts](run-allowed-executable.ts), `ApprovalDecision.pinnedExec`): the first word is resolved once, at approval time, to a real program file, through PATH entries that are absolute, exist and lie outside `--cwd` (never the current folder or an empty entry; on Windows only `.exe` or `.com`, and a `.cmd` or `.bat` found first refuses), a word with a path names that file, and a file inside `--cwd` (a planted `bin/node`, `./node_modules/.bin/…`) or nothing found means no pre-approval; the tool then spawns that file with the approved argv, without a shell, in the folder's real path (`verify.run`, and the contract checks that use it, swap only the program: the check keeps its private copy as the folder and its own arguments, which name the copy, once its project-relative argv matched the pin), and the child's PATH is only those filtered entries, so a `#!/usr/bin/env node` program (npx, npm, vitest) finds its interpreter there and never through `.`, an empty entry or a folder inside `--cwd`; a script whose `#!` names an interpreter inside `--cwd` or by a relative path is never pinned. A program path with `(`, `)`, `{` or `}` (`C:\Program Files (x86)\…`) is pinned for `os.shell.run`, which spawns it directly; a `verify.run` check whose runner would start that path through a shell asks instead. Only the host's decision carries the pin, never the call's arguments, and the tool honours it only for a call whose argv it equals; the contract checks go through `verify.run`'s authorization and are covered the same way. A different command, the same command in a parent folder, a dangerous or compound one, and every other tool still ask (and, piped, read as unavailable). It is never implied by `--auto-approve-project`, and a fusion worker's own calls stay under its refuse policy. stderr prints `approved by --allow-command: <command> (runs <file>)` for each, and a call refused as unavailable in a run that allows commands names them in the refusal ("This run pre-approves only `node --test sales.test.cjs` …"), so the model can retry in exactly that form; when the call already is the allowed command but nothing could be pinned, the refusal says why instead ("… resolves to a .cmd or .bat script", "… a file inside the project folder", "no program outside the project folder is named …") and that it cannot run unattended. Two consequences to weigh before using it. A test runner such as `node --test`, `npm test` or `pytest` executes the test files it finds, so allowing one amounts to allowing any code the model can write into `--cwd`: the words are fixed, what they run is not. And the option answers the CLI's prompt, which comes after the gate's saved rules: a saved deny rule still refuses the command, but a saved "ask" rule for that exact command is answered by this option without a prompt. Because a piped multi-line prompt still runs one turn per line, the first time a second piped line becomes its own turn `run` prints a one-line notice to stderr; a terminal session gets no notice (ATO-910). An `ask_user` question ([cli-user-question.ts](cli-user-question.ts), ATO-489) prints its numbered options and takes the next line as the answer: a number, several (`1,3`) when it allows more than one, or the person's own words when it allows them; an answer it does not take is asked again (three tries), an empty line or EOF skips it. The tool is offered only when stdin is a terminal and `--no-approval` is not set: a piped driver's next line is its next message, not an answer.

Fusion project gates (issue #39, [run-project-gate.ts](run-project-gate.ts)): after a turn that left the chat's project waiting on the person (brief, plan or a finished milestone), `run` prints the gate ([formatProjectGateText](../session/project-gate-text.ts): brief, the brief's decisions with status and citing tasks (issue #112), untrusted-draft warning, rows with worker, reviewer, estimate and basis, totals, violations, milestones, allowed verdicts), the session id and the command that approves it, and exits 3 without reading further input. The same check runs when the run ends without a turn to take it there (issue #100): stdin closed (EOF) or the chat finished while a gate still waits, as when `run --session <id>` continues a chat the director left at a failed milestone, prints the gate and how to resume and exits 3 instead of a silent 0; with `--auto-approve-project` the gates it may approve are approved first. `run --session <id>` continues a stored chat (to ask the director for changes); `--approve <version>` (needs `--session`) approves the open gate only at the version printed with it, prints what it approved and sends the continuing message as the next turn; bare `--approve` prints the gate with its version and exits 3, asking to repeat it with the version; nothing waiting, or a refusal (a hard cap, a gate that changed since that version: "not approved: the plan changed since version <v>; current is <c>"), exits 1 with the reason. `--auto-approve-project` approves every gate at its current version as it opens and prints each approval with its version, except a gate whose content changed outside Atomic Agent since it was decided or that has no decision on this machine (issue #109, `changedOutside`: it stops with exit 3 for a person), a failed milestone, where it stops with exit 3 because a retry, correction or cancel is the person's call, and a milestone whose approval the runtime refuses because a review still blocks it (`review-open`, issue #100), where it prints the block, the session id and `atomic-agent run --session <id>` to continue and exits 3 too, since approving over a review (`approveOverReview`) is the person's call; a plan whose approval a failing plan check refuses (also `review-open`, e.g. `decision-coverage`, issue #112) stops the same way with "A plan check still blocks the plan" and the check's message; a plan whose `planReview.autoApprovable` is false (issue #118: the plan reviewer's open notes still fail it, or with a plan reviewer configured it was not reviewed, its review is stale or none is recorded) stops before any decision is sent, saying which, since approving such a plan is the person's call (`run --approve <version>` still approves an unreviewed one; approving over open notes needs the TUI or desktop card); auto-approval must also make progress (issue #106): the same gate open again at the same version right after its approval, or more than `MAX_AUTO_APPROVALS_PER_RUN` (50) approvals in one run, prints `project: auto-approval made no progress (…)` with the gate and how to resume and exits 3; whatever ends the run, the runtime's teardown gets `RUN_SHUTDOWN_GRACE_MS` (5 s) after the session is saved, and a teardown still running then (a telemetry flush with no network, a server that never closes) is left behind with a stderr note so the process exits with its code instead of staying open; and as a last safety net (issue #104, [hard-exit-deadline.ts](hard-exit-deadline.ts)) the run arms a referenced 15 s deadline (`HARD_EXIT_DEADLINE_MS`) once its loop is over: if the process is still there then, whatever holds it, it writes one stderr line naming what is still alive (`process.getActiveResourcesInfo()`, and each handle's constructor, with program and pid for a child process) and calls `process.exit` with the run's exit code; because that timer runs on the main event loop, a watchdog on a worker thread backs it up (issue #106: the live process was still alive 178 s after `pending`, at 126 GiB private memory, and the deadline never ended it; a main loop starved by a never-yielding microtask loop is one hypothesis, which the memory trace below is there to confirm or rule out, and the watchdog contains the damage whatever the cause): it samples the process's resident memory every 200 ms and, past the cap (4 GiB, `ATOMIC_AGENT_RUN_RSS_LIMIT_MB` to change it) or 5 s after the deadline (`WATCHDOG_GRACE_MS`) with the process still alive, writes one `atomic-agent watchdog:` line to stderr (time since the run ended, rss, the worker's heap/external/array-buffer figures, the run's exit code) and kills the process: SIGKILL on POSIX, so the parent sees a signal rather than a code, and TerminateProcess with code 1 on Windows; the worker is unref'd and never keeps a process alive. Resident memory is what Node can read from a thread; Windows' private bytes are not visible to it; it is never the default, so an unattended run always stops at a gate.

At the plan gate, use `atomic-agent run --session <id> --defer-decision d1,d2` (issue #112) to defer decisions from the approved brief. Use `--reactivate-decision d1` to restore active status. Both flags accept comma-separated IDs and may be combined for distinct IDs. The command applies the edit before reading stdin, prints the new plan version and its `--approve <version>` command, then exits 3. A decision ID missing from the approved brief or a gate other than the plan exits 1. Run the approval separately. `--auto-approve-project` never edits decision status.

Memory trace of a run (issue #106, [run-memory-trace.ts](run-memory-trace.ts)): with `ATOMIC_AGENT_RUN_MEMORY_TRACE=<file>` (off when unset: nothing opened, no timer, no worker) `run` appends NDJSON to that file with one synchronous `writeSync` per line on a descriptor opened once, so lines reach the disk even when the main loop stops turning or the process is killed, and it keeps sampling until the process ends. Records: `{t:0, kind:"start", epochMs, pid, ppid, platform, arch, node, flags, argCount, intervalMs}` (flag names only, never their values); `{t, kind:"phase", phase, edge:"enter"}` and `{t, kind:"phase", phase, edge:"exit", ok, ms}` for `boot`, each `stdin-read`, each `turn` (with `n`), each `settle-gates`, `session-save`, `result-print` (the summary with the session status), `hard-exit-arm`, `stdin-close`, `incognito-discard`, `shutdown`, and inside it every step of the runtime's teardown as `shutdown:<step>` (`runtime.shutdown({ onPhase })`, see [lifecycle](../runtime/docs/lifecycle.md)); `{t, kind:"main", rss, heapUsed, heapTotal, external, arrayBuffers, lagMs, phase}` every second from the main thread (`lagMs`: how late the tick fired); `{t, kind:"worker", rss, heartbeatAgeMs, phase, lastPhase}` every second from a worker thread started with the trace, which reads the main thread's last sign of life and phase from shared memory, so a main loop that stops ticking stops the `main` lines while the `worker` lines say since when and in which phase; `{t, kind:"exit", code, phase}` when the process exits. `t` is ms since the start record. A growing `heapUsed` is a JS heap growth; `rss` growing with a flat heap points at buffers or native memory. The exit watchdog above is separate and unchanged. [scripts/sample-run-memory.mjs](../../scripts/sample-run-memory.mjs) samples the same process from outside, Windows private bytes included, and can stop it at a limit.

`config get --with-sha256` prints `{"sha256": "<hex>", "config": {...}}`: the normalised config and the lowercase sha256 of the raw `config.json` bytes it was parsed from, from one read (the empty-string hash when the file is missing). `config set - --expect-sha256 <hex>` writes the stdin payload only while the file still hashes to `<hex>`; otherwise it writes nothing, prints exactly `config changed since it was read` to stderr and exits 3. Without the flag `set -` is unchanged. This is the compare-and-swap the desktop uses since it shares the terminal agent's state dir (ATO-416); see [config-sha256.ts](config-sha256.ts).

Before any command runs, the entry reads `network.offline` from config.json without writing it ([offline-from-config.ts](offline-from-config.ts)) and turns offline mode on when it asks for it, so commands that build no runtime (`update`, the skill and plugin hubs) are refused remote hosts too. A missing or malformed file counts as off (ATO-1084, [offline mode](../llm/docs/offline-network.md)).

On a Windows console, startup switches the code page to UTF-8 (65001) so non-ASCII text and the output of console programs the agent runs are not garbled, and restores the original page on exit. It skips a non-TTY stdout (the desktop app reads through pipes), a console already on UTF-8, and macOS and Linux; a failing `chcp` never stops startup. See [windows-console-utf8.ts](windows-console-utf8.ts) (ATO-221). Typed input does not depend on the code page: on a Windows console Node reads the TTY through the console's UTF-16 API, so `Ã¨`-style mojibake in a trace viewed with Windows PowerShell 5.1's `Get-Content` is the viewer reading BOM-less UTF-8 as ANSI, not corrupt input. `doctor` on Windows adds a `console-code-page` line ([doctor-console-code-page.ts](doctor-console-code-page.ts)): ok on 65001, a warning naming another page, and the `Get-Content -Encoding UTF8` hint for traces.

`atomic-agent project lessons [folder] [--json]` lists the project's Markdown lessons and shows their declared status, current approval, effective status and stale choices. JSON includes `lessons` and `problems` arrays, plus `staleChoices` when applicable. Use `--approve <id>@<fingerprint>` with the 12-character fingerprint shown in the listing (case-insensitive), or use `--retire <id>` to record your choice for the current file, or `--reopen <id>` to clear a choice, including for a deleted file. Decide between turns from your terminal after opening the project in a regular chat. Exit 0 means the command completed, even if some files were skipped during listing. `atomic-agent project ui-exceptions [folder] [--json]` lists operator-approved Impeccable exceptions for the current or given project. Add or replace a choice with `--allow <rule>[:<file>] --reason "<reason>"`, or remove it with `--revoke <rule>[:<file>]`. Omit the file for a rule-wide exception. Use a project-relative path to limit the exception to a single source file. Run the command from your terminal between turns, after opening the project in a regular chat. Choices are stored in the project record in the Atomic Agent data directory. A project can add up to 200 exceptions. Revoking a missing entry leaves the record untouched. Incognito chats neither create nor use those choices. Exit 1 means the operation was refused or the record could not be read or written. Exit 2 means the arguments are invalid.

Atomic Agent sets `ATOMIC_AGENT_TOOL_CHILD=1` on shell and verification tool subprocesses. CLI commands that record project decisions refuse when this marker is present. This is a defense against agent-issued decisions. A process can remove the variable, so the marker provides no isolation boundary.

`projects list [--json]` and `project resume <folder> [--no-open]` (issue #109, [projects-command.ts](projects-command.ts)): `projects list` reads the folders in `<stateDir>/projects/registry.json` (paths only; a folder is added when a chat opens its project) and prints, per folder, the project's name and folder, what waits for the person (`brief`, `plan`, `milestone <id>`, `none`), the [attention zone](../session/project-attention.ts) (field `zone` with `--json`), what happens next, the last change (`updatedAt`) and the spend of its fusion runs whose checkpoints are still on disk ("no recorded runs" otherwise); a missing, damaged or unsupported folder is a row with its reason, never an error, and a damaged registry is reported (exit 1) and left as it is. `projects forget <folder>` drops a folder from the list; its project stays in the folder. `project resume <folder>` opens the folder's project (a damaged or unsupported file exits 1 with the reason), reuses the newest chat in that folder on that project or creates one bound to it, prints the gate waiting for the person with `run --session <id> --approve <version>`, and in a terminal opens the TUI on that chat (`--no-open`, or no terminal: prints only). `doctor [--fix] [--undo] [--json]` (ATO-577) runs a registry of checks ([doctor-checks.ts](doctor-checks.ts)): config.json parses and passes the schema, it is readable by its owner only, and every enabled stdio MCP server's command is installed; each `projects.constraints` folder gets a `project-constraints` line (allowed providers and egress classes, and that shell commands and the network use of stdio MCP servers marked `local: true` are not policed), and an unknown key inside an entry or an allowed provider that is not configured is a warning naming it (the same notice the load prints), as is an allowed local provider whose endpoint is another machine not listed in the entry's `allowedProviderHosts` (or cannot be read), which dispatch refuses there (issue #60); while any constraint exists, a stdio MCP server whose command and arguments match a catalog entry marked local (filesystem, git, time, memory, sequential thinking) but whose entry lacks `"local": true` is an `mcp-local` warning naming the fix (`set "local": true on mcp.servers[i]`, or add `mcp:<name>` to `allowedEgress`), with no automatic fix ([doctor-mcp-local.ts](doctor-mcp-local.ts), issue #60); a session pin file (`tasks.sqlite`, `webhook-sessions.json`) that exists but cannot be read is a `session-pins` warning with its fix, since retention skips its prune every start until it reads. The `sqlite` check opens an in-memory better-sqlite3 database and, when the native binding cannot load, fails with the loader's fix. A check may offer a bounded fix: an unknown `llm.activeTextProvider` becomes the first configured provider (another schema error in the file stays a reported failure), a missing MCP command turns that server off, a loose file mode becomes 600. Broken JSON and other schema errors are reported, never guessed at. `--fix` copies config.json to `<stateDir>/doctor-backups/config-<time>.json` before it edits the tree; `--undo` restores the newest copy and removes it. The state dir comes from `ATOMIC_AGENT_STATE_DIR` without loading the config, so the command runs when the config is the broken thing. Exit 1 while any check fails. Once the config is valid it also checks the local engine (installed, model on disk, enough memory, server running or its port free; external mode: the server answers) or, when a cloud provider is active, its key with one test token (Anthropic: one `GET /v1/models`) ([doctor-engine-checks.ts](doctor-engine-checks.ts)); these say the command that fixes them. The key line names where the key came from (`apiKey in config.json`, or the variable from `<stateDir>/.env` or from this shell's environment) with its length only, never a value or prefix; a `key-source` warning says when this shell's value overrides a different one in `.env`, and a malformed candidate (a placeholder such as `...`) is reported as not sent rather than as rejected.

`id` (ATO-1466, [id-command.ts](id-command.ts)) prints the support ID, the anonymous install id from `~/.atomic-agent-install-id` or `<stateDir>/analytics.json`, so a user can paste it into a bug report. It only reads; with analytics off it still prints the local id. `doctor` ends its text output with the same id.

`data backup|restore|move|reset|path` (ATO-579, [data-command.ts](data-command.ts), [data-archive.ts](data-archive.ts)) acts on the state dir the terminal and the desktop share. `backup <file.tar.gz>` writes an owner-only archive with a manifest; each `*.sqlite` goes in as a snapshot through SQLite's backup API, and `models/` (unless `--with-models`), `browser-profile/` (cookies), WAL/SHM, locks and runtime records stay out. `restore <file> --yes` unpacks into a sibling folder, refuses an archive without the manifest, carries this machine's `models/` over when the backup has none, then swaps folders and keeps the old one as `<stateDir>.before-restore-<time>`. `move <dir>` moves the folder (copy and remove across disks) and leaves a symlink (a junction on Windows) at the old path, so both apps keep finding it. `reset --keep-models --yes` moves everything but `models/` to `<stateDir>.reset-<time>`. Nothing is deleted; close every Atomic Agent first.

`data export-dataset --out <file.jsonl> [--sessions <n>] [--since <date>]` (ATO-1104, [data-export-dataset.ts](data-export-dataset.ts)) writes the stored chats as a chat fine-tuning file, one `{"messages":[{role, content}, ...]}` line per chat, newest first. Only user messages and the agent's closing answers go in (`SessionStore.listChatLines`); tool calls, tool output and progress notes never do. Every message is scrubbed first ([src/session/dataset-export](../session/dataset-export/scrub-dataset-text.ts)): keys, tokens and passwords become `[redacted:<kind>]`, emails `<email>`, home folders `~`, and the command prints how many of each it replaced. The file is created owner-only, never over an existing one, and nothing is uploaded.


`ideas list|refresh|show|accept <id> [--prompt <text>]|dismiss <id>` (ATO-458, [ideas-command.ts](ideas-command.ts)) shows and decides the suggestions built from local tasks and goals ([contract](../tasks/README.md#suggestions-ideas)). `accept` files a pending task (origin `cli`) that runs on the next drain; a Retry keeps the original task's limits, notify and folder.

`push on|off|status|test` (ATO-1129, [push-command.ts](push-command.ts)) sets up phone notifications through ntfy (`notifications.push`). `on [--server <url>] [--new-topic]` mints a random topic the first time (kept on later `on`s; a new server mints a new one) and prints the URL to subscribe to in the ntfy app plus the warning that topics on ntfy.sh are public by name; `off` keeps the topic; `test` sends one ping and exits 1 with the reason when it is not delivered. An optional access token is read from `NTFY_TOKEN` in `<stateDir>/.env`.

`overnight "<task>" [--budget <usd>] [--hours <h>] [--dir <path>] [--notify telegram] [--detach] [--no-approval]` (ATO-1113, [overnight-command.ts](overnight-command.ts)) creates one durable one-shot task (origin `cli`, one attempt) with the task's `maxCostUsd` and `maxDurationMs` (ATO-1108) and runs it. No `--budget` leaves the cap to `agent.task.maxCostUsd`; no `--hours` means 8. `--dir` becomes the runtime's working dir, so the run's session and every tool work there. Foreground prints one line per step to stderr ([overnight-progress.ts](overnight-progress.ts)) and a summary to stdout. Exit 0 when the agent finished on its own; 2 when a limit ended the run (the row is `completed` with a `stopCause`, or `blocked` with `budget_spent:` / `time_spent:`), and the summary then says `overnight stopped (<cause>)`; 1 when it failed or was cancelled (ATO-1323). An approval request is denied and counted, since nobody answers it; `--no-approval` boots at the top level. `--detach` re-runs the same command as a detached child (cwd = `--dir`, output to `<stateDir>/logs/overnight-<id>.log`) under a task id it prints first. A `task cancel` from another terminal is seen within 5 s and aborts the turn. The task carries `agent.task.maxSteps` as its step ceiling, so the per-leg `agent.maxSteps` does not end the run. Ctrl+C (SIGINT) cancels the task; SIGTERM and SIGHUP (shutdown, logout) stop the run the way a runtime shutdown does and leave the task pending to resume. Step lines count what the task spent before this run toward the cap.

`export <sessionId>|--last [--format md|html|docx] [--out <file> [--force]] [--no-tools]` ([export-command.ts](export-command.ts), ATO-1054) writes one chat through [exportChat](../session/chat-export-render.ts), masking the same known secrets tool output is masked with. Markdown and HTML go to stdout unless `--out`; DOCX goes to `--out` or a file named after the chat; an existing file needs `--force`. `--last` is the newest chat someone wrote in; an incognito chat is refused (exit 1). Exit 0, 1 when it failed, 2 on a usage error.

`fusion report [--days N] [--model X] [--json]` ([fusion-command.ts](fusion-command.ts)) prints the fusion outcome log aggregated per worker model and orchestrator provider (format and fields: [fusion README](../tools/fusion/README.md)); `/fusion report` in the TUI prints the same text. Exit 0, 1 when the report cannot be produced, 2 on a usage error; `--model` matches a model or provider id case-insensitively.

`fusion recover <journal> --project <dir> [--status|--dry-run|--rollback] [--json]` ([recovery command](fusion-recovery-command.ts)) inspects an interrupted candidate promotion. The default and `--status` are read-only; `--dry-run` validates backups and reports the proposed reverse steps without writing. Only `--rollback` restores entries that still match the delivered bytes/type/mode and preserves later user edits as conflicts. The selected project, version-2 journal, paths, backup hashes and process owner are validated before mutation. A live owner, unknown/legacy journal, corrupt backup or unsafe path refuses recovery. Committed delivery cannot be rolled back. A completed rollback keeps its terminal journal and backups; repeating it preserves subsequent edits. Nothing runs automatically at startup. Exit 0 for status/complete recovery, 1 for failure/conflicts, 2 for usage; `--json` returns state, owner, planned/restored paths and conflicts. See the [fusion recovery limits](../tools/fusion/README.md).

`models recommend --role worker [--json]` ([models-recommend.ts](models-recommend.ts)) names the model for fusion's workers instead of the three tiers: among the models this machine carries, by catalog fusion-worker rating (`good` > `ok` > unrated > `poor`), then room for `localModels.managed.parallel` worker slots, then rank, and prints why. `--json` keeps the default fields and adds `role` and `worker` (`{model, rating, ratingNote, slots, slotsWanted, needGb, why}`, `null` when nothing fits). Without `--role` (or `--role default`) the output is unchanged; another value exits 2.

## Fusion setup

`setup fusion [--yes] [--dry-run] [--judge] [--isolation] [--orchestrator <id>] [--orchestrator-model <id>] [--budget <usd>]` ([setup-command.ts](setup-command.ts)) switches to Fusion in one step. [setup-fusion-detect.ts](setup-fusion-detect.ts) reads config.json without creating it (an invalid file is named with "Fix or move <path>", exit 1), loads `.env`, asks `providers status`' check about Claude Code (no turn), and lists models on disk; an external llama-server gets a 1.5 s `/health` probe. The pure [planner](../llm/run-mode/fusion-setup-plan.ts) ranks the orchestrators that can answer: the stored fusion orchestrator unless it is definitely not ready (an inconclusive check, such as the CLI check timing out, keeps it with a warning; a replaced one is named with the reason), then the active text provider when it is a cloud one, then a signed-in subscription CLI (a configured entry, else a new keyless `claude-cli` entry), then other keyed cloud providers with Best/Balanced [tier](../llm/provider/presets/model-tiers.ts) models before Cheap ones. Last comes a cloud [preset](../llm/provider/presets/provider-presets.ts) whose key variable is set (shell or `.env`, e.g. `ANTHROPIC_API_KEY`) while no entry reads it: the facts carry the variable's name only, and setup adds the entry the TUI's preset wizard would save (`presetEntryFields`: its URL, `apiKeyEnvVar`, and the key header and headers of an `openai-compatible` one; Anthropic's is a native `kind: "anthropic"` entry). Its model is the preset's default chat model; a preset without one needs `--orchestrator-model <id>` (one value applies to the preset `--orchestrator` names, else only when a single such preset was found, and is checked against the listed models when the endpoint answered), and a terminal run lists the chat models the preset's `/v1/models` serves (asked with that key, embedding/speech/moderation/image ids dropped) and asks. That list is asked only when setup could choose the preset: `--orchestrator` names it, or no configured orchestrator is ready; otherwise no request goes out, `--dry-run` included. When the pick is Claude Code although `ANTHROPIC_API_KEY` was found, the plan says so and names `--orchestrator anthropic`. An unknown `--orchestrator` says to add it in the TUI (Esc → Manage › LLM › Cloud → n) or put its key in `<stateDir>/.env`. A key alone does not outrank a subscription: it may be there for a cheap or embedding model. Each leg shows its provider, model (`defaultChatModel`), tier when listed, and per-token or flat-rate billing; a Cheap tier orchestrator gets a warning. With more than one ready, a terminal run lists them and asks for a number (Enter keeps the first); `--yes`, `--dry-run` and a non-terminal print the others, and `--orchestrator <id>` picks one without asking ([setup-terminal-prompt.ts](setup-terminal-prompt.ts) reads both questions from one line reader). The worker is the first `llama-server` entry, served by the managed engine with its model on disk, or by an external server that answers. Otherwise it exits 1 with the next step: the `.env` variable or Manage › LLM › Cloud for a key, the Claude Code sign-in or install command, `models use <id>` for a model already on disk, or `models pull <id> --background` for the machine's balanced catalog pick.

It prints each change (`(unset) → value`), asks (a non-terminal needs `--yes`), and writes through [applyFusionSetupInConfig](../config/fusion-setup-commands.ts): one validated write of the new entry, `llm.activeTextProvider`, `llm.runMode.mode` and the fusion block. The legs are always pinned; the rest is filled only where unset, so a value you wrote is kept, and so is an enum value a newer build wrote ("kept (set by a newer version)"): `autoReplan: 1`, and on a priced orchestrator `escalation: "advisor"` and `turnBudgetUsd: 1` (the advisor's dollar cap needs a price; on a subscription leg only the counted caps hold a turn). A note explains the turn cap: once a turn's spend reaches it, no new delegation or worker starts and the orchestrator reports what is done and what is left in one short final reply (up to 4096 tokens); a reply already running when the cap is reached, and that final reply, are charged on top, so a turn can end a little over the cap ([request budgets](../runtime/docs/request-budgets.md)); 0 means no cap. `config set` cannot address the fusion block, so `--budget <usd>` sets it (over a stored value too; `--budget 0` for none). `judge` and `isolation` (a global setting) stay off unless `--judge`/`--isolation` is passed; the output says so. A re-run that changes nothing prints "already set up" and exits 0. `--dry-run` writes nothing.

[skill-eval-diff-formatter.ts](skill-eval-diff-formatter.ts) (ATO-1100) renders the `skill eval` result: one row per task plus a total, accuracy (passed/total), wall time and tokens in/out as `without -> with` with a delta column (accuracy in percentage points, the rest in percent; `n/a` against a zero baseline), and a verdict line. A task missing one side shows `-` and stays out of the total. Verdict: accuracy moved by 10 points or more decides; otherwise time or tokens down by 20% or more with nothing up by 20% is helped, the mirror is hurt, anything else is no clear difference. Plain text unless the caller passes `color` (`shouldUseColor` honours NO_COLOR and FORCE_COLOR).

`models toolcall-bench [--models a,b] [--tries n] [--json]` (ATO-1092, [models-toolcall-bench.ts](models-toolcall-bench.ts)) sends the fixed prompts of [toolcall-bench](../llm/toolcall-bench/bench-cases.ts) to each model `n` times (default 3, at most 50), one request at a time, and prints per model the share of tries with valid JSON arguments, the right tool and every required argument, plus parse failures, text-only answers, errors and the mean time of a try. A model is `<provider>` (its configured chat model) or `<provider>:<model>`, split at the first colon; no `--models` means the active provider. Only native-tools links are measured: the built-in local link and subscription CLIs use a grammar or their own CLI and are skipped with a note; to bench a local model, add its server as an openai-compatible provider. `models ask "<question>" --models a,b [--json]` sends one question, no tools, to every named model at once and prints the answers one after another under each model's name; exit 1 only when every model failed.

## Desktop state merge

`import atomic-desktop --source <dir> [--json]` merges the desktop app's former state dir (`~/.atomic-agent-desktop`) into the current one (`ATOMIC_AGENT_STATE_DIR`, default `~/.atomic-agent`) when the desktop moves onto the shared dir (ATO-416). The desktop runs it once and moves the plain files (config.json, .env, skills, traces, models) itself; this command handles only the databases:

- sessions and tasks keep their ids and are inserted only where the id is absent, so the target wins. A live turn arrives ended as interrupted, a running task arrives pending, and neither carries an owner mark.
- memory notes are added through `MemoryStore` unless the same text is already stored; profile facts through `ProfileStore` unless the target has any row for the key.
- lessons, procedures, votes, note links and embeddings are not copied; the embedding backfill or `memory reindex` rebuilds vectors.

Each source database is read from a private snapshot (a byte copy after a clean close, otherwise SQLite's online backup over a read-only connection), so the source is never written and nothing is deleted. Writes are short transactions that wait on the target's locks, so a TUI or `serve` may keep the target open. A re-run imports nothing new. `--json` prints one object, `{ok, sessions:{imported,skipped}, tasks, notes, profileFacts, warnings, error?}`; exit 0 only when every part imported. Implementation: [atomic-desktop importer](../import/atomic-desktop/atomic-desktop-importer.ts).

Checks: `npx vitest run src/cli` when tests are present; `npm run lint`; `npm run docs:check`.

## Handoff

`handoff --from claude-code|codex [--session latest|<id>] [--cwd <dir>] [--note <text>] [--list] [--json] [--no-open]` continues a Claude Code or Codex session that stopped mid-task (ATO-1154). It reads their transcript through the import readers ([handoff source](../import/handoff/handoff-source.ts)), saves it as a NEW native chat with a fresh `s-` id ([handoff session](../import/handoff/handoff-session.ts)), closes trailing tool calls that never got a result, and opens the TUI on it with `--session <id> --send <continuation message>`. `latest` is the newest session that ran in the current folder, else the newest anywhere; while `projects.constraints` has any entry, that fallback is refused when the chat would continue in another folder than the transcript's (name it with `--session`), and a transcript continued outside its folder keeps that folder's restriction as a read taint (issue #68, [provider policy](../llm/docs/provider-policy.md#read-taint)). `--list --json` prints `{from, sourceDir, sessions:[{agent,id,mtimeMs,cwd,title,messageCount}]}`; `--json` without `--list` saves the chat without opening it and prints `{ok, sessionId, title, workingDir, from, sourceSessionId, turns, closedCalls, prompt}` (the desktop uses both).

Before saving, the carried history is fitted into a local model's window (ATO-1155, [fit-context](../import/handoff/fit-context.ts)): when it is larger than half the window (`--context <tokens>`, default the managed model's pinned `contextSize`, else 32768; `0` skips this), the head becomes an extractive checkpoint (`SessionCompaction`, `kind: "extractive"`, no model call) cut at a safe boundary, the newest records stay verbatim, and very long tool outputs in that tail are clipped in the middle. `--json` reports it under `context`.

## Share

`share [--session latest|<id>] [--format html|md] [--out <file>] [--gist] [--json]` (ATO-581, [share-command.ts](share-command.ts)) writes one chat to a single file for a colleague. It reads only `SessionStore.listChatLines` (user messages and closing replies), so tool results and reasoning never enter the file, then runs each message and the title through [chat-export redaction](../session/chat-export/chat-export-redact.ts): shared secret detector plus a looser layer, absolute paths to `[path]` (paths under the chat's folder keep their tail as `<project>/...`), emails, IPv4, URL query strings and `<think>` blocks. HTML is self-contained with a `default-src 'none'` CSP and no script; text is escaped before a small Markdown subset is applied. Default file: `<stateDir>/shared-chats/chat-<id>.<ext>`, owner-only. `latest` is the newest chat in the current folder, else the newest anywhere; a unique id prefix works.

`--gist` is the only path off the machine ([share-gist.ts](share-gist.ts)). After writing the file it prints a preview (title, message count, what was removed, first messages, who can read a secret gist) and asks `[y/N]` in a terminal; only a typed y/yes uploads, with `gh gist create <file> --desc <title>` (secret, `--public` never passed; the token stays in gh). Without a terminal it refuses and exits 1. It also refuses (the file stays local) in offline mode and for a chat whose folder constraint or read taint lacks the `github` egress class (issue #33); an incognito chat is not shared at all. With `--gist` and no `--format` the file is Markdown, since GitHub renders Markdown and shows HTML as source. `--gist` cannot be combined with `--json`.


## MCP server

`mcp-server [--allow-write] [--allow-exec] [--tool <name>]... [--cwd <dir>]` (ATO-549) serves the agent's own tools to another MCP client (Claude Code, Codex, Cursor) over stdio, e.g. `claude mcp add atomic-agent -- atag mcp-server`. It boots no runtime and no model: [mcp-server-command.ts](mcp-server-command.ts) opens the memory database and the skill folders, [mcp-server-tools.ts](mcp-server-tools.ts) builds the tools with the runtime's own builders, and [mcp-server-bridge.ts](mcp-server-bridge.ts) answers `tools/list` and `tools/call` through a `ToolRegistry`, so secret masking applies. It exits when the client closes stdin; stdout carries only the protocol.

- Default, read-only: `memory_notes_recall` (keyword recall; embeddings are not attached here), `memory_lessons_recall`, `memory_procedures_recall`, `memory_profile_list` (each only when its `memory.*` family is on), `skills_list` and `skill_view`. Project skills load only from a folder the user trusted, as in the runtime.
- `--allow-write` adds `memory_notes_store` and `memory_profile_set`.
- `--allow-exec` adds `os_shell_run`. Every command still goes through `ApprovalGate` with the user's `agent.approvalLevel` and saved rules; the session (`mcp-server`) runs under a refuse policy, because an MCP client cannot show the approval prompt. So a command that would ask is refused with a message telling the client to ask the user, and only a level or an allow rule lets one run. The hardline shell guard blocks as always.
- `--tool` narrows the set (wire or dotted name); a name the flags do not allow is a usage error (exit 2).

Tool names on the wire use `_` for `.` because several clients accept only `[A-Za-z0-9_-]`. Results carry the whole text (`modelMode: "cloud"`), not the local model's short previews. Not done yet: HTTP transport in `serve`, a session turn or task tools.


`handoff --to claude|codex [--out <file> [--force]] [--session latest|<id>] [--cwd <dir>]` goes the other way (ATO-1158): it reads one Atomic Agent chat (`latest` = the newest chat in the folder, else the newest anywhere) and writes a Markdown handoff for the other agent ([handoff export](../import/handoff/handoff-export.ts)): the task and the latest request, the agent's last answers as decisions, open items (a turn that did not finish or was stopped), and the files changed by successful `os.fs.write|edit|move` calls and applied `os.fs.patch` calls (shell changes are not tracked). It goes to `--out` (relative to where the command ran; an existing file is kept unless `--force`) or to stdout, with the runtime's known secrets masked like `export`; an incognito chat is refused, and so is a chat whose effective provider policy (folder or read taint) is restricted unless one of its allowed provider ids names a configured provider of the target's vendor (`claude`: an `anthropic` or Claude subscription entry; `codex`: a Codex subscription entry or an `openai-compatible` one on api.openai.com); the refusal names the folder and the `allowedProviders` to extend (issue #68, [provider policy](../llm/docs/provider-policy.md#what-is-enforced)). Nothing is written into `~/.claude`, `~/.codex` or the session store: their session formats are undocumented, so the person hands the file over themselves. Serving Atomic Agent to those tools over MCP/ACP is ATO-990, not this command.

`serve` API key (issue #74, [serve-command.ts](serve-command.ts)): `--api-key <k>` or, when the flag is omitted, `ATOMIC_AGENT_API_KEY`. A launcher should prefer the environment variable, which `ps` does not show (the desktop passes its per-launch key that way). serve deletes the variable from its own environment right after parsing, so tools, shells and child processes never inherit it.

The [serve memory guard](serve-memory-guard.ts) samples heap and resident memory. Near exhaustion a supervised server shuts down with exit code 86 and leaves interrupted task runs marked as crashed. An unsupervised server reports the pressure and keeps running. Set `ATOMIC_AGENT_MEMORY_GUARD=0` to disable the guard.
