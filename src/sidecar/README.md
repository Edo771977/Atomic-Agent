# NDJSON sidecar

Status: current
Owner: src/sidecar/

Owns stdin/stdout transport and host event forwarding. Preserve protocol shapes, request/session ownership and the already-acquired turn lock seam.

Entry point: [main.ts](main.ts). Read the root instruction route and the underlying domain instructions before cross-domain changes.

`skill_list` uses the active cloud session's workspace and includes disabled reasons and selected source paths. Independent local sessions retain their existing registry. See [cloud workspace](../runtime/docs/cloud-workspace.md).

Checks: `npx vitest run src/sidecar` when tests are present; `npm run lint`; `npm run docs:check`.

Context controls: `compact_session` and `get_compaction` take `{sessionId}` and use normal response correlation; `compact_session` also takes an optional `instructions` string (what the summary must keep, at most 2000 characters). Session compaction lifecycle and part-progress events are forwarded with their session ID. `send_message` reloads saved state inside its existing FIFO lock, preserving checkpoints written between turns. See [context compaction](../runtime/docs/compaction.md).

`skill_install` security-scans the folder before copying ([install scan](../skills/docs/skill-format.md#install-security-scan)). A `caution` verdict fails the request (its message lists the findings summary and ends with `[scanId <id>]`) unless the payload has `confirm: "<id>"`; a `dangerous` one fails unless `acknowledgeRisk: "<id>"`. `true` or an older scan's id is not a yes.

Approvals ([approval-payload.ts](approval-payload.ts)): `approval_request` carries the prompt (`tool`, `category`, `reason`, `preview`, `affectedResources`), `commandShape`, `riskNote` / `riskLevel` / `riskReason` when smart approval ran (each surface draws them with `formatRiskLine`: `Risk check: medium. Installs a package`), and which remembered answers the request can take: `canSession`, `canShape`, `canAlways` and, when `canAlways`, `alwaysLabel`. `approval_response` takes `{approvalId, approved, reason?, grant?}` with `grant` one of `session` (the category for this chat), `shape` (this binary for this chat) or `always` (save an allow rule for the project). A grant the request cannot take fails the request and the approval stays pending (ATO-1270). A session grant can cover one site rather than the whole category: a browser submit or off-site request is granted per host (ATO-1181) and an HTTP request per origin (ATO-1182). Such a request carries `grantHost` (`shop.example`, `https://api.example.com`) so the host can label the choice; the response may echo it as `grantHost` with `grant: "session"`. The agent always takes the site from its own pending request, so the field cannot widen a grant: a `grantHost` that is not the request's own site, or one sent without `grant: "session"`, fails the request and it stays pending. Without `grantHost` a session grant behaves as before (ATO-1474).

`cancel` (`{sessionId}`) aborts the running `send_message` turn and the ones queued behind it, as the TUI's Esc drops its parked messages; the session stays usable, and a `send_message` sent after the cancel runs normally. It also cancels that session's compaction.

`get_provider_restriction` (`{sessionId}`) answers the session's per-folder provider restriction (`{label, allowedProviders, folder, readFrom}`) or `null` ([provider policy](../llm/docs/provider-policy.md#status)).

A request's `sessionId` on `compact_session`, `get_compaction`, `get_session`, `get_provider_restriction`, `get_project` and `project_decision` must pass the shared session id check (no `/`, `\`, `..`, leading `.` or control characters, at most 256 characters; issue #74, [session-id.ts](../session/session-id.ts)); any other value fails with `invalid sessionId: …` before the handler looks at the active runtime.

`budget_notice` carries `{sessionId, providerId, reason, text}` when a request uses soft/meter budget enforcement or its output ceiling is reduced to fit. The notice belongs to that session and owning turn; retries do not repeat the same provider/reason warning.

`send_message` takes optional `director` / `worker` / `reviewer` (`"<providerId>:<model>"`, issue #37; `reviewer` may be `"none"` or `"team"`, which clears the choice, issue #71), stamped on the session inside the already-locked turn; `fusion_director_notice` carries `{sessionId, member, reason, text}` when the runtime picked the session's director (`only`, `default`) or the director is a Codex CLI (`codex-direct-tasks`).

## Fusion project card (issue #39)

The contract the desktop app (a separate repository) draws its project card from.

- Capability: the project flow is opt-in per session. `start_session` `{workingDir, metadata?, capabilities?: {project?: boolean}}`: only `capabilities.project: true` gives the session the `project.*` tools and the director's project guidance, and with them the gates below. Absent (the default until the desktop card ships) or anything but `true`: no project tools, no gates, and a fan-out asks for approval as before. The answer is fixed for the session on its first turn (`metadata.projectGates`), because it is part of the session's stable prompt prefix; declare it when starting the session, not later. Types: [sidecar-events.ts](sidecar-events.ts) (`ProjectGateEventPayload`, `GetProjectPayload`, `ProjectDecisionPayload`, `ProjectDecisionResult`) and [ProjectGateView](../session/project-gate-view.ts), all exported from [index.ts](index.ts).

- Event `project_gate` `{sessionId, view}`: the active session's gate (brief, plan or a finished milestone) opened or changed; the whole view, never a delta. `view` (`schema: 1`, `sessionId`) holds `brief` or null (`what`, `users`, `how`, `game?`, `successCriteria`, `status`, `draftedAfterUntrusted`: show a warning when true), `plan` or null (`status`, `detail` `compact`/`full`, `version`, `draftedAfterUntrusted` (show the plan warning when true: approving lets its tasks run without asking again), `totals` (`costUsd`, `ms`, `unknownCostRows`) and `rows[]` (`taskId`, `title`, `milestoneId`, `worker`, `reviewer` or null, `reason`, `basis` `measured`/`preset`, `samples`, `estCostUsd` and `estMs`, either null when unknown, `local?` (true: a local worker, `estCostUsd` 0, shown as "$0.00 (local)" and not counted unpriced), and `selectableWorkers[]` / `selectableReviewers[]`, the members the person may pick), and `editable` (false when no row offers a choice: hide or disable "edit rows"; `edit` stays allowed)), `milestones[]` (`id`, `title`, `kind`, `state`, `runIds`, `summary?`, `corrections?`, `attachments?`, `criteriaFacts?`, `estCostUsd`, `estMs`), `gate` (`none`, `brief`, `plan`, `{kind: "milestone", id}`), `version` (null when nothing can be decided), `allowedVerdicts`, `cancelled`, `violations[]` (`kind`, `severity` `hard`/`warn`, `message`, `milestoneId?`, `taskId?`; approve is refused while a hard one stands), `hints[]` (one-line advice to show as is, issue #54: at the plan gate, that no reviewers are configured, that only one worker is available, or that no other team member is reachable now; empty otherwise) and `expectation`. Plan rows carry no file list: say on the card that approving lets the tasks write in the session's folder (a write outside it still asks), as the terminal card does.
- Quality evidence (issue #40, additive within `schema: 1`): `brief.successCriteria` stays the criteria's texts and `brief.criteria[]` carries each as `{id, text}`. A milestone may carry `attachments[]` `{path, caption, criteria?}` (at most 8: screenshots of its result; `path` is absolute, directly inside `<stateDir>/fusion-runs/<runId>/shots/` of one of its runs, checked when the director reported it; `criteria` are the criterion ids it shows) and `criteriaFacts[]` `{id, state: "passed"|"failed"|"unverified", why?}` (one per criterion, from its checks and the vision judgement; `unverified` blocks like a failure until the director decides). Show the caption and the path. The desktop renders the image through its own safe file read (an IPC that reads only an image under that state dir), never by handing the path to a web view: a follow-up for #47.
- Request `get_project` `{sessionId}` → `{sessionId, view}` (`view: null` without a project): draw the card on reopening a chat.
- Request `project_decision` `{sessionId, gate, version, verdict, edits?}`: `gate` and `version` exactly as the view gave them; `verdict` one of `view.allowedVerdicts` (draw the buttons from that list, never a fixed one); `edits.rows[]` `{taskId, worker?, reviewer?}` (null reviewer: no review) at the plan gate; `edits.decisionStatus` `{<decisionId>: "active" | "deferred" | "informational"}` with `edit` at the plan gate (issue #112: the person defers a decision the plan does not cite; the view's optional `decisions[]` `{id, text, status, citedBy}` lists them, and a plan check `decision-coverage: fail` hint names the uncited ones); `edits.note` (at most 2000 characters) the person's correction with `edit` at a milestone gate. A malformed payload fails the request. Otherwise the response is `{ok: true, view, continueMessage}` (draw `view`: an edit, `cheaper` or `quality` re-estimates the plan, which waits for approval again; when `continueMessage` is not null, send it with `send_message` so the director goes on: the runtime never continues by itself) or `{ok: false, error: {code, message}, view?}` with the runtime's code (`no-project`, `stale-version` or `wrong-gate`: redraw from `view`; `over-cap`; `verdict-not-allowed`; `turn-running`: decide again when the turn ends; `no-session`) and the current view.

Decisions are taken between turns; approval only ever comes from the person, and an unattended session stays at the gate.

## Fusion projects list (issue #109)

What a host's project list draws, additive to the requests above; every answer carries `schema: 1`. Types: [sidecar-events.ts](sidecar-events.ts) (`ListProjectsResult`, `ForgetProjectPayload`/`Result`, `ResumeProjectPayload`/`Result`, `GetProjectProblemPayload`/`Result`). The listing and the resume are `atomic-agent projects list` and `project resume`'s own code ([projects-command.ts](../cli/projects-command.ts)).

- `list_projects` `{}` → `{schema, projects, registryProblem}`: `projects` are the `projects list --json` rows (`folder`, `status` `ok`/`missing`/`damaged`/`unsupported`/`unreadable`, `zone` (issue #121: `needs-you`, `problem`, `in-progress`, `idle` or `done`, [project-attention.ts](../session/project-attention.ts); a list shows them in that order, the most recent first within each), and for `ok` `name`, `id`, `gate`, `next`, `updatedAt`, `spentUsd` (null: no recorded runs), `notices?`; otherwise `problem`). `registryProblem` (the list file could not be read; it is left as it is) comes with an empty list.
- `forget_project` `{folder}` (absolute) → `{schema, folder, forgotten}`: off the list only; the folder's files stay.
- `resume_project` `{folder}` (absolute, one the list names) → `{schema, ok: true, folder, name, sessionId, created, view}`: the newest chat on the folder's project, or a new one bound to it, becomes the active session with the project flow on (`session_started` follows, as for `start_session`); `view` is its gate. `{schema, ok: false, folder, error: {code, message}}` with `not-listed` or `project-unavailable` leaves the active session as it was.
- `get_project_problem` `{sessionId}` → `{sessionId, problem}`: why the session's project did not open (damaged, unsupported, an unusable record), `null` when it opened or there is none; `get_project` answers `view: null` for such a session.
