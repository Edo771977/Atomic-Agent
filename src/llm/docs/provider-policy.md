# Per-folder provider constraints

Status: current (issue #33 §5)
Owner: src/llm/ ([provider-policy.ts](../provider-policy.ts))

A folder listed in `projects.constraints` may only send a session's content to the provider ids it names. The setting, its fail-closed parsing and the folder matcher belong to config ([compatibility](../../config/docs/compatibility.md#per-folder-provider-constraints), [matcher](../../config/project-constraint-match.ts)). This page is the enforcement: every request that carries session content is checked at dispatch, against the provider that would actually receive it, before anything is sent. It is not prompt wording; nothing here can be lifted by the model.

## API (for callers and later work)

- `resolveProjectConstraint(config, workingDir)` → `ProviderPolicy | undefined`: `{ key, allowedProviders, allowedEgress, matchedDir, allows(providerId), allowsEgress(class) }`, or `undefined` when no entry covers the folder. `hasProjectConstraints(config)` says whether any entry exists. `toProviderPolicyStamp` / `providerPolicyFromStamp` carry a policy through session metadata.
- `runWithProviderPolicy(policy, fn, { role })` runs `fn` in an AsyncLocalStorage frame; `currentProviderPolicy()` / `currentProviderPolicyFrame()` read it, `currentPolicyAllows(id)` answers for the frame (no frame or no policy: allowed), `runWithProviderRole(role, fn)` keeps the policy and names the caller for a refusal.
- `ProviderNotAllowedError` (code `ATOMIC_AGENT_PROVIDER_NOT_ALLOWED`), found anywhere in a cause chain by `isProviderNotAllowed` / `findProviderNotAllowed`. `assertProviderAllowed(id, { constraintsActive })` throws it; `providerPolicyRefusalFor(id, role)` returns it for callers that answer with a tool error; `noAllowedProviderError(policy, role)` is the terminal refusal.
- `tightenCurrentProviderPolicy(policy, cell?)` narrows a running frame (read taint); `intersectProviderPolicies`, `policyCovers`; a policy's optional `readFrom` names the folders a taint came from. `describeProviderRestriction` / `formatProviderRestrictionLine` word it for frontends.
- `guardProvider(provider, { constraintsActive, endpoint? })` wraps an `LlmProvider` so `complete`, `completeStream` and `describeImage` check first, the endpoint too when given (`providerEndpointOf`, `providerEndpointRefusal`). Everything else passes through.

- `effectivePolicyForSession(sessionOrId)` ([session policy](../../runtime/session-provider-policy.ts)) is the one read every egress check makes: the running turn's (tightenable) frame when it was set for that session, else the session's folder intersected with its stored read taint (fail closed for an unknown id).

A frame with `policy: undefined` is an unconstrained folder. No frame at all while any constraint exists is a caller nobody scoped, and every guarded call refuses it (fail closed).

## Where frames come from

- Folder matching ([match](../../config/project-constraint-match.ts)) reads a path inside a linked git worktree as the same path in its main repository (the worktree's `.git` file names `<repo>/.git/worktrees/<name>`), so a `/new worktree` session (ATO-576), whose folder lives under `<stateDir>/worktrees`, keeps its repository's constraint for its turns, read taint and write-out.
- `executeTurn` and `runTurn` run inside the session's frame ([session policy](../../runtime/session-provider-policy.ts)), so the turn, its tools, the goal judge, compaction, naming and reflection started from it are covered. Roles: "the main model", "a fusion worker".
- A fusion worker obeys its parent's turn: `createEphemeralSession` stamps the frame running at fan-out into `FusionWorkerMeta.providerPolicy` (`null` for an unconstrained parent). The worker's own folder, often a temp copy, is never matched. A worker without a stamp while constraints exist is refused everything.
- A session a session's tool creates obeys its caller: `tasks.schedule { newSession: true }` and `tasks.cron` provision the task's session in the caller's folder (never the runtime's) with the caller's effective policy stored as its read taint (`childSessionSeed`, [task services](../../runtime/composition/runtime-task-services.ts)); a caller that resolves to nothing gives a refuse-all taint. A recurring task whose session was deleted is not recreated while any constraint exists: it is blocked as `session_not_recreated:` (the factory could not know the original folder or taint). Fusion and these task tools are the only sessions a model can create; HTTP, CLI and channel sessions are created by an operator or a chat and are matched by their own folder.
- The fallback seam gives a call that arrives with no frame, or inside a frame set for another session, but a `sessionId` that session's policy (`effectivePolicyForSession`: its folder, stored and live read taint), never the other session's frame (a side call's `reflection:<id>`, `compaction:<id>` partition reads as `<id>`). An id that names no stored session is refused everything.

## What is enforced

- Every provider the registry builds is wrapped by `guardProvider`, so direct `getProvider(id)` callers are covered: escalation ("fusion escalation"), the judge ("the fusion judge"), the local format check ("the fusion format check"), `vision.describe` (`describeImage`), subscription CLIs (they are providers). The escalation seam and format check also check explicitly before the spend ceiling.
- The fallback seam checks the asked id before `prepareLink` (no warm-up for a refused link) and again the id of the provider `resolveSlice` returned, since an unknown id resolves to the active provider.
- The chain ([fallback](fallback.md)) drops every link the frame's policy does not allow, primary included, and starts on the first allowed one. A refusal advances without the immediate signal, records no breaker failure, cooldown or sticky override, classifies as `transport` and is never an outage (no provider wait). With no allowed link left the call fails with `folder <key> is restricted to: <ids>; no allowed provider can serve <role>`. A turn that ends on such a refusal (or on an egress refusal, `ATOMIC_AGENT_EGRESS_NOT_ALLOWED`) is shown by [constraint-refusal.ts](../../runtime/constraint-refusal.ts) the same way on every surface: "This folder is restricted to: <ids>. <Role> can't use <provider> here." with the hint "switch to local with ctrl+r or /runmode local" when a local model is configured, else to edit `projects.constraints`; the TUI adds no `/report` hint, CLI `run` prints `» turn stopped [<code>]: …`, and the sidecar's `session_failed` and the HTTP failure frame carry the code as `code` and the sentence and hint as `advice`.
- The model router ([router](../router/README.md)) never picks a provider the folder does not allow.
- Fusion: the orchestrator not allowed but the worker leg allowed → the turn runs pinned to the worker leg as a single model and `fusion.delegate` is hidden and refused; only the orchestrator allowed → it works alone without `fusion.delegate`; neither → no fan-out, and the chain refuses unless another allowed link exists ([degradation](../../runtime/fusion-policy-degradation.ts)).
- Memory embeddings are judged by place, not id: an endpoint on this machine (loopback URL, or Atomic Core's embedding module) is always allowed; any other is refused in a constrained folder as `EmbeddingUnavailableError`, so recall falls back to full-text search and nothing is sent ([guard](../../memory/embeddings/embedding-policy-guard.ts)). The one exception is a computer on the local network the folder lists in `allowedProviderHosts` (`networkEndpointListed`, issue #60); a public endpoint stays refused even when listed, since embeddings have no provider id for the id-only match.
- Core-proxied media (`image.generate`, `video.generate`, and Core's OpenRouter key registration as a backstop) is refused unless the folder allows `openrouter`, where Core sends the job.
- A local provider allowed by id is also judged by where it is (issue #60): `llama-server`, and an `openai-compatible` / `qwen-openai-compatible` entry not marked `modelMode: "cloud"` and not on a known cloud service, is refused at dispatch when its endpoint is another computer on the local network, unless the folder lists that host in `allowedProviderHosts`. "On the local network" is the private-network form `isLocalServerUrl` reads (RFC 1918, link-local 169.254/16 and `fe80::/10`, CGNAT 100.64/10, unique-local `fc00::/7`, `.local`, `.lan`, `.home.arpa`, `.internal` and the other own-network suffixes, single-label names); this machine is always allowed, by literal address only (`localhost`, 127/8, `::1`, IPv4-mapped `::ffff:127.x`; not `*.localhost`, `0.0.0.0`, or a 6to4 / NAT64 / IPv4-compatible spelling of 127.0.0.1, which are judged as network hosts), and any public host keeps the id-only match (OpenRouter, Gemini, DashScope or a company gateway reached through `openai-compatible` are services the operator named). The endpoint is read at each call (`providerEndpointOf`: the entry's `baseUrl`, or a `llama-server`'s own `url`, else the live `localModels.url`), so a base URL repointed at another computer ("find on my network") is refused before anything is sent; an endpoint that cannot be read is refused too (fail closed). The refusal (reason `remote-endpoint`, same code) reads `provider "<id>" is allowed, but its endpoint <host> is another machine; nothing was sent. To allow it, add "<host>" to projects.constraints["<key>"].allowedProviderHosts`; the turn's line names the host and gives that as the hint instead of "switch to local". Cloud providers (the `anthropic`, `openrouter`, `gemini`, `aimlapi` and subscription kinds, and an `openai-compatible` entry on a known service) keep matching by id alone. The chain skips such a link like any refused one ([provider-policy.ts](../provider-policy.ts) `providerEndpointRefusal`, wired by the [registry](../provider/registry/provider-registry.ts)). Listing hosts rather than one switch keeps the opt-in to one computer: a later repoint to another host is refused again. The list travels with the policy (stamps, read taint, fusion workers) and intersects like the others; an older stamp carries none. Unconstrained folders are unchanged. `atomic-agent doctor` warns about each such provider a constrained folder allows. Compaction's exact token count, which POSTs the transcript to the llama-server's `/tokenize`, asks the same question first against the session's effective policy and falls back to the byte estimate when the server is a computer the folder does not list ([counter](../../runtime/compaction-token-counter.ts)). `replayInference` ([replay](../../replay/replay-inference.ts)) re-sends recorded prompts through whatever client its operator passes; no shipped command calls it, and a raw `LlamaServerClient` passed to it is not guarded, so a caller must pass a registry provider to keep the check.

## Egress (`allowedEgress`)

A constrained folder's tools may not send its content off the machine unless the entry's `allowedEgress` names their class; the default is none. The [tool registry](../../tools/tool-registry.ts) runs the guard ([inventory](../../tools/tool-egress.ts), [runtime wiring](../../runtime/composition/runtime-egress-guard.ts)) before the call: the batch scheduler asks `refusalBeforeDispatch` ahead of PreToolUse hooks and the approval ledger, and `invoke` checks again, so a refused call never prompts and never sends. The refusal (code `ATOMIC_AGENT_EGRESS_NOT_ALLOWED`) reads `folder <key> is restricted: <tool> would send content off this machine; add "<class>" to projects.constraints["<key>"].allowedEgress to allow it`.

| Class | Tools |
| --- | --- |
| `web` | `os.web.search`, `os.web.fetch`, `os.web.crawl` (a loopback URL stays allowed). Past a bot wall, `os.web.fetch` asks again per step: its browser render needs `browser`, a Jina Reader or Firecrawl read `http`; a refused step is skipped and named in the result |
| `http` | `os.http.request` (a loopback URL stays allowed); `os.web.fetch`'s reader-service step; OTLP span export to a collector off this machine (the session's spans are dropped otherwise, [gate](../../runtime/composition/runtime-otlp-gate.ts); an incognito chat never exports, and while one is open nothing does) |
| `browser` | every `browser.*` tool, `video.render_html` and every `verify.run` page probe (`kind: "page"`), local files and dev pages included: a local page can still load remote resources, and the page acted on may be remote whatever the arguments say. List `browser` to use a local page |
| `github` | `github.*`; the TUI issue report (environment facts only for a refused session; its traces and log lines left out) |
| `git` | `os.git.fetch`, `pull`, `push`, `clone` |
| `mail` | `os.email.*` (Atomic Mail); the mail trigger's `replyByEmail` answer |
| `channels` | `tasks.schedule` / `tasks.cron` with `notify`; a turn sent from Telegram, Discord, a swarm bot or a catalog chat (Slack, Signal, Matrix, Teams, Google Chat, iMessage); a task's report and live snapshots |
| `composio` | tools of the Composio MCP server |
| `serve` | `serve` listening on a network address (not loopback): the session's chat turns, `/api/sessions/{id}/…` routes and approval details on `/api/events` ([serve egress](../../http/serve-egress.ts)) |
| `mcp:<server>` | tools of an MCP server, and `mcp.resource.*` / `mcp.prompt.*` naming it: every remote (http, SSE) server and every stdio server not marked `local: true` (issue #60); a tool whose server is unknown counts too |

Chat turns: a turn whose origin is `telegram` or `discord` (swarm bots included) for a session in a constrained folder without `channels` is refused in `runTurn` before the queue and the model (`ChannelRestrictedError`); the adapters answer with the fixed `CHANNEL_RESTRICTED_NOTICE` ("This folder is restricted; open atomic-agent on the computer.") and nothing else. Because a turn can be tainted while it runs, the Telegram and Discord adapters (swarm bots use the same classes) ask again before each send ([channel egress](../../channels/channel-egress.ts), `AgentRuntime.channelSendRefusal`): progress labels and snapshots stop, and at the end the reply, its files, budget notices and failure text are replaced by the notice, once. An approval prompt routed to a chat for such a session carries only the tool and kind (`withholdApprovalDetails`: no preview, reason, resources or "Allow always" unit), and the approval-pending reminder goes generic, without the folder's name. Outside the turn's frame `effectivePolicyForSession` intersects every view of the session: the caller's object, the stored row and the running turn's object (read taint's live registry), whose taint may not be saved yet. Task reports: `TaskRunner.notifyRefusal` asks at send time, before each report and before live snapshots, through `channelNotifyRefusal`; a withheld report is logged as `task report withheld` and the result stays local. Webhooks only enqueue tasks, so their outbound side is that report. Every check reads `effectivePolicyForSession`, which takes an id or a session object, never borrows a frame set for another session, and returns the folder's policy narrowed by the read taint (providers and egress). The registry runs the read taint (`onDispatch`) before the egress guard, so a read that taints is followed by egress checks against the narrowed policy.

Network `serve`: on a loopback host nothing changes. On any other address, a session whose effective policy lacks `serve` is refused over HTTP with `403 folder_restricted` and a fixed message: `POST /v1/chat/completions` and `POST /api/ag-ui` before the turn and, once a read taints it mid-turn, the stream writes nothing more and the turn is stopped (a non-stream request answers 403 instead of the reply); every `/api/sessions/{id}/…` route (an id that names no session reads as refused while constraints exist); its approvals on `/api/events` carry only the tool and kind; `GET /api/sessions/search` lists none of its lines, and `/api/ideas` none of the ideas built from it (a goal's criteria, a failed task's message). `serve` prints which folders it refuses at startup. Not covered: `GET /api/sessions` (titles), `/api/tasks` results, and a client on the same machine reached through a third-party tunnel or reverse proxy to a loopback server. The built-in webhook tunnel gateway (ATO-625, [serve-webhook-tunnel.ts](../../cli/serve-webhook-tunnel.ts)) counts as a network listener; it serves only signed webhook POSTs, which answer a task id.

A stdio MCP server is a local process that can still fetch pages, drive a browser or call an API (fetch, playwright, firecrawl, tavily, notion and the like), so it is classed `mcp:<server>` like a remote one (issue #60). Only an entry in `mcp.servers` with `"local": true` (stdio only, a strict boolean) is treated as staying on the machine; the flag is the operator's word and nothing checks it, and a server marked local can still read files in a constrained folder without tainting the session. The refusal of an unmarked stdio server names both fixes: add `mcp:<server>` to the folder's `allowedEgress`, or set `"local": true` on its `mcp.servers` entry. Behaviour change: a constrained folder that used stdio servers without the flag now gets that refusal; folders without a constraint see no change. The built-in MCP catalog writes the flag only for servers that work on local data (filesystem, git, time, memory, sequential thinking). Fusion workers obey the stamped policy, egress included; an older stamp without the list allows none. `image.generate` / `video.generate` are checked as provider `openrouter` above, not as egress.

## Memory scoping

Durable memory is shared by every session, so a row written while a constraint governs the call (a note from the notes tool, reflection or a memory flush, a lesson or procedure, a profile fact, a reconciler's write) carries that constraint in its own `constraint_scope` column: `{key, allowedProviders, allowedEgress}` frozen at write time (a descriptor from before `allowedEgress` reads as none, the strictest, and is rewritten to that form when the store opens) ([scope](../../memory/memory-constraint-scope.ts)). It is a column, not a tag, so the notes tool, reflection EVOLVE and the reconciler cannot add or strip it. Every read (recall, hybrid recall, the memory and lesson indexes, link expansion, lessons, procedures, profile injection, `memory.notes.recall { id }`) passes through `memory_scope_visible()`, a SQLite function that reads the call's frame:

- an untagged row is visible to every call;
- a tagged row is visible to a policy with the same key, or a stricter one: its allowed providers a subset of the row's AND its allowed egress classes a subset of the row's AND its `allowedProviderHosts` a subset of the row's (the content could only reach providers, and leave through tools, its own folder already allowed). A folder allowing `web` does not see the rows of a folder with the same providers and no egress, nor a folder whose local provider may be reached on another computer the rows of one where it may not (the descriptor carries `allowedProviderHosts` only when non-empty, so older descriptors are unchanged);
- a call with no policy (an unconstrained folder, a CLI, an unscoped job) sees untagged rows only.

Dedup never merges a write into a row of another scope. A profile write never supersedes a fact of another scope; it is refused with a validation error, and `memory.profile.remove` / `memory.notes.forget` cannot delete what the session cannot see. Writes themselves are not refused: the providers they use (reflection model, embeddings) are already checked at dispatch, so tagging is enough. A row written by an older binary, or before its folder's constraint existed, is back-filled ([scope](../../memory/memory-constraint-scope.ts) `backfillConstraintScopes`): at startup, and again before a turn or a consolidator tick whenever `projects.constraints` differs from the block the last run saw, every untagged note, lesson and procedure whose `working_dir` falls under a constraint gets that constraint's scope, as if written under it. It is idempotent and never changes a tagged row, so removing or widening a constraint does not untag its rows; they stay visible only to sessions of that key. Profile facts name no folder and cannot be back-filled; `atomic-agent doctor` reports `N memory rows retro-tagged ...; M untagged rows under a constraint now` and warns about the untagged profile facts, which every session sees.

## Background jobs

The memory consolidator's timer and the embedding backfill (startup and `memory reindex`) have neither a frame nor a session. They work per row scope instead of being refused (the consolidator runs the back-fill above first, so a note written before its folder's constraint is not distilled unconstrained): one pass for untagged rows with no constraint, and one per constrained scope, under that row's own policy (`runInMemoryRowScope`), which sees and writes exactly that scope. A distill call a scope's policy refuses leaves its clusters as they were (`clustersSkippedByPolicy`); a note whose embedding endpoint is refused keeps no vector (`notAllowed`) and the run goes on. The deprecation sweep and vote decay send nothing and run over every row.

## Read taint

A session that reads files inside a constrained folder carries that folder's constraint from then on ([read taint](../../runtime/session-read-taint.ts)). The tool registry tells the runtime before a tool runs (`onDispatch`); the read targets are those the read scope knows (fs read, list, grep, glob, read_document, archives, git reads, `vision.describe`, `file://` pages, syntax checks), the writes that return or move a file's content (`os.fs.edit`, `os.fs.patch`, `os.fs.restore`, `os.fs.archive.extract` of its archive, and the git mutations, push, pull and fetch of their `repo`, so the egress guard then sees the repository's constraint), plus every `os.shell.run` and `verify.run` command's `cwd`, its absolute paths and its relative paths that climb with `..`. When a target falls under a constraint the session's policy does not already carry:

- the turn's frame is narrowed at once (frames hold one tightenable policy cell shared by nested role frames), so the read tool itself and the next model call must satisfy it;
- the taint is stored in the session metadata (`providerReadTaint`), so the next turn, side calls by session id and `/resume` keep it; the session's policy is its folder's intersected with it;
- several folders give the intersection of their lists; a Fusion worker's read taints its orchestrator's turn.

A refused call then reads `this session read files from <folder>, which is restricted to: <ids>`. A read the read scope refuses still taints (fail closed). A plain relative shell path reached by `cd` or a script, or a computed one, is not detected, nor what `skill.run_script` reads. Memory written after the taint is scoped to the tainted policy.

Moving a chat to another folder never widens what it may reach (issue #68, `moveSessionFolder` in [session policy](../../runtime/session-provider-policy.ts)): its transcript already holds what its folder governed (pasted text, shell output, model output) without any read tainting it. When the chat's policy before the move (folder intersected with read taint) is restricted, it is stored as the chat's read taint, the old folder added to `readFrom`, so the policy after the move is the old restriction intersected with the new folder's, kept by `/resume` and memory scoping like any taint. An unrestricted chat, or a move inside the same constraint entry, changes only the folder. Writers: `POST /api/sessions/{id}/working-dir` (its answer carries `restriction` and `restrictionKept`). A Retry card (`POST /api/ideas/{id}/accept`, `atomic-agent ideas accept`) opens its new chat in the original chat's folder, or the default one when it is gone, with the original chat's restriction (folder and read taint) stored the same way (`retrySessionSeed`); a retry whose original task or chat is gone is refused while constraints exist (its restriction is unknown). The other folder writers start a fresh, empty chat (`POST /api/tasks` with `workingDir`, `/new worktree`, whose worktree the matcher reads as its repository) or point a removed worktree's chat back at the folder it started from, which is the same constraint entry; none carries content to widen.

Another chat's transcript counts as that chat's content ([cross-session policy](../../runtime/cross-session-policy.ts)): `sessions.read`, a `sessions.check` answer and a `memory.sessions.search` read of one session taint the reader with the other chat's policy (its folder and its own read taint); a `memory.sessions.search` listing leaves out every chat whose policy the call could not see a memory row of (memory scoping), and `sessions.list` shows such a chat by id only, its name withheld and never matched; `sessions.send` stores the sender's effective policy as the target chat's read taint before the task is queued, so the target's turn cannot send the sender's content where the sender's folder may not.

## Write-out

A session whose effective policy is constrained (its folder, or a read taint) may write only inside a folder whose own constraint is the same entry or equal-or-stricter: its allowed providers, its allowed egress classes and its `allowedProviderHosts` all subsets of the session's ([guard](../../tools/tool-write-out.ts), composed after the egress guard in [runtime wiring](../../runtime/composition/runtime-egress-guard.ts)). Otherwise a copy written to an open folder would escape the read taint: the next session reading it would not be tainted. The writes checked are `os.fs.write`, `os.fs.edit`, `os.fs.restore`, `os.fs.move` destinations, `os.fs.archive.extract`'s `destDir`, an applied `os.fs.patch`'s `rootDir`, an applied `os.code.rewrite`'s `path`, the office writers (`os.fs.docx`, `os.fs.xlsx` except `read`, `os.fs.write_pptx`) and the files `video.render_html` and `canvas.render` save in the working folder; the refusal (code `ATOMIC_AGENT_WRITE_OUT_NOT_ALLOWED`) reads `folder <key> is restricted: <tool> would write its content to <path>, ...` (or `this session read files from <folders>, which is restricted: ...`). So an unconstrained session that read a constrained file can no longer write in its own folder for the rest of the session. The one exception is a fusion worker's own temp copy (its working directory under `atag-fusion-*`, while that worker's turn runs): it is stamped with the parent's policy and its changes come back to the parent's folder. The runtime's own writes (traces, spill files, the session store) are not tool calls. Shell commands and `verify.run` can still write anywhere (a redirect, `cp`); that is not detected.

## Status

`describeProviderRestriction(policy)` gives `{label, allowedProviders, folder, readFrom}` (`restricted to: local-llama`). The TUI draws the label as a chip after the composer's route and adds a `Providers:` line to `/status`; the sidecar answers `get_provider_restriction {sessionId}` and `serve` answers `GET /api/sessions/{id}/provider-restriction`, `null` when nothing applies.

## MCP sampling

Sampling requests go to the local llama-server client directly. A llama-server on this machine sends nothing anywhere and always serves. One at a remote `localModels.url` is refused while any constraint exists: an MCP client is shared by every session, so a sampling request belongs to no session, and the policy frame it runs in is only the one where the transport was opened (whichever turn connected the server), which is never read. For the same reason `allowedProviderHosts` does not apply to it: with no folder to read the list from, taking any folder's list would loosen every other folder, so a sampling server on another computer stays refused while any constraint exists.

## Not covered

Egress IS refused by default: `allowedProviders` covers model, embedding and media endpoints, and `allowedEgress` the tool classes above, both against the effective policy (folder plus read taint). A tainted unconstrained session is refused egress too, unless every folder it read from allows the class (the taint carries the intersection of the `allowedEgress` lists). Shell commands are checked best effort: an `os.shell.run` command or any command of a `verify.run` call that runs a known network client, after wrappers (`sudo`, `env X=1`, `xargs`) and inside `sh -c` / `bash -lc` / `powershell -Command` bodies ([detector](../../tools/os/shell-command-guard/network-clients.ts)), is refused at dispatch with the egress code unless its class is listed: `curl`, `wget`, `httpie`, `Invoke-WebRequest` / `iwr`, `Invoke-RestMethod` / `irm`, `npm`/`pnpm`/`yarn publish` as `http`; `git push`, `fetch`, `pull`, `clone`, `ls-remote`, `remote update` as `git`; `gh` as `github`; `ssh`, `scp`, `sftp`, `rsync` to a `host:` operand, `nc`, `telnet`, `ftp`, `socat` under no class (always refused). The refusal says the check is best effort and the shell is not a sandbox. Still not covered, and shown as such by `atomic-agent doctor`: a script, an interpreter one-liner (`python -c`), a renamed binary or a computed command a shell runs; skill scripts (`skill.run_script`); files a shell command writes outside the folder (a redirect, `cp`: see [write-out](#write-out)); the network use of a stdio MCP server marked `local: true` (a local process whose own requests nothing here sees), and the file reads of any stdio server (they do not taint the session); and a chat message folded into a turn that is already running (only a new chat turn is refused).
