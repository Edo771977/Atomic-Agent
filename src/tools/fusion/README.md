# Fusion workers

Status: current
Owner: src/tools/fusion/

Fusion delegates bounded task waves to worker turns. Contracts carry deliverables, declared inputs and dependencies. A sibling dependency releases its consumer only after the provider is `ok`, its required matched provides are present and inspectable, and its own deterministic checks and available syntax checker pass. Pathless `other` provides may act as advisory completion tokens: they order successful tasks and retain their cannot-be-checked warning, without proving an artifact exists. Missing or uncheckable matched artifact provides fail the provider; unavailable required checks leave it `needs_orchestrator`. Provider verification is deduplicated only within one release wave; before a later wave reuses the provider, presence, own checks and syntax are revalidated even when intervening workers emitted no file-tool changes. Fresh premerge gates may be reused for the first release. A `no_changes` provider (it wrote nothing) releases its consumers only when every required matched provide is a verifiable artifact that passes that same presence, own-check and syntax verification; its row stays `no_changes` and the consumer's contract still warns about it. Presence alone is not enough: at least one own check or syntax check must actually run in that release and pass (a syntax pass that checked nothing, or no runner, is no evidence). Pathless `other` tokens are no evidence for such a provider. Candidate integration never releases a `no_changes` provider's consumers: promotion requires every row `ok`, so their work could never be delivered. Failed, cancelled, timed-out, queued, step-limited, `needs_orchestrator` and unverified `no_changes` providers hold consumers transitively. This readiness rule applies with `autoReplan` off too: off means no automatic retry; consumers that used to run with a warning are now `not started: dependency blocked`. Cyclic dependencies remain held while independent work can run. Unmatched `requires` remain advisory warnings, as documented by the contract; they establish no sibling dependency and are never described as verified. Presence does not establish semantic compatibility, and call-level integration checks and the final judge still run after the waves. Preserve task status attribution and hand-back based on completed-step progress rather than an independent timer.

## Measured routing (opt-in)

Resumed carried tasks are reported and checked again, but never adapted or appended as new execution samples. Only tasks run in the current call train outcome history; rechecking an old artifact does not establish another provider execution.

The history reader validates task-record structure and keeps a 10,000-record ring while parsing. Dense malformed rows cannot overflow a spread call or build an unbounded record array. Unexpected history failures preserve the current default route.

Routing selects configured provider legs, retaining existing display/pricing labels; it adds no per-request model override. Eligible samples also need a matching opaque SHA256 request-configuration identity, captured at worker dispatch and unchanged at completion. The runtime derives it from provider kind, safe endpoint identity and explicit request model, or a managed main local model whose configured/live IDs match. Credentials, query strings, raw URLs and command arguments are never written to the log. Legacy/unidentified records, automatic model selectors, unknown adapters, subscription CLI argument routing and dynamic external local servers remain insufficient. No provider call discovers identity. This partitions known configuration changes; it does not attest which weights a remote gateway actually served, nor prove model-quality benchmarks.

Cloud identity must match both live configuration and the registry's defensive snapshot of the entry that successfully built the loaded provider. Pending model or endpoint edits and failed replacements remain unidentified until reload succeeds. Managed local identity additionally reads the loaded provider's actual text-client endpoint (including its pinned override) and tracked model ID; a vision-only entry URL cannot establish text identity. It must match the configured main managed endpoint/model. External local servers remain insufficient. A dynamic text client may follow the current main endpoint; a pinned old client cannot inherit a new endpoint's history identity.

`llm.runMode.fusion.measuredRouting: { "enabled": true, "minSamples": 8, "days": 30 }` enables deterministic selection for unpinned tasks using recent outcome history. It is off when absent or disabled. `minSamples` accepts 3–1000 and `days` 1–365. Explicit task models and configured role pins always win. Eligible alternatives are the configured build-role target and the existing orchestrator worker target; CLI targets whose own tools stay on and extra local models prohibited by `mixLocalModels` are excluded. Automatic orchestrator tasks consume the existing per-turn strong-task cap. Request budgets, provider pins, approval scopes and failure breakers still apply; retry families are never automatically rerouted.

[measured-routing.ts](measured-routing.ts) reads the live outcome file plus its two rotations through the existing reader, capped at 5 MiB per file and 10,000 newest retained records. Missing/malformed history falls back to the current route. Selection requires enough first-attempt, non-escalated objective task-check outcomes on both sides, matched exactly by requested task role, provider and model. Privacy-sanitized path aliases are insufficient for exact attribution. Legacy rows, self-reported success, judge-only green, held merges, retries and unverified checks do not establish acceptance. New `acceptance`/`acceptanceScope` fields describe only declared task checks; they do not establish full integration correctness. They are also not independent of the worker: the checks run in the workspace the worker edited, so a worker that weakens or deletes a test, or edits a file the check command reads, earns `checks-passed` there. The outcome row records only check counts, and check specs are free-form commands whose file inputs are not declared, so the log cannot tell such a sample apart; a `checks-passed` row is evidence about the declared checks as the worker left them, not about the original tests. Candidate executions carry separate final-disposition telemetry and never train task-check quality history, including after promotion; global integration acceptance cannot credit individual models.

Acceptance rate takes precedence: a gain of at least 10 percentage points can change the route. At equal rates, a target needs at least 20% lower median cost (only when all compared samples have known prices), otherwise at least 20% lower median duration. Missing prices remain unknown, never zero. Candidate order is deterministic, with the current worker winning ties. Latest infrastructure, permission, timeout or cancellation failures keep the default route or exclude an alternative; quality data cannot bypass a blocker. A transient block (timeout, cancellation, an unreachable or overloaded server, any class other than those below) lasts 24 hours from that row (`ROUTING_BLOCK_COOLDOWN_MS`): an excluded alternative is never run again and so never writes a newer row, and without expiry one timeout would exclude it for the whole history window. After the cooldown the leg's verified history counts again; a new blocking row restarts it. A credential or configuration failure (`not-signed-in`, `out-of-credit`, `cli-missing`, `tool-protocol`) does not heal on its own and blocks for the whole history window, until a newer row on the leg replaces it. `details.routing` records the selected provider/model, reason, sample counts, descriptive rates, known costs and exclusions. These observations are neither a benchmark nor a prediction for the current task. They never enter the cached prompt prefix; hermetic fixtures test policy without provider spend.

Routing selects configured provider legs using the existing display/pricing model labels; it does not add per-request model overrides. These labels identify configuration, not independently observed serving-model provenance or model-quality benchmarks. Provider pins retain the existing fallback restrictions.

## Project estimates

[project-estimate.ts](project-estimate.ts) (issue #39) estimates the rows of a project plan (`session/session-project.ts`). Pure: callers pass outcome records, prices, tiers and live limits. `estimateRow` uses medians once `minSamples` exact member + role rows lie inside `days` (`measured`; cost only when every row was priced); otherwise `preset` with reason "insufficient data, chosen from the preset", cost price × `PRESET_TASK_TOKENS` for the role (`priceOnly`) or unknown, and time from the local speed or unknown. A local member (`EstimateRowOptions.local`, from `ProjectPlanContext.isLocal`) with no configured pricing costs $0 on either basis (a localhost proxy with prices keeps its cost): `estCostUsd: 0` and `local: true`, which the row keeps (`withRowEstimate`) and the surfaces show as "$0.00 (local)"; it is never counted unpriced (issue #54). A row's cost includes its review (issue #74, `withReviewEstimate`: `estimateRow` for the reviewer in role `review`, added by `project.plan`, a person's row edit and the variants, whose cheaper comparison counts it too; an unpriced review keeps the worker's figure and says so in the reason; a row stays `local` only at $0 in all); the vision judgement of a page check is not estimated, since the checks are not known at plan time. `estimatePlan` sums known costs, gives wave time (milestones in order, tasks in parallel, local tasks packed over `localSlots`), and flags hard violations (a milestone over `turnBudgetUsd`, the next milestone over today's remaining limit, a member the folder's policy refuses) and warnings (local slots; the whole plan over today's remaining limit, since it resets daily); approval is refused while a hard one stands. `cheaperVariant` picks the lowest known cost among members not weaker than the planned worker (unknown cloud tiers are never compared); `qualityVariant` the highest tier, ties by `acceptanceRate`. Both keep a reviewer the person picked at the gate (`reviewerByPerson`, their "no review" included) unless it became the worker, and never drop an existing review to none: the routed reviewer, else the old one, else the team's next reviewer. `planDetailFor` picks compact or full detail from `llm.runMode.fusion.project` (`fullPlanAboveTasks`, default 4; `fullPlanAboveUsd`, default 1; an unknown cost is not above it); `/plan` forces full. These are descriptive figures, not predictions.

## Worker lifecycle

`maxWorkers` bounds the entire `fusion.delegate` call across the main worker, role-model and orchestrator pools. Each call owns a FIFO permit queue; independent calls keep independent ceilings. Active legs retain their physical slot, per-provider-pool `cloudWorkers` and strong-model limits. The result's `maxWorkers` is the smaller of the requested width and the sum of those active capacities; `cloudWorkers` is not a new aggregate cap across cloud providers. A call that names no `maxWorkers` is bounded by that sum alone: the unnamed default (one worker on an unpinned local main leg, else `workers`) sizes only the main leg, never cloud role or orchestrator legs. With no `maxWorkers` and no pinned `runMode.fusion.workers`, all slot-affine (local) legs, the main leg and any local role leg (`mixLocalModels`), share one local worker at a time, since they draw on the same GPU; cloud legs still add their own widths beside it. A local main pool with no assigned tasks does not constrain cloud-only role work. The result's slot or cloud-cap note is judged on the main leg's own tasks and width, with or without role legs beside it. A queued task is admitted again against cancellation, turn budgets and failure breakers before its session and task clocks start. Its scheduler wait appears separately as the row's `schedulerQueueWaitMs`, and the call's result adds one line counting the tasks that waited and the longest wait; provider first-token `queueWaitMs` keeps its existing meaning. Permits are released on completion and failure before split expansion or retries acquire their own. A task whose time limit or first-token clock fired but whose turn has not settled gives its permit back after `TASK_PERMIT_RELEASE_GRACE_MS` (5 s), so a turn that ignores its abort cannot starve the call; its row is still reported when the turn ends. An escalation re-run (`escalationReplace`) after such a release first waits for a permit again like any queued task (if the turn is stopped meanwhile, the re-run is not started and the row says so), and the re-run's own time limit or cap arms the same grace.

Verification through `verify.run` requires a throwaway workspace copy. If the copy exceeds its 2 GiB limit or cannot be created, command, service and page runs all fail before starting an executor; there is no in-place fallback. The result carries `errorCode: "workspace-unavailable"`, `isolated: false` and failed, unevaluated checks with the setup reason. Cancellation before execution also starts nothing and cleans up a completed copy. Existing dependency-directory links and user symlinks retain their targets: this copy is not a process sandbox.

On Windows, fan-out write scopes compare supported `\\?\C:\...` and `\\?\UNC\server\share\...` spellings with ordinary Win32 drive/UNC paths ([scope-path.ts](scope-path.ts)), so isolation rebases either spelling into the private workspace. Device paths (`\\.\...`), unknown or unsupported namespace spellings, and forms whose normalization can change identity are refused: these include dot segments in extended paths, trailing dots/spaces and reserved device components. If an original root cannot be compared safely, only the private workspace scope remains; an uncomparable private workspace grants nothing. These lexical approval-scope rules do not establish an OS sandbox or resolve symlink targets.

`fusion report` retains the JSON `green` / `firstPassGreen` fields as reported task-status counters: `status: "ok"` alone can increment them, even with judge off and no acceptance evidence. Human tables label these as reported green and reported first-pass. Separate `checksPassed`, `checksFailed` and `checksUnverified` counts require consistent `acceptanceScope: "task-checks"`, terminal status, failure and merge flags, with no judge retry or escalation. `checksNone` (the human column's `no-checks`) counts records whose `taskChecks` is 0: no contract check was attributed to the task, so there was no evidence to miss; a declared check that never ran, a judge that could not decide, a held or conflicted merge, a candidate row or an escalation stay unverified, and so does an older record without `taskChecks`. `selfChecked` (column `self-checked`) is telemetry, never acceptance: the record's `selfCheckPassed` says the worker's own last `verify.run` had the identical spec (`checkSpecKey`) of one of its task's declared checks and passed after its last change in its workspace (`WorkerCheckRuns.lastRunPassedOneOf`; not set on a row a cloud re-run replaced, and the orchestrator's own `verify.run` never counts). Measured routing keeps reading only `taskCheckEvidence`. A later replan attempt can still have check evidence; the measured-routing selector keeps its stricter first-attempt eligibility. Legacy, incomplete and contradictory records remain unverified. These counts describe the declared checks in the worker's workspace: the worker can modify the checks and their inputs, so passing them does not establish semantic correctness or full integration acceptance.

Per-task review (issue #38) is recorded as the task record's optional `review: {decision, passes, reviewer, blockers, majors, minors}` (`ReviewOutcome`, built by `reviewOutcome(verdict, passes)` and passed in `TaskOutcomeContext.review` by `fusion.delegate` for every task a review ran on: with a team its review passes, without one the judge's verdict with its one retry as a pass; absent while review is off; the record stays `v: 1`; no issue text, item or file). A record with `passes > 0` also has `judgeRetried: true` and no `acceptance`, so `taskCheckEvidence` and measured routing treat a review pass as they treat a judge retry. `fusion report` reads the field through `readReviewOutcome` (an older or malformed field is no review): per model, `review` in JSON (`reviewed`, `accept`, `needsChanges`, `unverified`, `notReviewed`, `medianPasses`), the human columns `reviewed accept/needs-changes/unverified` and `review passes` (median, reviewed tasks only), `-` when no task of the model has a review; and `reviewers`, the `Reviewer models` table per reviewer label (`(automated checks only)` for a review no model gave) with decisions, median passes and issue counts by severity. A review decision is a model's opinion after the automated checks, not check evidence. The watch (issue #43) is recorded as the optional `watch: {checks, judgeCalls, hints, stopped, judge}` (`watchOutcome`, counts and the judge's `outcomeLabel`, never a hint's text; `readWatchOutcome` reads an older or malformed field as none), and a task it stopped has the failure category `stuck`; `fusion report` shows `watch hints/stops` per model (`-` when no task of the model was watched).

Workers are ephemeral: no durable session row/reflection/trace; no recursive delegation or invisible interactive approval. Provider pins must not fall over to a different billing/model leg. Declared input replacement remains forbidden. A worker's approval-gated call is refused by its session policy. A fan-out's directory covers its writes and ordinary commands there, never a dangerous command (`shell_dangerous`), the agent's own config or secret files (`trust_config`, `state_secret`), mail, passwords or payments: those are refused with `FUSION_WORKER_OPERATOR_ONLY_REFUSED`, and the task comes back `needs_orchestrator` with a note telling the orchestrator to hand the step to the user instead of re-sending it (ATO-1222, ATO-1223). A fan-out whose write scope lies inside the agent's own state directory (`~/.atomic-agent`) is refused before the operator is asked, and the worker brief says an operator-only refusal is reported, not sent back for a re-send (ATO-1267). Concurrency is resolved from the call, task count and serving slot capability, rather than blindly capturing startup state.

A local worker leg has no reasoning-effort parameter, so [worker-runner.ts](worker-runner.ts) turns `workerReasoning` (or its unset default) into the turn's `reasoningBudgetTokens` (`localWorkerReasoningBudgetTokens` in `src/llm/reasoning-budget.ts`); the step applies it to the per-request grammar only, and the forced final step stays unbounded. The levels and default are in the root README's Run modes section. A cloud worker leg gets no bound and needs none for a fallback: every worker turn is pinned to its leg's provider and a pinned request never falls over ([llm-fallback-seam.ts](../../runtime/llm-fallback-seam.ts)), so a cloud worker's step cannot land on a local grammar link. If pins ever fall over, compute the bound where the link is resolved (`prepareForLink`). The step reports on `llm_completed` (`reasoningBoundTokens`) the bound the serving request really carried, which is absent with a plain-instruct profile or a native-tools link; the time-limit hint names the bound only then.

A worker brief ([worker-prompt.ts](worker-prompt.ts)) puts the task, its files, deliverable and contract part, and the rules first, then the quoted original request (at most 6,000 chars on a local leg, 16,000 on a cloud one; a local leg's `### fusion` block and the `fusion.delegate` summary tell the orchestrator to put in `instructions` what a task needs past the 6,000) and a one-line task reminder; a clip of the worker's pinned request cuts inside the quote, never the task. The quote cap does not narrow input-file protection: each worker session carries the whole request (`FusionWorkerMeta.operatorRequest`), and the input guard reads that, not the brief's clipped quote (`workerRequestRecord`). On a local leg the `### fusion` block sizes tasks at one file or function and ~N new lines, N being the worker's completion cap over 25 tokens a line (`workerMaxNewLines`), and a local task writing more than three files (tests, fixtures, snapshots and contract inputs not counted) gets a warning, never a refusal: on the fan-out's approval line, before any worker starts, and on the result (`localTaskSizeWarnings`, `details.sizeWarnings`), the first thing the orchestrator reads after the call.

After a local worker is cut off (time limit, queue wait, hand-back or operator cancel), the next local dispatch first asks the server `GET /health` ([local-leg-health.ts](local-leg-health.ts), ATO-917); a server that does not answer fails the task at once with a restart hint instead of letting it wait out its budget. A server that does answer gets the worker on fresh connections: the process's HTTP pool is swapped for a new one first (`renewTransportPool`, ATO-1357), the part of an agent restart that cleared the field case, while requests already in flight keep their sockets. A worker that still gets no token while `/slots` shows every slot idle is told the request got stuck on the agent's side, not to restart the server. One whose first-token wait runs out while `/slots` keeps showing a slot processing with no token decoded (`SLOTS_CONTENDED_MIN_POLLS` answers in a row, `LlamaServerError.contended`) is reported as slow or contended, its GPU possibly shared, with a close-the-other-program-or-run-fewer-workers hint, not as a server that stopped answering; the chat's wait notice says the same. No probe completion is sent for this: a cancelled one is what wedges the server (issue #490).
Worker spend is priced per completion with the prompt-cache discount (`estimateUsageCostUsd`, ATO-918). With `llm.runMode.fusion.turnBudgetUsd` / `turnTimeBudgetMs` set, [turn-budget.ts](turn-budget.ts) caps a fusion turn (ATO-947): reset at the turn's start, checked before a delegation, before each worker starts and on every worker completion; reaching it stops running workers and returns a plain-words instruction to the orchestrator. Unset, none of it runs.

Before the first fan-out on a local worker leg (after the cheap refusals, before the approval prompt), [local-grammar-smoke.ts](local-grammar-smoke.ts) runs one format check: a completion of at most 96 tokens with a 10 s budget, asking for a `reply` call under a worker step's per-request grammar (its thinking decision, reasoning prelude and tool set, the think bound tightened to 16 tokens so it fits) ([grammar-smoke.ts](../../llm/grammar/grammar-smoke.ts)). The completion is grammar-constrained, so this checks that the server takes the workers' grammar and that framing, grammar and parser agree, not the model's skill. Only a definite answer refuses the fan-out — the local server rejected the workers' grammar, or a reply that finished on its own did not parse — with the breaker's tool-protocol words and instruction, noting that blocker on the turn. A timeout, cancel, unreachable server or reply cut at the cap or a stop word has no verdict and dispatches as before. The check is skipped, not queued, while a fan-out this process started is live on that server or its `/slots` shows every slot working. A pass is kept per (server, model, profile, managed daemon launch) for the process, a failure for 10 minutes and a check with no verdict (except a cancel) for 2 minutes; nothing is kept when the model id is unknown. A leg where a worker already finished with a tool call this session is not asked, and that success drops a failure kept for the leg. It runs on the reserved side-call slot (reflection, compaction) when one is reserved, else on slot -1, where the server picks an idle slot and the check clears it; with one slot and the orchestrator on the same server the check is not made. Only the main local server's llama-server legs are probed (the runtime's `fusion-format-check.ts`), never a cloud leg; `llm.runMode.fusion.localFormatCheck: false` turns it off.

[failure-breaker.ts](failure-breaker.ts) stops a fan-out that keeps failing the same way (ATO-1406): one blocker (tool-call protocol mismatch, CLI missing or signed out, out of credit) or `REPEAT_FAILURE_STREAK` identical failures in a row on a leg, and no new task starts there; running workers finish. Trips are kept on the turn's `FusionTurnBudget`, and a later delegation is refused on a leg that hit a blocker, or after the same repeat stopped two rounds. The same state counts rounds and tasks against `maxRoundsPerTurn` / `maxTasksPerTurn` (defaults 6 / 48, `0` off), checked before the fan-out's approval; the approval line names the round and the task count. Admission, the approval line and the count noted when workers start use one set, the tasks the call will run (issue #87): a resume's carried rows and rows awaiting the person's confirmation are not counted, for the orchestrator cap too, nor do they trip the `orchestrator-target-off` refusal or use measured routing's remaining orchestrator room. `model: "orchestrator"` tasks have their own count, `maxOrchestratorTasksPerTurn` (default 4, `DEFAULT_FUSION_MAX_ORCHESTRATOR_TASKS_PER_TURN`; `0` turns the target off and such a task is refused as `orchestrator-target-off`): a call that would pass it is refused whole (`kind: "orchestrator-tasks"`, the message names the cap), per call too when there is no per-turn state, and once it is used no replan fix names that target. Both need the runtime's per-turn `turnBudget`.

[escalation.ts](escalation.ts) escalates a stuck worker (ATO-942): with `escalation: "advisor"`, the first stall or cut first answer asks `ResolvedRunMode.escalation` (a configured provider other than the worker leg) for a hint at most `ADVISOR_MAX_OUTPUT_TOKENS` long, refused when its worst case is over `escalationMaxUsd`, and steers the worker with it. A later stall re-runs the task on that model only with `escalationReplace`. A task a team reviewer still sends back after the last pass (`needs-changes`; an `unverified` review stays `needs_orchestrator`), and was not stopped, ends `failed` with `failure: "review-exhausted"` (its error starts `review-exhausted: <decision> after <n> review passes`; the outcome log's failure category is `review-exhausted`). Every turn on a member's leg asks its provider for the member's model (`TaskLeg.pinModel`, the runner's `model`, a per-turn model the runtime builds as a model variant that keeps the provider id, so folder constraints still match); a local member gets no pin, since its server serves one model. Pricing and the budget read the member's model, and a pinned model other than the worker leg's carries no routing identity, so its outcome rows are never measured-routing evidence. The `### fusion` block adds a `Team workers:` line. With a team, tasks are reviewed when `reviewEnabled(team, judge)` says so (issue #38: `team.review` wins; listed `reviewers` turn review on even with `judge` off; else `judge` decides). A task's judge is `pickReviewer` for the member that ran it (the worker leg counts as `workerProvider:workerModel`), given the members' strength (`teamStrengthOf`): never a reviewer weaker than the worker, stronger before equal before unknown tier, and within each another family first while `crossFamilyReview` is on (default), then config order; it is asked on its own model (`JudgeTarget.pinModel`, the `EscalationComplete` call's `model`, which the runtime serves from the provider's model variant after the same `assertProviderAllowed`). No reviewer fits: `judgeProvider` while `judge` is on; otherwise that task gets no checklist and no model review. `team.review: "off"` judges nothing. The chat's reviewer (issue #71, `currentReviewer`) judges every task it can serve (allowed, reachable, not the worker) before `pickReviewer`, whatever its strength, and turns review on for the chat; `"none"` judges nothing in the chat, even with `team.review: "on"`: a chat's own choice wins over the config. `project.plan` rows default to the same reviewer (`"none"`: no reviewer); a person's row edit still wins. At run time (issue #74) the approved plan row's reviewer reviews, and watches, its planned task whoever named it (the person at the gate, `reviewerByPerson`, or the director's draft the person approved), before the chat's reviewer, the team's pick and `team.review`; a row's null judges nothing, not even on `judgeProvider`, when a reviewer could have been named (the person chose it, or the team lists reviewers). A task outside the plan keeps the default above. A row's reviewer that can no longer review here (not a team reviewer the folder allows and that can answer, or now the worker) falls back to the default; the plan then no longer stands for the fan-out prompt, and the prompt's reason and the task's row note say which reviewer runs instead and why (`plan reviewer <ref> is no longer usable here (<why>); …`). A re-plan keeps `reviewerByPerson` on a row whose worker and reviewer are unchanged.

A Codex subscription as reviewer (issue #71): a `subscription-cli` entry with cli `codex` can be a team reviewer like any provider (family `openai`, so it is the cross-family pick for an Anthropic or local worker). Each review is one `codex exec` completion, run with `-s read-only`: Codex cannot change the workspace, but `-s read-only` confines its own shell rather than turning it off, so that shell can read outside the worker's read scope (anywhere the account can read), as for a Codex CLI worker or orchestrator leg (`cliToolsStayOn`). So in a chat whose effective provider policy is restricted (a folder constraint, a read taint or a moved stamp) such a reviewer is never used: `resolveTeamRouting` and the plan context leave it out (`restricted`), a named one is refused at the turn, and `GET /api/fusion/team` lists it with `reason: "cli-tools"`. In an unrestricted chat it reviews, with that caveat. With no model on the entry (Codex uses the ChatGPT account's default), list it as `"<providerId>:default"`: the model `default` is the entry's own (`TEAM_MEMBER_PROVIDER_MODEL`, accepted for a `subscription-cli` entry only: an API provider is priced and tiered by the model it names, so validation refuses `<api>:default`), so the call runs on the entry without `-m`; a named model runs on a copy with `-m <model>`. A signed-out or missing `codex` is not reachable and is passed over; a subscription has no per-token price, so its reviews are unpriced. Codex has no tier in the model tier table, so the team's own pick ranks it as unknown strength, after reviewers known to be stronger or equal; a chat that chooses it (`reviewer`) uses it whatever its strength. Without a team, `judge` alone decides, as before. With a session director, an escalation or judge that lands on the director is asked on the director's model (`FusionEscalationTarget.pinModel` and the judge's `pinModel`: the advice call's `model` and the re-run's `model`), the model it is priced at. Without a team, or a team with no `workers`, routing is as above, except that with a team the orchestrator target is still the director member, so a director and the worker leg on one provider stay two legs.

[worker-watch.ts](worker-watch.ts) is the periodic watch on a team run's running workers (issue #43). Each task is checked every `watchMinutes` (the task's, rounded and clamped to 1..60 by `delegate-args.ts`), else `team.watchEveryMinutes` (default 5); 0 is off, and without a team nothing is watched. The first check waits a per-task jitter (`watchFirstTickJitterMs`: at most a quarter interval, never over 30 s) so a wave's watches do not judge in the same instant. The deterministic check (`decideWatch`) reads what `WatchProbeTracker` counts from the worker's event stream (finished steps, completion tokens plus streamed text, the streamed tail, tool calls parsed and not yet executed, a request awaiting its first token) with the files the collector recorded as changed and `detectStall`, and never stops work by itself: clear progress (a file changed, steps that do not look stalled, or more than `WATCH_STREAMING_FLOOR_TOKENS` = 50 output tokens streamed in the interval) costs nothing; stalled steps ask the judge at once; otherwise an interval is waiting, and not counted, while a tool call runs (a build, `verify.run`, `shell.exec`) bounded by the task's own wall clock, or a request has not produced its first token (slow prompt processing on a later step) for at most `WATCH_FIRST_TOKEN_WAIT_INTERVALS` = 2 checks in a row; from the third such check, with no tool running, the silence counts as nothing at all (judge-able, counted toward the quiet intervals, and the judge prompt says `no first token for at least N min (request in flight), no tool running`), so a server that answers its health check but never the request (#29) is not left to `localModels.firstTokenTimeoutMs`; a trickle at or below the floor, or nothing at all, for two intervals asks the judge, whose prompt then carries the last 600 chars of the streamed text. A worker the server has not answered yet is the queue watchdog's, and the time its self-check runs the task's checks is not counted. The judge is the task's reviewer (`reviewerFor`, the review's folder policy and model pin; none with `team.review: "off"`, as for the review), else the director on its own model. Before each call the turn budget is checked; under a $ cap a judge without verified pricing is skipped with a `watch: judge not asked: …` note (a plan-billed, subscription judge has no verified price, so it is skipped for the same reason escalation refuses it), and a priced call first reserves its worst case (the prompt plus `WATCH_JUDGE_MAX_OUTPUT_TOKENS` at the judge's price) against the cap until its spend lands. At most `team.watchMaxChecks` calls (default 3) are made per task across all its runs (the first, every review pass and the escalation re-run); the spend counts as judge spend. A call has its own 60 s timeout; one that does not answer, an unreadable answer or a failed call is progressing, and a check that throws is noted and the watch goes on. The worker's tool results and streamed tail reach the judge framed as outside data (`frameUntrustedText`). Its answer is strict JSON `{"state":"progressing"|"looping"|"stuck"|"off-track","hint":string|null}` (`parseWatchAnswer`, hint at most 300 chars). `looping` / `off-track` steer the hint, framed as advisory, into the worker's own session through `steerWorker`, the advisor's path (step-mutable; no prefix, grammar or profile change); no hint is sent in an interval the advisor already steered. `stuck` is honoured only when the counts agree (nothing moved this interval and two quiet intervals in a row), else it is read as looping, so text the worker read cannot stop it. A stuck verdict aborts the worker's turn (`stopByWatch`), no escalation re-run follows, and the row ends `failed` with `failure: "stuck"`, its changes kept as a failed task's under the isolation rules; the escalation's re-run is watched the same way. `describeReplan` lists it in its own `stuck` bucket (`STOPPED BY THE WATCH`) with the review-exhausted guidance (re-delegate, fix it, accept the partial work with reasons, ask the person only if it cannot proceed), also with `autoReplan` off and with no replans left (`redelegate: false`); a dependent held only on it is pending with `awaitsReview` and does not hold the step. The timer is unref'd, never overlaps a judge call, and is cleared with the turn. The row carries `watch: {checks, judgeCalls, hints, stopped, judge}` (both runs' counts when the task was re-run); its status-table line gets a `watch:` clause when hints were sent or the task was stopped, and `details.watch[id]` holds every watched task's counts.

[worker-repeated-writes.ts](worker-repeated-writes.ts) stops a worker that keeps writing the same bytes to one file (issue #95), with or without a watch: after `REPEATED_WRITE_LIMIT` (3) consecutive rewrites of a path that each produce a version the same run of writes already produced (the SHA-256 of the `os.fs.write` content is one of the path's last `REPEATED_WRITE_RECENT_HASHES` (4), so alternating between two versions counts too; the path is resolved under the working dir, so `a`, `./a` and `/repo/a` are one; each `ok`) with no progress in between (any other successful call that is not read-only, such as a write to another file, an edit or a shell command, ends the run; failed calls, read-only ones and `verify.run` do not), counted afresh when the self-check's grace turn begins (not seen as repeats, by design: writes through the shell, and content that differs only by a timestamp), the runner aborts the worker on the watch's stop path, so the row is `failed` with `failure: "stuck"`, its files kept as a failed task's, and `stalled: { reason: "repeated identical writes", path, sha256, writes, lastCheck? }` (the worker's last `verify.run`: its spec, whether it passed, `sinceLastChange`, whether it ran after the worker's last change, an identical rewrite not counting as one, and `coversFile`, whether its spec names the file; the row says "not run since the last change" for a stale one, and only a fresh pass of a check naming the file says the file may be usable). The row's error starts `stalled: repeated identical writes` and names the path, the hash's first 12 characters and the last check; `describeReplan` lists it with the stuck tasks and tells the director to verify the file before re-delegating, instead of the task running on to its time limit.
[branch-workspace.ts](branch-workspace.ts) and [branch-merge.ts](branch-merge.ts) are branch isolation (ATO-946, `isolation: "worktree"`, default `"off"`): each run of tasks (a wave, a judge's retry) gets a workspace per task plus an untouched base, all from one snapshot of the working directory. In a Git repository every workspace has an independent Git directory and index with detached snapshot HEAD, then every tracked path is compared with the original working tree's actual bytes and symlink targets: only a path whose checkout differs (a clean/smudge filter, an eol attribute, a cached-clean index entry) or that was removed is overlaid and charged to the copy limit, while an identical checkout only takes the original's mode and times; each task takes that same frozen base the same way. Git's cached-clean index and clean/smudge filters are not byte authorities. Change detection skips excluded directory names (`build`, `dist`, `target`, …) and ignored directories, except a tracked path or an ancestor of one (`scripts/build/pack.sh`), whose changes are merged and patched like any other. Untracked files and ignored standalone files are copied privately. In direct integration every other ignored directory Git lists (a virtualenv, `.next/`, `dist/`, a cache) is linked to the original exactly like a dependency directory (below), charged nothing: direct mode is not a sandbox, and copying them into the base and every task refused isolation for ordinary repositories; candidate integration copies them privately instead. Elsewhere the workspace is a private folder copy without the original `.git` metadata. Dependency directories named `node_modules`, `target` or `.venv` (`SHARED_DEPENDENCY_DIRECTORIES`) normally get a generated symlink to the original in the base and every task, charged nothing, so a large dependency tree does not refuse isolation. If the host denies a generated directory symlink (Windows without the symlink privilege), a directory junction to the same target is tried; it resolves the same way, so writes through it still reach the original. Only if no link is possible does that entry become a private copy charged to the same cumulative byte limit: the base copies it once and each task links (or junctions) to the base's copy, falling back to a copy of its own only when that link fails too. A refusal caused by such copies says so (`dependency folders could not be linked on this system and copying them exceeds the copy limit (N bytes)`) instead of calling the folder too large, but only when the rest of what was copied (the file that did not fit included) would have fitted without those copies; a large source tree keeps `the folder is too large to copy`. This fallback applies only to runtime-generated links, including links copied from the base; user links retain their targets (except inside a candidate's private dependency copy, below) and are never expanded into copies. When a tracked placeholder (`node_modules/.gitkeep`) keeps the directory itself unignored, Git lists its ignored children instead; each ignored directory under a dependency directory name is linked the same way, while tracked files there are copied. They are never stamped or merged, but in direct integration a write through such a link (a worker's shell or a fan-out-scoped fs write) lands in the original, as with `verify.run`; the same holds for the other linked ignored directories. Candidate integration copies them instead (below). The copy limit (`tools.verify.maxCopyBytes`, default 2 GiB) is cumulative across the base, task copies and frozen ignore-rule files, including tracked byte overlays (only paths whose checkout differs); Git's separate checkout materializations are not charged. If a workspace cannot be created or that copy limit is exceeded, the whole wave is refused before any worker starts, including a retry mixing kept and fresh workspaces; it never falls back to direct writes. [branch-ignore-policy.ts](branch-ignore-policy.ts) freezes ancestor/nested `.gitignore` files and available repository-info/global excludes in a separate private Git evaluator. Newly created ignored directories, and in a folder copy or a candidate existing ones too, stay disposable on both green and failed tasks; a direct merge does not drop their files silently: the files a task added, changed or removed there are listed in `BranchMergeOutcome.ignoredChanges` and in a row note (`not merged: N files under ignored directories (src/generated/api.ts)…`), and a task whose declared `files` or `provides` paths (a `file` name or `in`) lie at or under one of them turns `needs_orchestrator`; ordinary ignored standalone files keep their copy-and-merge behavior. Put deliverables in tracked/unignored paths outside disposable directories. Git is required when a repository or ignore files need classification: if it is unavailable those waves fail closed; plain no-ignore folders can still be copied. Existing user-created symlinks retain their targets, and real worktrees retain Git's common metadata; workspace isolation is not whole-process confinement. The worker's session, brief, write scope, declared inputs and declared-file check all point at its workspace (`RunWorkerTasksOptions.taskWorkspace`). Every directory of a workspace the original also has takes the original directory's permission bits after the copy or checkout (which apply the umask), so a `chmod 775 src` or `700` in the original does not read as a change to the candidate's directory-mode inventory. Copied files keep the original's mtime and atime (and mode), so the declared-file check, which reads an mtime from the worker's start on as a write, reports an idle worker `no_changes` in either mode, candidate integration included; the task manifest is still stamped from the workspace after the copy. After the wave each workspace is merged back in task order, file by file against the base: a file only the task changed is copied in, one the folder also changed is merged with `git merge-file`, anything else is a conflict that leaves the folder's file untouched, saves both sides under `.atomic-agent/fusion-merge/`, turns the row `needs_orchestrator` and returns a `merge-<id>` task in `details.merges` for the planner. A declared input the task removed or cut to under half its lines is refused at merge time. Failed, cancelled, timed-out and queued tasks are not merged; their row names the paths it drops (`not applied: csv_total.py (task cancelled)`, up to 10 then a count), and a rejected candidate's result names its unapplied files the same way. A worker whose turn failed or threw after it changed files (not on credit, approval, budget or cancellation, nor on a fan-out breaker blocker such as a tool-protocol mismatch, a rejected sign-in or a usage limit, which stays `failed` with the same files note so the breaker still trips) comes back `needs_orchestrator` with `finishedWithoutReply` and a note naming the files (`finished without a reply; files changed: …; unverified — read/check them before accepting`, issue #29) instead of `failed`, and the breaker counts it by its underlying error; under isolation its gate still runs but its workspace is held as a patch, never merged unseen, and in place its files go through the usual syntax and contract passes (a syntax failure is added to its notes, `syntax: 1 file failed (a.py)`, and the row stays `needs_orchestrator`). Partial `no_changes`, `needs_orchestrator` and `max_steps` rows remain eligible for merge under the existing integration policy; isolation does not make a wave transactional or verify every partial result. For completed `ok` tasks, the merge gate ([merge-gate.ts](merge-gate.ts)) runs the task's own checks (`check.task`) and the syntax pass on its changed (else declared) files in its workspace and, with the judge on, the judge rules there; a red task is held back (`failed`; one the judge could not verify is `needs_orchestrator`, so autoReplan holds its dependents), the folder untouched, its changes saved by [branch-diff.ts](branch-diff.ts) as `.atomic-agent/fusion-merge/<task>-<hash>.patch` (sanitised id plus a short hash of it) and named in its row's note. With git on the machine the patch is made by git in a throwaway object store (`hash-object --no-filters` of both sides of the touched paths, `diff-tree --binary`), so `git apply` on the folder reproduces the workspace, binary, empty, removed files, symlinks and exec bits included (stamps cover symlinks and modes); without git, the text patch is kept and the rest is copied whole into `<task>-<hash>.files/`, which the note names. The merge folder gets a `.gitignore` of `*`; a task's patch is removed once a later attempt merges green. A judged-red task's workspace is kept (`BranchSet.cleanup(keep)`) and its retry runs in it, so the retry fixes its first attempt against the base it started from and is gated again; kept workspaces are removed after the judge, and in a `finally` around everything after the waves. A gate verdict is reused after the waves unless it went stale (`MergeGateState`): the task's own merge needed `merge-file` (or hit a conflict), a later merge changed one of its files (merged paths plus declared files); a stale task's gated checks and syntax pass run again on the merged folder, and a stale check that fails drops its gate verdict so the judge rules on the folder. Not gated, and run on the merged folder after the waves as before: checks with no owning task, an own check whose spec names a path a concurrent task writes (`concurrentPaths`), and a split's subtasks. Workspaces are removed in a `finally`, on abort and throw too: Node's `rm` removes each workspace and its own Git store without following generated symlinks or junctions. Setup, planning, cleanup and stale sweeping never register, prune or remove worktrees in the original repository.
[task-tree.ts](task-tree.ts) is the task tree (ATO-940, `taskTree.enabled`, default off; `maxDepth` 2, hard cap 3; `maxNodes` 24). Workers still never delegate: a worker that may split is told how in its brief and steered once at the half-budget hand-back or a cut first answer (`SPLIT_GRACE_STEPS` more steps), and ends its turn with a fenced `split_proposal`. The delegate validates it with `parseDelegateArgs` plus the depth, node and parent-files caps, namespaces ids as `parent/child`, runs the children through the same runner (turn caps, approval scope, child budgets clamped to the parent's), checks their contract and the parent's declared files, and closes the parent row on them. A refused proposal leaves the task `needs_orchestrator`. `details.taskTree` carries the nodes.
[task-profiles.ts](task-profiles.ts) is subagent profiles (ATO-566): a task's `profile` (built-in `explore` / `review` / `research`, or a trusted project's, the user's or a plugin's, see [subagent profiles](../../agent-profiles/README.md)) quotes the profile's instructions into the brief (a `PROFILE` block after the TASK, FILES, DELIVERABLE and contract, before the RULES; on a local leg its instructions are clipped to `LOCAL_PROFILE_PROMPT_CHAR_BUDGET`, 2,000 chars, with a note), narrows the worker's tools to its allowlist (`workerToolFilterFor`, ANDed with the worker policy) and, when the task named no `model` or `role`, sets the role or model from the profile's `model`. A split's children (`task-tree.ts`) run under their parent's profile; a profile a child names itself is dropped. An unknown name refuses the call; `details.profiles` says what was applied, and each profiled row carries `profile` (`{ name, source, tools }`, `tools: "all"` when not narrowed; a non-built-in profile shadowing a built-in's name without `tools` also gets a row note). No task naming a profile, nothing is loaded.
[run-checkpoint.ts](run-checkpoint.ts) and [run-resume.ts](run-resume.ts) let a run survive a restart (ATO-617): one JSON file per run under `<stateDir>/fusion-runs/` (not a table: the session store's schema and turn marks are pinned, and a checkpoint write must never fail a fan-out), written after every finished task (row, spend, side-effect tools as they start) and every wave, deleted on a normal end, kept as `interrupted` when the turn was stopped. A resume counts the checkpoint's recorded spend toward the turn's cap once per run and turn (`FusionTurnBudget.openRunAccounting`, issue #87): a retry after a refused or timed-out approval, the checkpoint unchanged, adds nothing, and new spend on the checkpoint adds only its increment over what the turn counted; a fan-out that ends records for its run what the turn actually counted (the import plus the cap's own growth during the fan-out: requests and carried spend under a request cap, worker spend otherwise), never the checkpoint's figure, whose estimates the cap may not have seen, so a later resume in the same turn imports only that difference. The handle is bound to the turn the call started in: a fan-out that unwinds after the next turn began records nothing into it. A file whose process is gone or stopped is offered (`runtime.fusionRuns`, `/fusion` in the TUI) for 7 days. `fusion.delegate { resume: runId }` replays the checkpoint's own arguments: settled tasks are carried; cancelled, queued and explicitly not-started rows run again, subject to the same side-effect confirmation guard. Spend so far counts toward the turn's cap, and a task whose worker called anything outside the file tools and reads (`toolHasSideEffects`) is not re-run until `confirm: [taskId]`. Checkpoints retain observed changed paths, the shell-coverage flag and a `needs_input` row's `question` (apart from the clipped reply; optional, so older v1 files still load), so resumed artifacts are checked again, including files omitted from `task.files`. JSON input is bounded to 8 MiB and nested task/result fields are validated. Reader-only limits do not reject accepted ids, requests, tool maps or legacy labels within that aggregate budget. New writes bound display titles; arguments, identities and the original request stay exact. Aggregate verification detail is compacted with incomplete coverage rather than making the run unreadable. If exact replay data alone exceeds 8 MiB, or storage is unavailable, the delegate reports checkpointWarning and non-resumability without advertising a run id. The optional v1 metadata keeps old checkpoints readable; an old successful filesystem mutation (including move/trash) without coverage metadata, a new row with untracked shell/archive/skill writes, or a row whose path/notes metadata was clipped becomes `needs_orchestrator` instead of silently passing verification. This records file-tool coverage. Shell writes can escape the observed path list, so a resumed successful row with such writes requires orchestrator verification even when it declared files; the runtime does not claim those names cover every shell output. Desktop has no offer yet. With a fusion team (issue #37) the checkpoint records the session's `director` (optional, still version 1); a resume under a different director proceeds, logs a warning and says so in the summary (`details.resume.director`), and the turn's `### route` note names the director change. The director is the run mode's (`mode.director`); `FusionDelegateDeps.currentWorker` gives the calling session's preferred worker (`runtime/session-director.ts`).
[outcome-log.ts](outcome-log.ts) is the outcome log: when a fan-out finishes (`FusionDelegateDeps.outcomeLog`), one `"task"` NDJSON record per task that ran (a `not started:` row is left out) goes to `<stateDir>/fusion/outcomes.ndjson`: provider and model (`outcomeLabel`: a value that reads as a local file path keeps only its base name, without a model-file extension), leg (`local` / `cloud` / `orchestrator`), role, status, a failure category from a fixed list (`failureCategory`: the non-`ok` status, else the breaker's blocker class, `syntax`, `checks`, `judge-red`, `not-started` or `error`), the turn's attempt (`FusionTurnBudget.attempts`, counted every round whether or not autoReplan is on, so a manual re-delegation is attempt 2), judge retry, self-check notice and escalations (`WorkerTaskResult.selfCheckNotice` / `escalations`, set by the runner), judge verdict, syntax demotion, steps, work time (`durationMs`: the row's wall time less `queuedMs`, the wait for the server's first token or the whole time of a worker never served, and `heldMs`, the time its self-check spent in the held runner's authorization, an operator prompt included; the report's median and measured routing read it) and wall time (`wallMs`; older records have none and wrote wall time as `durationMs`), tokens, cached tokens (a completion without reported `usage`, a llama-server worker's, adds its `timing` counts and `cacheHitTokens` to `WorkerTaskResult.localTokens`, never to synthetic `usage`, and the record falls back to them: such a row's "in" includes each step's cached prompt part; a row a cloud re-run replaced keeps only the local attempt's counts), cost (`null` unpriced) and merge outcome under isolation (`merged` / `conflict` / `held`). Each task record also carries `taskKey` (issue #95), and `milestoneKey` when the approved project plan has a row for the task, so a report that knows the plan's ids can join per-task outcomes to plan rows: each key is `outcomeKey(id)`, the first 16 lowercase hex characters of SHA-256 over the bare id string encoded as UTF-8 (no prefix, salt or trimming; the task id `impl` gives `ced2128f3bc92a57`), the task's `fusion.delegate` id and the plan row's `milestoneId`. Both are absent on older records, which still read. No brief, reply, title, task id, milestone id, path or error text; the session is `sessionTag`, a 12-hex sha256 prefix. Appends are synchronous whole lines; the file rotates at `OUTCOME_LOG_MAX_BYTES` (5 MB) keeping `OUTCOME_LOG_KEEP` (2), only under the `<log>.lock` O_EXCL file shared by every process ([outcome-log-lock.ts](outcome-log-lock.ts): owner pid, broken when that pid is gone or after 5 s; a writer that cannot take it within 25 ms appends without rotating); a torn last line is skipped by the reader; a failed write is a warning, never the fan-out's error; `llm.runMode.fusion.outcomeLog: false` writes nothing. [turn-receipt.ts](turn-receipt.ts) tallies the turn (`FusionTurnLedger`, opened with the fan-out grant, fed every orchestrator completion through `TurnUsageMeter`'s `onRecord` and every fan-out by the delegate); just before the turn's `turn_finished` the runtime ([runtime-fusion-outcomes.ts](../../runtime/composition/runtime-fusion-outcomes.ts)) emits it as a `fusion_worker` event (role `orchestrator`, task `fusion.turn`) whose summary is the receipt line (strong-side $: the orchestrator's requests, its `model: "orchestrator"` tasks and the judge and escalation calls, one total when all are priced, else each part named, e.g. `unpriced (subscription) + $0.03 judge`; requests, `cache hit X%` of the prompt tokens when cached tokens were reported: `usage.cachedTokens`, or a subscription CLI's `cacheHitTokens` (`completionUsageForTurn`), worker-leg tokens and wall time, tasks ok/failed) and appends a `"turn"` record with the per-step prompt and cached tokens (first `TURN_STEPS_RECORDED`). [outcome-report.ts](outcome-report.ts) aggregates both for `atomic-agent fusion report` and `/fusion report`; a worker model's `costUsd` sums its priced tasks only and `unpricedTasks` counts the rest, printed `$x (+N unpriced)` like the orchestrator rows (issue #74). The runner also brackets those two waits with `fusion_worker` events `phase: "queued"` / `"awaiting-approval"` and `edge: "start" | "end"` (the held runner calls `ContractCheckRunner` ctx `onHold`); the TUI's live row says `queued` / `waiting for approval` and leaves them out of its elapsed time, its expectation correction and its stuck flag, and the fan-out block names a pending approval of the operator's (merge gate, candidate finish, a check's `verify.run`) as `waiting for your approval: <tool> (<category>)`. The per-approval deadline stays on wall time.

[Private Git stores](private-git-workspace.ts) apply to the candidate, every nested task, the frozen checked source and the untouched base. Read-only source queries import available commit history and branch/tag/remote-tracking refs, including symbolic refs, as private object/ref data; an already shallow source keeps its available shallow boundary. A changed working tree gets a private snapshot commit parented to the original HEAD, preserving actual tracked bytes throughout the repository, including dirty sibling packages outside a selected subdirectory. HEAD is detached as before. Reflogs and unreachable objects are not imported. Source config/includes/hooks, operational remotes, object alternates, hardlinks and worktree pointers are not copied; remote-tracking refs therefore remain readable data without granting a configured fetch/push destination. Info/global ignore-rule bytes are frozen into each private store, with only a private excludes-file setting. Source index and shared-index files are copied through pinned read-only handles before any index query; Git inventories operate only on those private copies, because reading an aged split index with Git can otherwise freshen its original shared-index metadata. Workspace indexes are then rebuilt privately. Checkout byte overlays cover every tracked path in the repository, including siblings whose ident/eol attributes transformed checkout bytes. Ordinary shell commands, existing external user links and side effects remain outside this workspace-isolation boundary.

`tools.verify.maxGitObjectBytes` (default 2 GiB, configurable up to 1 TiB) separately bounds cumulative raw object inspection/imports, compressed pack transfers, private index data, dirty-blob staging and frozen exclusion data per branch set. Git checkout materialization remains exempt from the existing payload copy allowance, so a tracked 700 KiB file still fits a 1 MiB payload cap. Object/ref/tracked inventories allow at most 100,000 entries each; source ignore-rule files are at most 8 MiB each. Each preparation or materialization operation has its own 120-second deadline under caller cancellation, and pack children are stopped on cancellation or overflow. Excess history fails closed with the setting named in the reason; it never silently truncates history or takes an unreserved folder-copy fallback. The public `isolation: "worktree"` and internal method name remain compatibility names for this private Git implementation.

[worker-question.ts](worker-question.ts) is a worker's question (ATO-945): there is no blocking call to the planner (its turn is inside `fusion.delegate`), so a worker that cannot do its task right without an answer ends its own turn with a `NEEDS_INPUT: <question>` line. The task comes back `needs_input` with `question` (at most 300 chars) on its row and a note telling the orchestrator to answer it and send the task again; when it wrote nothing its declared files are not checked and a failing check does not turn it `failed` (one that wrote files is checked as if done: a missing declared file or a failing own check turns it `failed`, the question kept on the row; under `isolation: "worktree"` a failing own check or syntax pass holds its changes back as a patch, the row still `needs_input`), the breaker treats it like a finished task, a dependent is warned it did not deliver, and `autoReplan` keeps it open.

A later wave's CONTRACT block carries what the waves before it did (`completedWaveNotes` in [contract-waves.ts](contract-waves.ts)); for a delivered task that is its reply's `PROVIDED:` list, the names and paths it really exposed, renamed ones included (ATO-945), else the head of its reply.

[outcome-journal.ts](outcome-journal.ts) and [outcome-summary.ts](outcome-summary.ts) are the planner's memory of this machine (ATO-949; a separate file from the outcome log above, `FusionDelegateDeps.outcomeJournal`): every finished worker task appends one JSONL row to `<stateDir>/fusion-outcomes.jsonl` with counts and labels only (leg, model, role, a size bucket from brief length and declared files, status, time, steps, writes, output tokens, priced spend). Never the brief, title, task id, paths, errors or reply. Past 512 KB the file is rewritten with its newest rows (at most 2000, at most half the cap). The newest 300 rows are summarized into the `### fusion` block's last line once per session (the first step of each session reads the log; the summary is then held for that session), "Past runs here: …": one fact per (leg, model, size) group with at least 3 judged tasks (`cancelled` and `queued` are not judged), failing groups first, at most 6. Held per session because those bytes sit in the cached stable prefix; a new chat in the same long-lived process sees the rows appended since. `llm.runMode.fusion.outcomeJournal: false` (default `true`) writes no rows and states no summary.

## Runtime artifact evidence

A fan-out with artifact or verification evidence exposes `details.artifactManifests[taskId]`, also on each task's `artifactManifest`. The task block's `manifest:` line points to these structured details. Entries use paths relative to the final working folder, actual file kinds/modes, and SHA256 of allowed regular-file bytes or a symlink's link text. Link targets and outside-root ancestor links are not read. No file contents, link text, command arguments, check output or worker claims become manifest evidence. A hash describes the current folder at collection time; it does not upgrade a failed or held-back worker into a successful delivery.

Default inventory comes from runtime-observed file-tool changes (including moved-from/deleted paths), declared files and provide locations. It is explicitly `observed` and incomplete: shell/archive/skill writes can create other outputs, and a declared file list is not a snapshot. Contract/syntax outcomes come only from their runtime runners; missing runners and advisory dependency tokens stay `unknown`. Dependency evidence aggregates all required provides for each provider/requirement pair, matching findings by kind, name and exact search locations. Any missing location blocks the evidence; absent findings remain unknown. Checks that failed are recorded as failed facts, not hidden by the worker's reply. `coverage.complete` describes evidence coverage, not test success; inspect `checks` and `dependencies` as well.

Collection adds no model call. It hashes at most 8 MiB for the entire fan-out, 2 MiB per file, with up to 128 inventory entries per task and a shared 2 s deadline under the turn's abort signal. A manifest is at most 128 KiB of JSON. Missing/unreadable/out-of-scope/changed-during-read files, cancellation and clipped entries are explicit reasons for incomplete coverage. The v1 checkpoint stores this optional, validated field; serialization clipping marks incomplete coverage. Older checkpoints still load. On resume the recorded inventory is recollected before publishing fresh results, including an empty historical manifest: saved snapshot authority is never carried into INNER results. Unidentifiable paths and lost inventory stay explicitly incomplete; persisted hashed entries require a real relative path. Saved hashes are historical evidence, not proof that files stayed unchanged.

`collectArtifactManifest` also accepts an authoritative `snapshot` inventory from runtime snapshot/diff code. Only that inventory may claim complete coverage when all bounds, scope and evidence checks permit it; worker prose cannot select snapshot authority. The collector is independent of candidate execution or promotion.

## Candidate integration

Protected check inputs may live under excluded directories such as `dist/` or `node_modules/`. The built-in verifier copies each excluded ancestor containing a declared input privately into its actual execution workspace and charges those bytes to its existing configured copy ceiling. Unrelated excluded directories retain their existing linking policy. Original linked ancestors remain refused, and actual-copy begin/completion byte, identity and write observations remain required; declaring a path does not grant trust to its contents or transitive imports.

The additional private final-check source consumes the same cumulative copy allowance as candidate staging. This can refuse a project that fit the earlier candidate implementation; increase `tools.verify.maxCopyBytes` when that extra private copy is required. Staging uses already measured private dependency-copy bytes as a minimum floor and refuses before workers when that floor alone exceeds the remaining allowance. This is no exact reservation: ignored files, checkout differences and worker output growth can still cause a later refusal. Budget errors distinguish the configured ceiling, staging bytes spent, remaining allowance and minimum additional dependency bytes. Dependencies are never aliased back to the writable candidate to evade this cost.

Check plans remap literal project paths at staging, final-source creation and actual execution. Recognized source file URLs (including encoded spaces and Windows UNC paths), home-variable, tilde, escaped or redundant-separator/dot aliases that still resolve into the source are refused before execution; external paths and similarly named siblings stay unchanged. This restricted remapper does not parse arbitrary shell languages or confine reads reached indirectly by a program. Linux preserves case-distinct paths; Windows and macOS use their conservative case identity. Ignored-output declarations likewise use native path identity, including macOS normalization and Win32 component aliases, so an undelivered declared output cannot stay green through another spelling.

`llm.runMode.fusion.integration: "candidate"` opts into whole-fanout file promotion ([candidate-integration.ts](candidate-integration.ts)). Unset or `"direct"` preserves the existing integration policy above. The original project is approved first; the complete fan-out, its waves and optional per-task `isolation: "worktree"` then run inside one private candidate. Candidate write scopes must stay inside the selected project. Saved project rules still apply; original-path deny/ask rules and declined files map to their candidate copies. Allow rules are not widened by that mapping. Declared inputs and worker refusal policies remain dispatch guards.

Promotion requires every task to close `ok`, all declared provides to be present and inspectable, and at least one explicit `contract.checks` entry. All declared checks run again on the final candidate after all task output and retries, including checks previously passed by an isolated merge gate. Missing runners, skipped checks, cancellation, blocked or partial rows, absent provides and failed checks hold the candidate back. Every final check uses one private frozen source made after all workers finish. The candidate and frozen source must match before and after checking, including unchanged code; promotion copies only frozen checked bytes. Custom runners that change deliverable files during final checks are rejected. The production verify runner writes outputs only in its own disposable copies. This verifies the declared checks, not semantic correctness beyond them. Unmatched external `requires` stay advisory and appear as unknown evidence. The bounded artifact manifest reports incomplete coverage explicitly; the separate complete transaction inventory governs byte delivery. Candidate executed task outcomes are appended only after the final disposition and remain telemetry, never accepted routing quality history. Call-level checks do not credit an individual worker model.

The original dirty and untracked state is the merge base. A byte/type/mode inventory, without following symlinks or trusting modification-time caches, must still match before promotion. Concurrent changes hold the entire candidate back; promotion never performs an untested three-way merge. That full inventory is taken once; before each write delivery re-verifies only the target and its ancestor directories (lstat plus bytes, against the merge base overlaid with already-delivered entries), and after the last write it verifies the touched paths once more, so delivery costs the changed bytes rather than one tree scan per path. A concurrent change at a touched path stops delivery and attempts rollback, as does a later write failure or cancellation; an unrelated user edit made while delivery is running is left alone and is not detected. Immediately before each rename, removal, directory creation or directory removal every ancestor directory is lstat-ed again and must still be a real directory with the device and inode that step verified (a parent swapped for a symlink is refused), and the target must keep the identity (device, inode, size, modification/change times, mode) it had when that step hashed it, or still be absent; otherwise it counts as a concurrent change and the user's bytes are kept. The rename or removal itself cannot compare-and-swap, so an edit landing between that last lstat and the call can still be overwritten. Before the first write, promotion creates a journal `.atomic-agent/fusion-merge/<candidate-id>.promotion.json` (requested mode `0600`, written tmp-then-rename with file fsync and best-effort directory sync, including its newly created parents) and a `<candidate-id>.promotion-backup/` folder beside it with requested mode `0700`; each backup file requests mode `0600` whatever the original's mode, which the journal records. A delivered file's temp copy is made writable with requested mode `0600` to open a write-capable handle, then its final mode is restored and both bytes and metadata are fsynced through that retained handle before renaming it, and best-effort directory sync is requested for each change's parent afterwards. Each step is appended as `intent` before its write and marked `applied` after it, with its `path`, `action` (`write`, `delete`, `mkdir`, `rmdir`), `original` and `promoted` entry (`kind`, `mode`, file `sha256`, symlink `linkTarget`; `null` when absent) and, for a modified or deleted file, `backup`: the pre-image bytes, relative to the merge folder; a file or symlink write also names its `temp`, the `.atag-candidate-*` sibling it is staged under before the rename (relative to the project). If the first journal write fails, the backup folder is removed and nothing is delivered. After the final verification, successful delivery writes and file-syncs `state: "committed"` and then deletes both; if that removal fails, the promotion still stands and the report names the leftover journal in `promotionJournal` with a `promotionJournalNote`. A `"committed"` journal means do nothing: the delivery completed and was verified, so just delete the journal and its backup folder. A complete rollback deletes both; a rollback with conflicts keeps them, marks steps `rolled-back`/`rollback-conflict`, sets `state: "rolled-back-with-conflicts"` and names the journal in `CandidateIntegrationReport.promotionJournal`. A journal still in `state: "promoting"` or `"rolling-back"` means the process stopped mid-delivery. Inspect it with `atomic-agent fusion recover <journal> --project <project>` (default read-only status), preview with `--dry-run`, and explicitly request `--rollback` to restore verified pre-images. The [recovery reader](promotion-recovery.ts) validates version 2, the selected canonical project, paths, entry identities, backup hashes and the owner process before writes. Unknown versions and incomplete legacy journals require manual inspection. It reverses steps while preserving later user edits as conflicts; an already-restored entry is recognized after a second crash. A completed explicit rollback retains a terminal `rolled-back` journal and backups, so repeating it cannot undo subsequent edits. Committed delivery cannot be rolled back by this command. Nothing resumes or rolls back at startup. The marked private candidate workspace is also retained for comparison. Rollback re-verifies each delivered path individually (a directory it created counts as delivered as soon as it exists, so it is removed while empty even if setting its mode failed), preserves a path edited after delivery and reports any path it cannot restore. This is a guarded file transaction, not atomic visibility across several files or whole-process confinement: existing user symlink targets, shell commands and external side effects retain their existing boundaries. Directory type/mode replacements that cannot be safely delivered are refused for review, and so is deleting a directory that still holds ignored or disposable entries in the original (they are never removed): the reason lists them before anything is written.

Permission and durability limits: the requested `0600` file and `0700` directory modes provide owner-only POSIX permissions. On Windows, `chmod` changes the read-only attribute rather than installing owner-only ACLs; journal and backup access depends on inherited ACLs. File fsync tolerates `EINVAL`, `ENOTSUP` and `EOPNOTSUPP` from filesystems that cannot flush, so those hosts do not get the corresponding durability guarantee; other errors, including `EPERM`, reject the operation. Directory sync is best effort: it is skipped entirely on Windows, and errors on other platforms are ignored. Persistence of the journal names, promoted renames and directory entries across power loss therefore depends on the host filesystem and directory-sync support.

Private workspace copies retain the existing cumulative limit per branch set (`tools.verify.maxCopyBytes`, default 2 GiB, the same setting that bounds `verify.run`'s copy; it also bounds candidate inventories and hashes), charging actual base/task/ignore-rule copies but not Git's separate checkout materializations. Before workers start, a dry run of the same copier measures the entire baseline final frozen-source branch set, including ordinary payloads, tracked byte overlays, private dependencies and frozen ignore-rule files. It creates only temporary Git checkouts, links and metadata, without copying payload files, and is bounded to 30 seconds and 100,000 visited entries under caller cancellation. Staging refuses when that measured baseline cannot fit the remaining candidate byte budget. The final frozen check source then spends that same remaining budget (it does not receive a renewed allowance); later worker growth or changed copy policy can still refuse it. Its plan fixes the canonical source and Git/folder method: Git takes a fresh final snapshot so tracked worker edits retain efficient checkout materialization, and loss of Git or a changed repository root refuses staging instead of taking an unreserved folder-copy fallback. Final creation has a 120-second caller-cancellable limit. Nested per-task isolation retains its separate branch-set budget. Nothing may reach the original before promotion, so the candidate does not link the shared dependency directories (`node_modules`, `target`, `.venv`) to the original: it gets one private copy of them (`privateDependencyDirectories`), charged to the copy limit; the candidate's base normally links (symlink, else junction), since nobody writes to it; when neither is possible it holds an empty placeholder instead of a second copy, so the dependency tree is copied from the original exactly once. A dependency tree too large for the limit therefore refuses candidate staging; the error names the same reason as an isolation refusal (`candidate workspace unavailable: the candidate's private copy of the dependency folders exceeds the copy limit (N bytes)` when only that copy overflows, else `… the folder is too large to copy`). A user link inside that copy whose absolute target lies inside the working directory (npm workspaces on Windows, pnpm: `node_modules/@s/pkg` → `<project>/packages/pkg`) is pointed at the same place inside the candidate, so a write through it stays private. In a monorepo subdirectory (working directory `packages/app`) the candidate's worktree holds the whole repository's tracked files, so a target elsewhere in the repository (`<top>/packages/lib`) is pointed at the same place in that worktree; when that place is untracked or ignored and so absent there, staging is refused. A folder-copy candidate holds only the working directory, so a dependency link into the repository outside it refuses staging (`the dependency link node_modules/lib points into the repository outside the working directory …`) instead of leaving a write path to the original. A relative target that resolves inside the working directory (from the original link's folder) is kept relative; one leaving it is recreated as its absolute original target, so it neither dangles nor resolves to an unrelated folder beside the copy, and then follows the rules above (this also applies to any dependency link copied because no directory link was possible). Targets outside the repository (without one, outside the working directory) are kept as they are (a write through them is not isolated). Where symlinks are denied, a user link to a directory under a dependency directory is recreated as a junction to the same resolved path; any other user link that cannot be recreated fails workspace setup with a reason naming it. Nested task isolation creates its own branch sets from the candidate, so its task workspaces link to the candidate's copy, never to the original; a worker write there is discarded with a rejected candidate and is never promoted (the folders are not inventoried). Ignored directories remain private, disposable inputs/caches. Unlike worktree merging, candidate promotion also keeps ignored standalone files (`.env`, logs) private: they are copied for checks but excluded from both inventories, so a worker's edit or deletion of them is never promoted. They are classified with the same frozen rules as directories, so a dir-only pattern (`out/`) also keeps an untracked file named `out` private. Work the ignore rules would silently lose is refused rather than dropped: a declared `provides` path (a `file` name or any `in`) at or under an ignored or disposable path rejects the candidate, as does a deleted tracked file whose bytes reappear in a new ignored standalone file (`notes.md` renamed to `notes.log`). Ignored directories are stamped at their top level only, never walked, so a rename into an existing ignored directory is not matched; every new or resized ignored path is listed in `CandidateIntegrationReport.ignoredChanges` and in the tool result's note. A candidate change under the project's agent state folder `.atomic-agent/` (approval rules and other operator-owned state; the root merge folder excepted), or under a nested one at any depth (`pkg/.atomic-agent/`, which a session working in `pkg/` would load), rejects the whole candidate with a reason naming the paths. The folder name is matched conservatively on every platform, in every path component, case-insensitively and with Win32 trailing dots, spaces and `:stream` suffixes dropped, so `.ATOMIC-AGENT/` or `.atomic-agent./` is refused too; an ignored `.atomic-agent/` is simply never promoted. The candidate inventory never applies ignore rules or the dependency/build folder names (`node_modules`, `build`, `dist`, `target`, `.venv`) to a path the snapshot tracks: a tracked `scripts/build/pack.sh` is copied, checked and promoted like any other file. Untracked folders with those names stay disposable (a folder-copy candidate has no tracked paths, so there they are always disposable: outside Git, and also inside a repository that falls back to a folder copy because Git cannot snapshot it, such as one with no commit yet or a merge in progress). Candidate setup is bounded to 120 seconds; each streamed inventory is bounded to the copy limit (2 GiB by default), 100,000 entries and 30 seconds, and promotion has a 120-second deadline. Caller/turn cancellation remains active; declared checks retain their runner's limits. A limit or unreadable input fails closed.

Candidate mode is explicitly non-resumable: it creates no ordinary run checkpoint and no resumable run ID (`details.runId`) and refuses `resume`, so carried green rows cannot be replayed onto a fresh candidate. Its evidence still gets a real run (issue #74): a fresh `fr-<uuid>` whose `<stateDir>/fusion-runs/<runId>/` folder holds only the checks' screenshots and `criteria.json`, and which a project milestone records (`milestone_run`), so a done report reads the run's facts like any other. Those facts are written after the candidate's finish: a candidate not promoted keeps no criterion `passed` (each becomes `unverified`, "candidate not promoted: <reason>"). Gracefully rejected/interrupted changes are retained as the existing binary-capable patch under `.atomic-agent/fusion-merge/`; held inner-task patches are copied there too. Patch/recovery metadata may be written there even when project outputs are rejected. If bounded patch creation fails, the result names the private recovery workspace and cleanup retains it. A recovery ownership marker prevents stale sweeping from deleting it; after inspection/recovery, remove the retained workspace manually. A hard process stop cannot produce a final patch: its marked private workspace remains for manual recovery and is never advertised as a resumable run. Successful and fully patched rejected runs remove their temporary workspaces normally.

A candidate may declare `contract.checkInputs`: up to 32 exact existing regular project files (no patterns, outside paths, linked ancestors, symlinks or alternate streams), at most 2 MiB each and 8 MiB total. These bytes, type and mode are frozen from the original before workers start, hashed through a pinned verified file descriptor (with no-follow open where supported), and verified in the candidate, final checked source, and every actual verification execution copy. The trusted runtime runner verifies baseline bytes before execution and bytes plus file identity and modification/change timestamps afterwards, detecting ordinary writes even when the check restores its contents. Every declared check must complete that guard. Explicit absolute project references are rebased into the actual guarded execution copy as well as the frozen source; unrelated executables and sibling paths are preserved. Ambiguous escaped project references are refused. A changed, missing or unreadable declaration, or a custom runner unable to attest this execution scope, rejects promotion. These are before/after runtime observations, not kernel-enforced immutability. This is separate from editable `contract.inputs`. Omitting declarations retains declared/unprotected legacy checks. Protected-declared scope proves only integrity of the declared check files; it proves neither operator approval nor discovery of transitive command inputs. Direct integration refuses checkInputs rather than suggesting it protected them.

Verification rebasing recognizes a finite literal policy: complete quoted paths, ordinary absolute arguments, `=` values, path-list segments (drive colons remain part of Windows paths), `<`, `>`, `|`, `&`, `@`, `+`, and attached `-C`/`-I` paths. Environment values and assignments named `PATH`, `PYTHONPATH`, `NODE_PATH`, `LD_LIBRARY_PATH` or `DYLD_LIBRARY_PATH` retain list context even when quoted, PowerShell-prefixed or beginning with a relative/URL-looking entry; other quoted filenames retain literal colons and semicolons. Quoted path spaces and metacharacters retain their identity; sibling and embedded external paths remain outside the project. Outside those named lists, URL spans are classified before filesystem tokens, so external URL paths, queries and fragments are preserved. Unquoted command operators end a URL span; operators inside a quoted/argv/non-list environment URL remain data. Native source `file:` URL pathnames are rebased using the platform's drive/UNC and case rules; encoded suffixes, query and fragment are retained. Recognizable source references using home expansion (including the PowerShell user-profile namespace), normalized/escaped aliases, unsupported attached options, literal controls or unfinished quotes are refused. This is lexical remapping, not shell/program evaluation, transitive input discovery or an OS sandbox; computed references and external side effects retain their existing boundaries.

The final `acceptanceReceipt` uses only an opaque runtime ID, fixed disposition/check scope/status/rejection categories, bounded counts and optional SHA256 checked-payload/check-plan digests. A receipt is promoted only after guarded delivery verification; a promoted report with zero changed paths has receipt disposition unchanged. Rejected receipts cannot imply delivery, even if checks passed. The checked-payload digest covers the authoritative transaction inventory, with documented ignored/disposable entries excluded; it is not process confinement or external-side-effect attestation. A hard stop during promotion retains the marked checked source and names it in the journal's `checkedWorkspace`; a rollback conflict also returns `retainedCheckedWorkspace`. Remove retained sources manually after recovery. After a candidate decision completes, later rendering or metadata failures preserve that disposition and the once-recorded outcomes. If safe redaction metadata is unavailable, the tool returns only a generic terminal status and bounded counts with metadataUnavailable; worker prose, error text and recovery paths are omitted.

Candidate inputs inside the project use their declared relative suffix for both worker dispatch and final promotion guards. Absolute declarations retain the same protected original identity; literal braces or brackets in a generated workspace prefix cannot turn them into advisory globs. Genuine glob suffixes retain their advisory behavior. Setup tree stamps and ignore queries carry the setup/caller signal throughout traversal. Recovery tree scans and patch commands share an independent 30-second signal so an already-cancelled turn can still save its patch; expiration retains the marked workspace for manual recovery.


The tool output always starts with `artifact-evidence:` followed by one bounded runtime JSON document, including when no manifest exists. It is available in the next local/cloud model request. The runtime outcome distinguishes tool status and task-status counts; a candidate disposition/reason summary is derived only from a fully validated receipt. Task hashes are final-project observations, never final-delivery proof. Only the authoritative final candidate snapshot can bind its receipt ID, checked payload/check-plan digests, check scope/status and promoted/rejected/unchanged disposition. Legacy v1 manifests remain unbound; resumed task observations are recollected. Worker prose follows inside the existing nonce-fenced untrusted-content wrapper; reserved evidence labels, forged fences, chat delimiters and invisible controls are neutralized. Paths reject control/format characters and Unicode line/paragraph separators and remain quoted data, not instructions. Every structured string escapes Unicode line/paragraph separators and angle brackets during JSON serialization; budgets measure the escaped output. This framing separates provenance; it is not a guarantee against every semantic prompt injection. Configured and environment known secrets are masked on complete source strings before evidence budgeting or prose clipping. Projection scans at most 256 rows, retains up to 16 valid task manifests and initially 8 artifacts/checks/dependencies each, and admits relative paths up to 256 characters. JSON is capped at 4,000 characters and normally 40% of the configured whole-result budget, reserving readable failure/outcome prose; tiny caps may use more for a minimal whole runtime document. Trimming removes whole facts and marks omitted/incomplete. A full receipt is never shortened into an apparently canonical partial receipt: when it cannot fit it is omitted, while the separate validated outcome remains. Contents, raw commands/check output and worker claims do not enter the runtime evidence.

Candidate outcomes are appended after final disposition only for workers actually executed in this call. `candidate.receipt` contains opaque identities/digests, bounded counts and fixed categories; `candidate.taskChecks` counts only task-attributed final reruns. The report's separate Candidate task runs table distinguishes promoted/rejected/unchanged/unverified. A row is one aggregated task run, not one inference or candidate call. Optional `candidate.workerRuns` counts completed worker-task invocations for that task ID in this call, including a judge retry; missing counts remain unknown. `knownWorkerRuns` sums those explicit counts and `workerRunsUnverified` counts task rows without them. Configured-leg grouping can include retries or escalations served elsewhere; costs, usage and duration retain their existing row-reported scope and do not establish complete billing or per-provider performance. Any candidate metadata presence, including malformed/unknown, excludes direct task-check quality evidence. Candidate outcomes remain telemetry only; promoted-only rates would be conditioned on success. Provider failure/blocking history remains active. The shared task-check classifier excludes inconsistent judge/syntax/merge/status metadata; reports permit later replans while routing additionally requires a first attempt with no self-check notice.

Recovery accepts an absolute journal path or one relative to `--project`; `--json` returns the state, live-owner flag, planned/restored paths and conflicts. Status and dry-run never create files. Rollback refuses a live owner and uses a recovery lock; interrupted recovery is repeatable after that process exits. Files are streamed with a 2 GiB per-file ceiling, journals are at most 8 MiB/100,000 steps, and one invocation has a 120-second deadline. Linked ancestors, Git/operator-state paths, platform-ambiguous names, unknown staging files and corrupt backups are refused. Empty created directories may be removed; user contents are never recursively deleted. Keep retained journals, backups and checked sources until inspection is complete; the command never recursively deletes a `checkedWorkspace` path taken from a journal. Filesystem identity checks have the same final syscall race and platform durability limits as promotion.

A conflict retry skips steps already marked `rolled-back` or `not-applied`: later user edits cannot reopen those completed steps even when they happen to match the former promoted bytes. A partial or edited staging file is kept as `retainedStaging` in the preview, result and journal; recovery restores a verified target through a fresh staging path and never deletes the unattested file.

Recovery validates canonical filesystem names as well as journal spelling. NTFS short-name aliases cannot reach `.git` or `.atomic-agent`, and noncanonical existing output aliases are refused before mutation. A preview accounts for files that will remain inside a created directory and reports the same non-empty-directory conflict as rollback. On Windows an original link to an existing directory can be recreated as a junction; file symlinks still require the host's symlink support.

An ancestor outside the selected project may be a junction or NTFS short name. An absolute journal under the caller's project spelling or the canonical project root is accepted by mapping its validated relative name into the canonical root. The journal itself is never canonicalized through internal links: `.atomic-agent` and `fusion-merge` must still be real directories, an outside journal is refused, and the journal header must name the canonical project.
