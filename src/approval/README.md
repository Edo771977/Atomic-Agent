## Entry points

- [coding-mode.ts](coding-mode.ts): shared default/plan/auto/bypass mapping and mode metadata; frontends adapt its policy to their controls.
- [approval-gate.ts](approval-gate.ts)
- [approval-router.ts](approval-router.ts)
- [dangerous-tool.ts](dangerous-tool.ts)
- [read-scope-grants.ts](read-scope-grants.ts)
- [approval-rules.ts](approval-rules.ts): saved allow / ask / deny rules (ATO-1141): parse, validate, `matchRules` (deny > ask > allow; an allow never applies to a category `isGrantableCategory` rejects), and the rule "Allow always" saves (`buildAlwaysRule`, `canGrantAlways`, `describeAlwaysRule`). A rule's optional `origin` matches the request's `grantKey`; an "Allow always" on `os.http.request` saves its target origin there, so it covers one host only (ATO-1471). Pure.
- [approval-rules-store.ts](approval-rules-store.ts): the files. Global `<stateDir>/approval-rules.json` (allow / ask / deny, optionally `project`-scoped; a write asks as `trust_config`, a read as `state_secret`) and per project `<workdir>/.atomic-agent/approval-rules.json`, where only ask and deny count because the model can write in the workspace. Reloads on a stat change, writes tmp + rename at 0600, and treats a missing or unreadable file as empty (an unreadable one is logged and moved aside before the next save).
- `verify_page_local`: a `verify.run` page probe that starts no command, keeps `network: false` and opens a project file or a loopback URL ([verify-page-local.ts](../tools/verify/verify-page-local.ts)). Quiet from level 2 (the `auto` coding mode); every other verification asks as `shell`. A deny or ask rule on `shell`, and a `shell` session grant, cover it; a fan-out scope covers it like a shell command. In a constrained folder every page probe needs `browser` in `allowedEgress` ([tool-egress.ts](../tools/tool-egress.ts)).
- HTTP has two categories (ATO-1462): `http` for reads (GET), quiet from level 3, and `http_write` for requests that send data (POST), quiet from level 4. A grant or allow rule on one never answers the other; a deny or ask rule on `http` also matches `http_write` (`ruleMatches`).
- [approval-workdir.ts](approval-workdir.ts): the dispatching tool call's session folder, so the gate can scope rules to a project without threading it through every tool.
- [risk-review.ts](risk-review.ts): smart approval (`agent.smartApproval`, off by default). Before a grantable request prompts, a model rates it low/medium/high under a grammar or one-field schema; `low` runs it, anything else and every failure prompts with `riskNote`. Fail-closed; never for non-grantable categories, `fs_read_outside` or a session under a refuse policy. Wired by [runtime-risk-review](../runtime/composition/runtime-risk-review.ts).
- [untrusted-taint.ts](untrusted-taint.ts): review after outside content (`agent.taintReview`, off by default, ATO-618). The tool registry reports every tool result that carries outside text (`untrustedOutput`, `externalSource`) to `ApprovalGate.noteUntrustedContent`; the agent loop clears it when a turn starts (not on a steer). While a session is tainted, a request the level or a session grant would approve, of a category `isTaintSensitive` names (it could send data out, act outward or run code), goes to the risk reviewer with the outside sources and an AlignmentCheck question ("does this serve what the user asked for?"); `low` runs it, anything else, a reviewer that is off, and a category the reviewer may not settle put it to the person with `riskNote`. A saved allow rule still answers. An `ask_user` question (`user_question`) is never held, but on a tainted session it carries `riskNote` (`formatQuestionTaintNote`, whatever `agent.taintReview` says) warning that the question may come from that content and not to type secrets; the TUI question card shows it. A session under a refuse policy (a Fusion worker) goes to the reviewer too, since the request is one its level or grant would have run anyway: `low` runs it, anything else (or no reviewer) is refused with that policy's reason (`reasonFor` or `reason`), not a taint-specific one. A fan-out (`fusion_fanout`) is held like the rest, and the turn's standing yes to an earlier fan-out does not cover one asked after outside content. Taint crosses delegation both ways (`followTaint`, armed with the worker's session): a worker counts as tainted while its orchestrator is, and outside content a worker reads marks the orchestrator too (source "a Fusion worker"), since its findings reach the orchestrator's context. A tainted worker's shell command inside its fan-out scope (`scopedByFanout` in `os.shell.run`, likewise `verify.run`) goes to the gate instead of running on the fan-out's yes. Calls that skip the gate on their own (a GET of `os.http.request` under `http.approvalMode: "writes"`, every `os.web.fetch`) ask `ApprovalGate.holdsForOutsideContent` and, when it says yes, request an `http` approval so the hold decides: their URL alone can carry data out. `http.approvalMode: "never"` and a set `http.hostAllowlist` keep answering for `os.http.request`. Known gaps, by design of where the mark is taken: output of a shell command (`curl`, `wget` through `os.shell.run`) is not a taint source, nor is reading a file such a command downloaded (only spilled output of a marked tool is); and an MCP tool that never reaches the gate (a server with `trust: "pure_read"`, or a stdio tool trusted on its `readOnlyHint`) is not held, though its output still taints the session. The orchestrator's declared `contract.checks` run what the workers wrote, so every complete batch passes the shared verification authorizer ([contract-check-hold.ts](../tools/fusion/contract-check-hold.ts)) before execution. Each check requests as `verify.run` with shell command metadata, its complete masked preview and original project scope. Runtime registration supplies live canonical credentials (including custom configured keys) and both command and local-target read guards; host-marked definitions avoid a duplicate legacy read wrapper. Local page paths and file URL surfaces use the filesystem read boundary; shell command-prefix deny/ask rules cross that tool boundary, while shell tool-only allows do not. Hard refusals and saved denies preflight the whole batch; levels, grants and smart/taint review still decide the remaining requests. No call-wide yes covers later child, retry or candidate checks. The actual rebased commands are guarded again at execution. Held: no check runs or becomes green; a candidate remains unverified and keeps its patch.
- [user-question.ts](user-question.ts): the clarifying question `ask_user` asks (ATO-489). It goes through the gate as a `user_question` request carrying `question` (prompt, 2-8 options, `multiSelect`, `allowOther`), so the turn waits like an approval and every surface that gets approvals gets it. No level, grant, allow rule or reviewer answers it (`isAutoApprovedAt` is false at every level); a refuse policy or a deny rule refuses it at once and the model is told to go on with its best guess. The answer comes back in `ApprovalDecision.answer`, checked by `validateUserQuestionAnswer`; a Deny is a skip. Pending questions live in memory like approvals: a reconnecting client gets them back from `/api/events`, a restarted agent does not (its turn ended).
- [approval-preview.ts](approval-preview.ts): fits a long preview onto a size-limited surface (TUI modal, Telegram message) by whole lines, with an explicit "+N more lines" note instead of a silent cut, and pages the whole preview (`pagePreview`) for a surface that shows all of it before the decision.

## Ownership and dependencies

A host may resolve an approval with `pinnedExec` (`{ file, argv, cwd }`, issue #95: `run --allow-command`); `requireApproval` hands it to the tool only for a `literalExec` or `verifyPlainCommand` request whose `commandArgv` it equals and whose folder's real path is its `cwd`, and the tool spawns exactly that file and argv without a shell; a pin that does not fit refuses the call (`automatic`), never runs it unpinned or elsewhere. Gate order in `ApprovalGate.request`: the same-turn refusal (`declinedInTurn`), then the same rule over calls a host resolved `unavailable` (issue #95: nobody could be asked, e.g. a piped `run`; `unavailableInTurn` refuses the same call or a write of the same file unasked for the rest of the turn, `automatic` and worded as nobody's decision, never as the user's; `hasDeclinedTarget` counts those files too), a matching deny rule (refused, `automatic`), a matching ask rule (skips the level and grants and prompts), the level, the session grant (both held back after outside content when `agent.taintReview` is on, see untrusted-taint.ts), a matching allow rule, then the session's refuse policy or the prompt. `resolve({ grant: "always" })` saves the allow rule built from the pending request, scoped to its project; hardline shell-guard rules fire before the gate and no rule touches them. A fan-out scope returns before the gate, so the tools ask `ruleDecisionFor` first: a deny or ask rule sends the call to the gate. A shell command the guard deems safe never asks either, so `os.shell.run` asks `ruleDecisionFor` for it too: a deny rule sends it to the gate, which refuses it (ATO-1332). Deny and ask rules match every command in `commandSegments`: past wrappers and their value flags (`sudo -u root`, `nice -n 5`, `timeout 5`, `env -u X`, `xargs -n 1`), inside a nested `sh|bash|zsh|dash|ksh|fish|csh|tcsh -c` line, `eval` and `find -exec` (`shellRuleSegments`). A script fed to a bare shell or interpreter through a pipe, a redirect or a heredoc (`printf … | sh`) cannot be read, so the request is marked `commandUnreadable` and any deny or ask command rule matches it. An allow rule still needs `commandArgv`. A worker in a throwaway worktree matches rules against its parent's project (`SessionApprovalPolicy.ruleWorkdir`). A session grant on a request with a `grantKey` covers that key only; a key-less `other` request (the catch-all for MCP tools, writes outside home and uncategorised tools) is keyed by its tool name, so a grant on one tool never answers another. A filesystem mutation outside home (`requireFsApproval`, `fsOtherGrantKey`) is keyed by tool and directory: the target's parent, an extraction's destination, a git verb's repository; a grant covers that directory only. `wouldPrompt` (the fan-out's pre-check) follows the same order: a deny or allow rule means no prompt, an ask rule means a prompt whatever the level or a grant (ATO-1270).

A local page probe's turn grant: the authorizer offers a turn grant (`offerVerifyPageTurnGrant`) for a `verify_page_local` request about a folder the session's approved project plan covers; only a person approving that pending request ("Allow once", in `resolve`) records that exact folder, kept on the top orchestrator session and dropped with its grants (`clearSessionGrants`, the no-argument form for every session) (a level, session grant, allow rule or reviewer approving it quietly records nothing), until the session's next turn starts (`clearUntrustedContent`). Only a probe that opens a file inside that folder (`path` or a file: URL, no `start`, network off) records or uses it; a loopback http(s) URL always asks, since it runs whatever that server serves. Later such `verify.run` page probes and fan-out contract page checks of the same folder in that turn, on the session or on a Fusion worker following it (`followTaint`), run unasked (`verifyPageGrantedForTurn`). It never covers another folder (not even a parent), another category or a session without an approved plan, and not after outside content was read in the turn by the session or its orchestrator (whether or not `agent.taintReview` is on), a declined target, or a saved deny or ask rule; every other category keeps "Allow once".

`setPendingObserver` sees exactly the prompts a person is asked: `opened` after the emit (only while still pending), `closed` on resolve, a session-wide denial or an aborted turn; it cannot decide anything and a throwing observer is ignored. The runtime installs the [approval-pending reminder](../notifications/README.md) there (`notifications.approvalPending`, off by default).

ApprovalRouter selects the handler for the owning session; level/grant logic decides whether a dispatch can proceed unattended or needs a decision. Frontends and channel bridges provide interaction, while tools consume the decision. Approval state is separate from offered prompt schemas and from the currently selected UI chat.
