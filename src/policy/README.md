# Organization policy

Status: current
Owner: src/policy/

Rules an administrator sets for every agent on a machine (ATO-587): which shell commands, file writes, web requests, skills and MCP servers are allowed, need a person's yes, or are blocked. The user cannot loosen them from the agent.

## Where the policy comes from

Read at start. No source can loosen another: each one is evaluated on its own and the strictest answer across them wins. A source the user can write (their own file, `ATOMIC_POLICY_URL`, the cache) can only add `ask`, `deny` and allowlist limits; it can never cancel the machine-wide file's `ask` or widen its MCP allowlist.

1. `<stateDir>/policy.json` (usually `~/.atomic-agent/policy.json`).
2. The machine-wide file: macOS `/Library/Application Support/AtomicAgent/policy.json`, Linux `/etc/atomic-agent/policy.json`, Windows `%ProgramData%\AtomicAgent\policy.json`.
3. A policy URL, fetched once at start with a 3 s timeout: the machine-wide file's `"url"` field if it has one (the user cannot unset it), else `ATOMIC_POLICY_URL`. A `url` in the user's own file is ignored. A good copy is cached in `<stateDir>/policy-cache.json`; when the fetch fails the cached copy for the same URL is used. A policy server that is down never stops the agent.

A missing optional local file is no policy. A malformed or unreadable local file refuses startup (and short-lived commands) with its source and reason. Unknown keys at the document, rule and allowlist levels are errors. An evaluator failure refuses the call. This fork tightens upstream's warning-only treatment of broken local files.

The upstream URL availability exception is retained explicitly: a failed fetch, invalid remote document or unusable cache falls back to the validated cached document for the same URL; without one, the source is reported as `unreachable`. Local file restrictions remain in force. Offline mode checks the destination before invoking the transport. Put mandatory restrictions in the machine-wide file rather than relying solely on a remote policy being reachable.

Policy delivery accepts HTTPS only, rejects user-info credentials and refuses redirects. A source report shows only the service origin; path/query/fragment and raw transport errors never enter `status.error` or `policy show`. The protected owner-only cache retains the exact URL solely to bind the cached policy to its source. Short-lived `skill install` and `policy show` use `loadLocalPolicy` and the validated cache; they do not refresh the network source. This is upstream's availability model, not a fresh remote-policy check: keep mandatory skill restrictions in the system file or start the operator runtime to fetch a new copy first.

## Format

```json
{
  "version": 1,
  "rules": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status*", "effect": "allow" },
    { "action": "shell", "resource": "rm -rf *", "effect": "deny", "note": "ask IT" },
    { "action": "webfetch", "resource": "https://*.internal.example.com/*", "effect": "deny" },
    { "action": "skill", "resource": "publish-*", "effect": "deny" },
    { "action": "mcp", "resource": "github/delete_*", "effect": "deny" }
  ],
  "mcpAllowlist": { "servers": ["github", "https://mcp.example.com/*"], "warnOnly": false }
}
```

- `action`: `shell` (the command line and each command in it, read like saved deny rules: past `sudo` / `env` / `FOO=1`, inside `bash -c`, `eval` and `find -exec`, and each also with its program reduced to its name, so `/bin/rm -rf x` matches `rm *`; a script piped into a shell, `printf … | sh`, matches every shell `deny` and `ask`), `edit` (file paths written, moved or trashed), `webfetch` (URLs, as given and as the fetch reads them: scheme and host lowercased, no user info or default port, at least a `/` path; plus the origin and the host alone, so `https://evil.com`, `evil.com` or `*.evil.com` covers every URL on that host), `websearch` (the query), `skill` (skill name), `mcp` (`<server>/<tool>`).
- `resource`: bounded wildcard comparison; `*` is any run of characters including `/`, `?` one UTF-16 code unit. Default `*`. No regular expression is compiled. Resources over 128 Ki characters, patterns over 4096 characters or a comparison exceeding one million steps are unreadable: deny/ask remains restrictive and allow cannot authorize that comparison.
- `effect`: inside one source the last matching rule wins, except that any matching `deny` wins wherever it sits. `allow` only cancels an earlier `ask` of the same source; it never cancels another source's `ask` and never skips a prompt the user's own settings would show.
- `mcpAllowlist.servers`: globs matched against a server's name, URL or stdio command line. With a list present, a server not on it stays down with the reason as its error. When several sources set a list, a server must be on each one. `warnOnly: true` logs it and lets it connect, for that list only. No list: every server may connect.
- `url` (machine-wide file only): the policy URL to fetch, see above.

## Where it is enforced

- Dispatch (`agent/dispatch/batch-gates.ts`, `refuseByOrgPolicy`) and direct registry invocation: a denied call is refused before hooks or tool execution. The registry retains the fork's independent egress and read boundaries.
- Approval gate (`ApprovalGate.setOrgPolicy`): a policy `deny` or `ask` acts like a saved rule of the user's, above them; `ask` prompts whatever the approval level or session grants say.
- Filesystem mutations outside home/workspace keep the fork's `other` approval category and still match `edit` policy, including Office writers and archive extraction.
- MCP (`McpManagerDeps.serverPolicy`): the allowlist, checked before every connect.
- `atag mcp-server` (`cli/mcp-server-command.ts`, `cli/mcp-server-bridge.ts`): loads and installs the policy itself, gives its gate `setOrgPolicy`, and refuses a denied call before it runs; a policy `ask` is refused there, since an MCP client cannot answer a prompt.
- Skills: `prepareSkillInstall` refuses a denied skill (`policy_denied`, HTTP 403); the registry and workspace discovery exclude it, and a previously selected workspace skill is checked again before use. A policy allow never activates an unconfirmed learned draft.
- Tool-child trust inventories retain metadata and pending counts, with skill bodies removed and loading refused; the fork's operator-only trust advice remains visible without exposing policy contents.
- Fusion and verification: workers share the dispatch/gate policy; worker candidate paths are also matched against the original project. Contract authorization and the actual rebased executor check shell denies (including stdin scripts) and explicit page/probe URLs. Detached shell jobs pass the same launch checks before becoming jobs. Fixed verification executors (including UI detectors) also check the command actually spawned. A host-retargeted file write is checked at its approved destination.

## Who manages the files

The operator edits the user policy outside agent tools. The system policy remains in the administrator-owned system location, separate from relocated user state. Its restrictions intersect with the user policy and URL/cache restrictions; moving user state cannot loosen the system file. Keep the system directory and file writable only by administrators.

The user policy, cache and system file are included in `getTrustConfigPaths` and `getStateSecretPaths`, alongside configuration and `serve-api.key`. They reach the same read-scope, shell secret scan and sandbox protection. Policy-file reads, replacement and deletion through agent tools are refused even at full trust; an approval card cannot override this refusal. The cache uses the configuration's owner-only atomic writer. `ATOMIC_AGENT_TOOL_CHILD` children (including MCP stdio servers) may bootstrap ordinary tools without policy. Supported launcher/CLI calls refuse child `policy show` and retain the inherited contexts when state is relocated. The marker and paths are indicative metadata, not process attestation: arbitrary same-account code can replace its environment. The administrator-owned system file is the mandatory authority, backed by OS permissions and isolation, not by those metadata values. There are no HTTP policy-management routes or config keys that disable policy; changing saved approval rules cannot cancel it.

These are application checks plus the existing optional OS sandbox, not isolation from arbitrary code running under the operator's OS account. Recognized shell paths receive the secret/state guard; computed paths have the same best-effort classifier limits as configuration and the serve key. Windows has no native command sandbox; requested Safe Mode refuses execution there. See [OS sandbox](../../docs/user/os-sandbox.md).

Point reads compare the exact canonical file. Listing or searching an ancestor (home, `/etc`, a filesystem root) is not a policy-file read; grep, glob and code-map exclude the protected files within those trees. Ancestor containment is retained for mutations that could replace or remove a policy. Canonical read decisions are scoped to one operation and are never retained after it.

When every protected file is definitely absent, read dispatch and recursive filters retain exact lexical protection of the reserved filenames but do not resolve every ordinary target. This preserves no-policy reads on volumes whose metadata is unavailable, including a missing Windows UNC share. Existing or unreadable protected files still require canonical identity; indeterminate mutations always refuse. Presence and canonical facts last for one operation only. This removes per-file realpath scans from ordinary no-policy recursive reads without weakening creation/replacement protection.

Diff refuses either protected input before reading; structural code search/rewrite exclude protected paths before launching ast-grep and discard protected returned matches. Canonical identities resolve symlinks, including missing final targets, with a 256-step limit; protected-entry ancestor scans also stop after 256 levels. An indeterminate path refuses the operation. Hard links are outside this path-based mechanism: a different hard-link name is not recognized as the same inode. Protect policy directories with administrator ownership and the existing OS sandbox where available.

## Not done yet

`ask` prompts for shell commands including ordinary commands classified safe, and for file writes, HTTP requests and gated MCP tools. `os.web.search` and read-only MCP tools honour `deny` but are not prompted on `ask`. The policy is read once per start. No cloud publishing of skills or MCP servers per organization, no admin UI.

MCP resource/prompt operations use the server selected by `args.server`: `<server>/resource.list`, `resource.read`, `prompt.list` or `prompt.get`. Dynamic tool and server names are case-sensitive, as their catalog identities are. Server names are assigned by the operator; a policy name is not an attestation of a server's executable or URL.

MCP allowlist entries are alternative selectors, retaining upstream semantics: a name-only entry authorizes any stdio command or remote endpoint configured by the operator under that name. It does not bind the name to a command/URL. To constrain transport identity, omit that name selector and list command-line or endpoint URL patterns instead. Entries within one list are OR; different sources' lists intersect. This selects configured identities, not authenticated code provenance.

Web patterns normalize scheme/host case, IDN to ASCII punycode, trailing host dots and default ports; paths remain case-sensitive. A bare host (`example.com`, `*.example.com`) covers every HTTP(S) scheme, port and path; `example.com:443` selects that effective port regardless of scheme. Use a URL form when scheme/port matters: `https://example.com` covers its default HTTPS origin, `https://example.com:8443/*` covers that origin/path pattern. MCP endpoint URL selectors receive the same URL canonicalization but remain endpoint patterns, without webfetch's origin-only shorthand. MCP tool/server names and stdio command text remain case-sensitive.

Path identity deliberately uses WHATWG URL serialization, rather than a server-specific resource identity: dot segments are resolved, but percent-encoded unreserved characters are not decoded (`/%61` differs from `/a`), percent-encoded separators remain encoded, and repeated slashes are not collapsed (`/a//b` differs from `/a/b`). Query ordering/encoding is not rewritten. Servers may map those spellings to the same content. Use a host/origin restriction when all such spellings must be covered; a path rule is an exact serialized spelling plus its explicit wildcards. The identity tests preserve this existing behavior; they are contract coverage, not a newly failing security regression.

Web fetch and HTTP request check every redirect destination before the next transport call, independently of approval mode. Crawl uses the same raw-page checks for links, robots and sitemaps; cached pages and their final URLs are checked again before use.

`os.http.request` applies both policy `ask` and `deny` to the initial URL and each redirect, even with `http.approvalMode: never`. `os.web.fetch` and crawl retain upstream's read-only semantics: policy `deny` is enforced at every hop; policy `ask` alone does not create a prompt for a raw/read-only fetch. Their independent URL-data and outside-content approval checks remain in place where an approval adapter is supplied. Use `deny` for a mandatory read restriction.

HTTP(S) destinations extracted by the fork's shell URL scanner (curl/wget and explicit Git URLs, including verification stdin) also receive `webfetch`; a shell allow never substitutes for that decision. Structured clone/fetch/pull resolve configured Git URLs (including `insteadOf`) using read-only Git queries before the network command. A web `ask` requires a fresh decision even after a command pin or full-trust grant. Recognized shell Git remotes, submodule add/update, LFS clone/fetch/pull/push, package-manager installs/publishing (npm/pnpm/yarn/bun/pip/uv/npx, including python -m pip), and SSH/SCP/netcat-family clients retain an unreadable destination when their complete transport/configuration is unknown. Any restrictive webfetch rule then denies or asks conservatively; a hostname is not treated as an inspected HTTP trace. Arbitrary programs, renamed clients, internal client redirects and runtime-computed calls remain outside this heuristic. Use shell/network egress restrictions for that perimeter.

`edit` is enforced on structured tools' actual mutation plans. Shell writes remain governed by shell rules, the fork's write/secret scanner and sandbox; `edit` is not a general filesystem monitor for arbitrary shell code.

Edit patterns and targets share canonical path normalization in the gate, dispatch and mutation plans: relative prefixes use that call's working directory, separators become `/`, and win32/darwin compare without case (including drive letters). Literal prefixes before a wildcard are canonicalized too. A leading wildcard remains a global wildcard, so `*.txt` still covers matching files at any depth. Canonicalization caches are scoped to one evaluation; they cannot retain an obsolete symlink decision between calls. Batch preflight passes the session working directory explicitly.

Mutation policy is checked on actual plans in `requireFsApproval`, before fanout grants or disabled ordinary approvals can settle the call. This covers Office, code rewrite and canvas without a tool-name list. Move/trash check both ends and real descendants; directory moves map source entries to their future destination. Inspection stops at 4096 entries or depth 64, does not recursively follow link entries, and falls back to a conservative restrictive-glob intersection if the tree cannot be inspected completely. Archives pass every listed entry separately, rather than treating the destination folder as every file it might contain. Git checkout obtains a complete read-only diff before approval when an edit rule or protected policy entry can intersect the repository; Git metadata (including shared worktree metadata) and staged paths are also checked. An uninspectable relevant checkout plan is refused. Video render checks its resolved output before ffmpeg; generated video checks the actual copy destination (the remote job has its separate paid-generation approval). Fusion checks all changed original-project paths before copying any of them; an `ask` holds promotion for the operator rather than opening an invisible worker prompt.

Remote Git verbs retain local edit checks: clone checks its new tree; fetch/push and remote configuration changes check metadata. Relevant policy makes pull fetch first with its independent URL/data approvals, pin FETCH_HEAD, inspect changed paths and approve local integration before merge/rebase. With no relevant policy, the ordinary pull command remains unchanged. Add/commit use selected unstaged/untracked files and the already staged index, including staged files outside commit paths; unreadable plans refuse. The fork's `git_remote` approval and remote-sync switch remain independent.

Git HTTP(S) URL decisions are separate: organization policy may require a fresh `http` decision or deny the destination; the fork's `http.urlDataGuard` independently requests `http_write` for data-bearing URLs (and first-site visits in strict mode). An organization allow/approval does not answer the data request. Resolved clone/fetch/pull URLs and explicit remote URLs are checked before transport; Git's own redirects remain inside its client and are outside this static trace.

## Tool-child bootstrap

Within the supported launcher flow, the launcher records the original state and system-policy paths in reserved, indicative child metadata; MCP server env overrides cannot replace them. Children intersect those local files with their own context and every validated cache, including when the delivery URL has been removed from the environment. They do not fetch. Child sources ignore allow rules, so combining contexts can only add restrictions; operator commands remain reserved. A malformed child cache refuses startup. A fresh remote policy must be persisted before parent startup succeeds, otherwise children could obtain an older, weaker snapshot. This deliberately tightens upstream’s cache-write availability exception; download failures still retain the documented cache fallback.

The installed policy records file identities (path, source kind and SHA-256), without rule bodies or delivery URLs, in reserved child metadata. A child retaining the supported marker/metadata validates and loads every inherited snapshot, including stricter intermediate contexts and their caches. These checks do not attest that arbitrary descendants retained that environment; the administrator-owned system file and OS isolation remain the independent mandatory boundary. Missing, unreadable or changed mandatory bytes refuse child startup; this also covers state hidden by an OS sandbox. Restart the parent after an operator changes those files. A missing policy at parent startup does not create a mandatory snapshot. At most 64 inherited files are accepted, and all pinned paths join the same protected-file inventories. Reads are shared within one load so validation and parsing use the same bytes. Configured subprocess environment cannot replace this metadata.

An embedded `atag mcp-server` keeps the tool-child marker. It may start without policy, and its own state remains configurable by the operator, but the parent's pinned local/system/cache restrictions also apply when that stdio instance uses another state directory. Policy asks are refused because this transport cannot collect an operator decision. The stdio integration test starts the actual command handler in a Node child and uses the SDK protocol transport for discovery and ordinary/deny/ask calls; it does not import the monolithic interactive CLI dispatcher.

Shell classification is bounded static analysis, not execution. Runtime definitions (`trap`, `hash`, alias/function definitions), recognized non-shell inline code and sed/awk external-command extensions are opaque to restrictive organization rules. Ordinary source/file/module loads and text transformations retain their literal resource identities. ANSI-C program quoting decodes supported printable ASCII hexadecimal/Unicode escapes; unsupported/control/locale-dependent encodings and localized `$"..."` program names are indeterminate. Ordinary dynamic arguments retain their known executable; an indeterminate program or opaque script matches deny/ask conservatively. This cannot infer arbitrary executable semantics. Skill policy selects skill discovery/loading/install by name; it is not an ACL on the skill directory's ordinary files. Use read-scope/filesystem permissions to restrict direct file access.

Personal saved rules retain the main-branch segment/prefix parser and conservative fallback for unknown interpreter options. One intentional tightening is shared with verification: recognized value-taking options are skipped before locating an actual stdin script, and an unrelated descriptor cannot be treated as the supplied verify payload. Thus `python3 -W error -` fed by a pipe, or verify reading `/dev/fd/3`, may match a personal deny/ask that main missed; this is independent of organization policy and never grants an allow. Organization policy uses a separate bounded conservative analysis; it does not turn unrelated personal rules into interpreter-wide denials. Interpreter flags are read only before the script/module operand or `--`; script arguments remain data. Ordinary file/module loading and sed/awk text transformations stay readable; recognized inline code and external-command DSL extensions are opaque for organization policy.

Inherited metadata is a launcher contract, not an unforgeable credential: arbitrary code under the same OS account can create a new environment or read operator-writable state. The system file is the authoritative mandatory source only when OS ownership prevents that account from replacing it. Use an administrator-owned system directory and OS isolation/egress controls; Windows has no native command sandbox in this fork. The launcher strips configured overrides. A best-effort dispatch guard additionally uses the shared wrapper analysis to refuse explicit assignments/unsets/export changes of the marker and policy metadata, plus recognized env/exec environment resets that would remove metadata present in the parent process, in visible argv; it cannot observe arbitrary code modifying its own environment and does not claim to do so.

Installing a policy loaded from a local file records its pins in the parent environment even when no tool-child marker was initially present. A visible environment reset that removes those pins is intentionally refused. Keep the inherited marker, state/system paths and file pins unchanged; remove individual unrelated variables with `env -u NAME` instead of `env -i` or `exec -c`. Explicitly replacing the reserved variables is also refused. The installed-file registry test exercises the real loader and `installPolicy`/`rememberPins`; reset enforcement itself predates this test, while the actionable refusal message is new.

Snapshot changes require restarting the parent, including a second instance rewriting the user file or cache with equivalent rules or merely new cache metadata. No semantic subset comparison or automatic reload is accepted: byte hashes must still match. A stricter update may therefore temporarily refuse a child too. Files hidden by OS isolation also refuse mandatory child bootstrap; an unreadable snapshot never becomes empty policy.

For organization policy only, the Git reader marks literal argv `key=value` selectors for `alias.*`, `core.sshCommand`, `core.pager`, `core.editor` and `sequence.editor` opaque, plus `--paginate`/`--exec-path` and visible GIT_CONFIG*, GIT_PAGER*, GIT_SSH* and GIT_EDITOR* prefixes. This is a narrow selector list, not all Git execution configuration; see the inventory below. Implicit aliases, repository/global config, hooks, SSH helpers and pager defaults are not resolved by this static analysis: even an ordinary Git verb can execute operator-installed code. Configure trusted Git state and OS egress separately. Ordinary make (including parallel builds and named targets) loads recipe files under the same file-code boundary as ordinary script loading; recipes are not read. Explicit make -E/--eval, makefile stream operands in -f/--file/--makefile (separate, attached or = forms), and SHELL/.SHELLFLAGS selectors are opaque; ordinary make and file-loaded recipes remain readable. Startup-capable Vim/GDB invocations are opaque (version/help probes remain readable). Tar remains readable for ordinary archiving but external-command/compressor/checkpoint options are opaque. Explicit shell initialization environment and rcfile options are opaque; ambient initialization files/environment are not introspected. These are command selectors, not a general filesystem/network monitor, and do not change personal saved-rule parsing.

## Static-analysis boundary

A readable script/module/file operand (including ordinary `source`) identifies a file to execute; the policy parser does not read that file's code or prove its effects. Inline snippets it recognizes are conservative, but Deno, Bun, Lua, Rscript, Julia and PyPy execution are not language analyzers here. Bun package-manager/network forms have their separate recognized network classification; that is not coverage of Bun programs. Renaming an interpreter or an executable also defeats name-based recognition. Use OS sandbox filesystem restrictions and project egress to confine effects; shell `edit` rules do not monitor arbitrary writes.

Script operands `/dev/stdin`, descriptor paths and process substitution are not ordinary file proof. Script operands are resolved lexically against the invocation cwd, including relative paths. Under /dev or /proc every path except a recognized stdin spelling is indeterminate, with /dev/null explicitly treated as an empty script (none) for Make and shell. Other interpreter/DSL /dev/null classifications remain conservative. Recognized stdin includes /dev/stdin, /dev/fd/0, /proc/{self,thread-self,pid}/fd/0 and /proc/{self,thread-self,pid}/task/{tid}/fd/0. A known stdin shell body supplied to verify is analyzed with the POSIX dialect; descriptor identities not tied to that payload and computed process-substitution script paths are opaque for restrictive organization rules. Literal script arguments that merely contain those spellings stay data. Symlink cycles, unknown canonical metadata and resolution beyond the bound refuse rather than guessing a target. The missing-policy optimization applies only to definite absence; it never ignores an existing or unreadable protected file. Reserved names stay protected on structured file operations. Without loaded policy and with every file absent, the extra organization shell scan is skipped; the fork's independent state-secret/write/read-scope guards still run.

Registry invocation passes a fresh explicit evaluation scope to the shell tool. Identical policy inspections and canonical facts are shared only inside that invocation, including the expanded command and its trusted shell wrapper; the concrete wrapper selector is still evaluated. A host-pinned executable gets its own inspection. A later invoke creates a new scope even when the caller reuses ToolContext; saved approval rules, grants and human decisions are not cached by this scope.

Interpreter option tables stop at a file/module or `--`. Recognized value options (for example Python `-W`, `-X`, `--check-hash-based-pycs`; Node preload/input/title/test options; Ruby encoding options) consume their attached or separate value. Unrecognized Python/Ruby long-option semantics remain opaque for organization policy. Node uses an explicit code-selector boundary; unknown long flags stay readable without stdin, while an unknown flag's separate following word cannot prove a script when stdin is present. Unknown short forms remain indeterminate. Known value-taking flags consume attached or separate values, including -r and -C. --run selects none. File/configuration contents and future code-bearing options are outside this static analysis. Option references: [Python command line](https://docs.python.org/3/using/cmdline.html) and [Node command line](https://nodejs.org/api/cli.html). Personal prefix matching remains unchanged; actual stdin/descriptor detection has the explicit tightening described above.

For a policy-relevant pull without an explicit branch, the planned fetch selects the current branch's configured merge source before pinning FETCH_HEAD. It does not choose the first ref from an unrestricted multi-ref fetch. Detached, missing, different-remote or multi-source tracking information is refused with a request to specify a branch; the unplanned no-policy pull retains main behavior.

Ordinary sed blocks and awk logical OR, regex alternation and quoted pipes stay readable; recognized sed execution extensions and awk system/external pipes remain opaque. These bounded selectors do not implement every extension of every sed/awk dialect. Node long operational flags stay readable before a file operand; eval/print (-e, -p, -pe and long forms), data-URL preloads and typed/interactive stdin remain opaque. The same selectors apply to inherited or visible NODE_OPTIONS (prefix assignment, env and export), including nested shell calls. Operational NODE_OPTIONS remains readable.

The shared shell family also recognizes rbash, mksh/lksh, ash/hush, yash/posh, oksh/loksh and sash. A literal BusyBox applet is analyzed as its selected program, including script input from a pipe; global BusyBox help/list/install flags are not applet selectors. Renamed binaries and runtime-selected applets remain outside literal name recognition.

## Less common families and follow-up

The fourth-review inventory uses synthetic argv only, never execution of the supplied fixtures. Literal classification means the selector was readable, not that its code or runtime effects were proved. Remaining coverage is tracked in [fork issue #266](https://github.com/Edo771977/Atomic-Agent/issues/266), linked from PR #246.

| Family | Current boundary and remaining limits |
| --- | --- |
| Environment wrappers | Known env flags, split-string and wrapper chains are read; visible reset/export changes receive the separate metadata guard. BSD/signal/argv0 variants, optional arguments and arbitrary changes inside code are not exhaustive. |
| Package managers | npm exec/npx call and known network selectors are read. dlx/corepack aliases, configuration, lifecycle hooks and downloaded programs are not inspected or attested. |
| Process utilities | Known prefix/options for setsid, ionice, chroot, strace, unshare, flock, script, su and parallel are read. Remote modes, unusual bundles/abbreviations and runtime-selected commands are not a complete process trace. |
| Node | Long operational flags remain ordinary; eval/print, data-URL preloads/reporters and input-type/interactive stdin are opaque, including inherited and visibly assigned NODE_OPTIONS. Organization option names normalize underscores to hyphens; values do not. Unknown long flags with a separate ambiguous word and supplied/possible stdin are indeterminate. NODE_PATH, startup/configuration and file/module preload contents are not read; new code-bearing options require follow-up. |
| Git | Only the literal selectors listed below are conservative. core.fsmonitor, diff.external, filters, GIT_EXTERNAL_DIFF/GIT_SEQUENCE_EDITOR, upload-pack, rebase exec, bisect run and difftool are not a complete execution trace. Clone and joined config-env have the limits below. |
| Tar and zip | Explicit tar program selectors, bundled/old-style I and zip -TT are opaque. TAR_OPTIONS, bsdtar variants, implicit testers/compressors, abbreviations and permutations are not exhaustively parsed. Ordinary archives remain file operations, not proof of program effects. |
| Editors and shell startup | Common vi/view/r/g/nvim names are conservative; literal shell/BusyBox names and explicit initialization selectors are recognized. Renamed/alternative binaries, ambient rc/plugins/profiles and help/version behavior across implementations are not attested. |
| sed and awk | Ordinary blocks, OR, regex alternation and strings differ from recognized execution/pipe extensions. gawk modules, other awk names/dialects, new extensions and file-loaded DSL code are not interpreted. |
| Perl, PHP and Python | Known option boundaries locate file/module/stdin. PHP r/B/R/E inline code is opaque. PERL5OPT, imports/startup hooks, file contents and uncommon/future interpreter options are not a language interpreter. |

A mandatory restriction on actual filesystem or network effects needs the administrator-owned policy plus OS permissions, available sandbox and egress controls. Shell selectors and inherited metadata do not isolate arbitrary same-account code. Windows has no native command sandbox in this fork. Prefer explicit structured tools when their complete mutation/network plans are needed; the policy itself never widens the fork's independent guards.

Sed is a bounded selector scan, not a complete GNU/BSD grammar. Extended/step/relative addresses (including 0~1e and 1,+1e), alternate regex address delimiters (for example \cXce), address flags I/M (including /x/Ie and /x/Me) and value-taking or platform-dependent options (including -l N and in-place suffix options) can change which operand is treated as the DSL; their semantics are not exhaustively modeled. Script files are not read. Script-stream recognition is lexical: symlinks or other aliases outside /dev and /proc, runtime-expanded paths, shell-internal cwd changes and descriptor/namespace identity are not resolved or attested. The known-fd0 convention lets verify associate the supplied payload; it is not OS proof of that descriptor's origin.

For a literal Node permission glob on a POSIX shell line, quote the value or the whole option: `node --allow-fs-read='/work/*' fixture.js` or `node '--allow-fs-write=/work/*' fixture.js`. On cmd use double quotes for the whole option. Quoting passes the pattern literally to Node. An unquoted wildcard in `--allow-fs-*` remains conservative for organization deny/ask rules: the shared lexer replaces dynamic words without preserving whether the source was only a wildcard or a different expansion. There is no permission-option exception to that shared boundary. The quoting regression test records the existing behavior (including the readable quoted forms), rather than claiming a newly failing code regression.

### Intentional personal stdin differences

Without any organization policy, source detection is intentionally stricter than main for awk/sed `-f -`, bash and POSIX dot loading stdin paths, value-taking PHP (-c/-d) and osascript (-l/-s) options before stdin, and pipes into mksh, ash or a literal BusyBox sh applet. The previously documented Python/Node/Perl/Ruby value-option cases and indeterminate verify descriptors also remain. This includes /proc/thread-self/fd/0, /proc/*/task/*/fd/0 and relative spellings that lexically resolve to /dev/stdin; these are intentional personal stdin differences, not main parity claims. Saved deny/ask rules can therefore match calls main missed; literal prefix matching is unchanged. `policy-personal-stream-boundary.test.ts` records these differences as conservation, not new behavioral fixes.

For organization policy, Node normalizes `_` to `-` only in long option names, before selector and value-option comparisons. This applies to ordinary argv and inherited/visible NODE_OPTIONS: `--experimental_loader` and `--input_type` have the same boundaries as their hyphen forms. Values, inline code and script/module filenames retain their original bytes. The personal parser keeps its established option tables and fallback; this organization change does not reinterpret saved personal rules.

Node distinguishes eval/print, data-URL code loads (including `--test-reporter` in separate or `=` form) and input-type/interactive with stdin from operational flags. Known value-taking flags consume their separate or attached value; the organization table includes cpu/heap profiler dir/name, heapsnapshot-signal, report-signal/dir/filename, trace-event-categories/file-pattern, watch-kill-signal, test-isolation/reporter-destination and diagnostic-dir, alongside the earlier selectors. If verification supplies stdin, or the shell line can feed it through a pipe/redirect, an unknown long option without `=` followed by a simple word is indeterminate: that word may be an option value instead of a script. Use a known option boundary, an attached `=value`, or `--` before an identified script to disambiguate. Flags after an identified script remain script arguments; an attached value is never reinterpreted as the script. Without stdin, unknown long operational flags remain readable. These are bounded static decisions, not inspection of file/configuration contents. Make's short groups, unique GNU prefixes and empty `/dev/null` script behavior are unchanged.

Shell stdin is assigned per parsed command, rather than inferred from characters anywhere in the line. The right side of a pipeline and a command's own fd0 input redirection (`<`, `0<`, heredoc or here-string) receive a stream. A pipe carrying the command's output, `||`, another command's operators, stderr redirection and quoted `|` or `<` do not supply its stdin. Nested `sh -c`, loops and subshells inherit their enclosing input; pipeline stages and trailing group input redirections retain their own routing. The analysis is bounded and does not attest runtime descriptor consumption or inspect input files. Supplied verification shell bodies retain their visible NODE_OPTIONS and are analyzed without treating the script payload itself as every child command's stdin.

Known Node booleans include trace-gc, use-system-ca, jitless, prof, experimental-transform-types and test-force-exit. Known boolean names also accept their `--no-` negation, including `--no-experimental-detect-module`; option-name underscore normalization still applies. With real stdin, a future boolean unknown to this table followed by a simple word remains ambiguous, including when supplied through NODE_OPTIONS: the word could instead be its option value. Use `--` before the script or the option's `=value` form when supported to make the boundary explicit. Without incoming stdin, an output pipeline alone does not introduce this ambiguity. Code selectors and data-URL loaders remain opaque, and the personal-rule option tables are unchanged.

The organization reader snapshots descriptor provenance per command and frame. A literal `exec` without a program retains its input redirections and descriptor duplications for later commands and nested shells in that frame. Unknown descriptors are treated as streams. Subshell frames do not export these changes; persistent changes in conditional/brace frames are conservatively unreadable when their execution or restoration cannot prove the later descriptor. This is static provenance, not runtime descriptor attestation. Pipeline input survives newline, blank lines and comments after the pipe. Quoting, escaping and command position distinguish actual group/keyword syntax from literal `}`, `done`, `fi` and `esac` words.

The supported nested-shell context carries fd0. Nonzero descriptors inherited across a shell boundary are not attested; they remain unknown at that boundary, including an outer fd3 opened on /dev/null and then duplicated inside sh -c. The fork's approval gate independently reanalyzes flattened command metadata and must retain that conservative decision. To identify an empty input at that boundary, redirect fd0 to /dev/null explicitly in the nested call. Conservation tests cover deny/ask at both levels; they already pass before this documentation and are not new RED claims.

Literal assignment prefixes and command/builtin wrappers around exec retain the same descriptor boundary. Exec with options that leave its program boundary uncertain is unreadable. Exec in a pipeline is also unreadable because the last pipeline stage's persistent effects depend on shell settings; the reader does not assume those effects disappear. An eval body that persistently changes descriptors is held rather than treating it as a child shell with no effect on the caller. Ordinary parsed eval bodies retain their existing analysis.

Both command-substitution syntaxes inherit the input reference of their containing segment, including trailing input redirections and enclosing groups. Bash-like process-substitution producers inherit that reference too; a `>(...)` consumer receives the substitution's output stream as stdin. Other shell implementations may reject process substitution; the reader does not enable it or execute it. Explicit file/pipe inputs supersede inherited input. A statically identified `/dev/null` input remains empty through supported descriptor duplication and shell/substitution boundaries, even if verify supplied other stdin. A subsequent real file or pipeline supersedes the empty source. Dynamic paths, descriptor identity, file contents and arbitrary aliases remain unproven.

Incomplete or ambiguous syntax is held conservatively: a dangling input redirect or pipe, unmatched frame, or uncertain persistent descriptor makes the affected operation unreadable for organization deny/ask, holding the call. The fallback concerns the unparsed line/operation; it does not infer input for unrelated parsed commands from quoted metacharacters or an operator elsewhere in the whole multi-line string. Length/token, nesting and input-reference traversal bounds remain fail-closed. Personal saved-rule tables and prefix matching are unchanged.

Node option arity was checked against the official Node **25.9.0** binary's `--help`; `--max-old-space-size` and `--stack-size` are V8 value options verified with `--v8-options` because they are absent from the main help. TLS cipher-list/keylog, openssl-config, icu-data-dir, title, redirect-warnings, unhandled-rejections, max-old-space-size, stack-size and localstorage-file consume a separate or attached value. TLS min-v1.0/min-v1.1/min-v1.2/min-v1.3 and max-v1.2/max-v1.3 are booleans. These organization-only arity facts do not inspect configuration or script files and do not redefine the personal parser.
