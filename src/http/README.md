## Ownership and dependencies

The HTTP server owns request handling and connection cancellation; route modules translate transport payloads into runtime operations. Session routes use the existing turn/steering contract, and webhook routes materialize durable tasks; the persistent-webhook session map moves a corrupt file aside to `.corrupt-<time>` instead of silently overwriting it. Runtime owns session execution, task storage and approval policy; routes must retain authentication and error mapping. MCP routes use [shared server-config commands](../config/mcp-server-commands.ts) and manager operations, independently of TUI.

A request body that is valid JSON but not an object (`null`, an array, a scalar) is `400` on `POST /v1/chat/completions` (issue #74).

Session ids from clients (issue #74, [session-id.ts](../session/session-id.ts)): a `session_id` body field or `X-Atomic-Session-Id` header, an AG-UI `threadId` and the `{id}` of every `/api/sessions/{id}` route may be any id the store holds, imported chats' `claude-code:<id>` and the like included, but not empty, longer than 256 characters, with `/` or `\`, with `..` or a leading `.`, or with control characters. Such an id is `400` (`param` `session_id`, or `id` on the session routes) before a handler runs. An id never names a file as it is: the trace is `<traces>/<sessionFileName(id)>.ndjson` (unchanged for `[A-Za-z0-9._-]` ids, `~xx` escapes otherwise, so no `:` reaches a Windows path); a trace an older build wrote under the raw id is still read and appended to.

[Compaction routes](route-compaction.ts) expose `POST /api/sessions/{id}/compact` and `GET /api/sessions/{id}/compaction`. The POST waits for runtime completion and cancels only its operation on disconnect. See [the shared contract](../runtime/docs/compaction.md). With `x-atomic-extensions: 1`, a chat stream also carries `compaction_started`, `compaction_progress`, `compaction_completed`, `compaction_failed` and `history_trimmed` frames ([mapping](stream-maintenance-frames.ts)): counts and statuses only. It also carries `usage_updated` (ATO-569): the session's spend so far, priced / unpriced / local / plan call counts, and the account's rate-limit windows (used percent, remaining, reset time); the same snapshot is persisted as `sessionUsage` on `GET /api/sessions/{id}`. With `llm.costTracking.showInStatusBar` on or `llm.costTracking.dailyLimitUsd` set, the frame also carries `today: { day, cost_usd, priced_calls, unpriced_calls, limit_usd? }` (ATO-649): what every session spent today, live only and never persisted with a session. `today` is sent only when a configured cloud link has a known price. Once `cost_usd` reaches `limit_usd`, paid cloud links are refused before the request is sent: with `llm.costTracking.onDailyLimit: "stop"` (default) the turn fails with "Daily cloud limit reached: …" (failure cause `daily_limit_reached`); with `"local"` the fallback chain moves on to the local link and a `provider_switched` frame says so. A `tool_disabled` frame (ATO-1417) says a tool was left out of the turn's requests because the server refused its JSON schema: `tool`, `reason` (`schema_rejected`), `step_index` and the chat sentence in `notice`, once per tool per turn. A `project_instructions` frame (ATO-42) says the local prompt carried the chat's project instructions: `name`, the full text's `tokens`, `truncated` when the block was cut to `max_tokens` (1500), once per turn.

Skills and capabilities accept optional `sessionId` for the selected cloud
workspace. `workspace=true` without an ID previews a new, unsaved session in
the server's startup directory; it accepts no client filesystem path. Calls
without either query retain the legacy registry. Cloud skill lists include
disabled reasons, source paths and a content fingerprint for refreshing open
details. These are operator views; disabled entries are excluded from model
capabilities and dispatch still enforces the current policy.

[Turn phases](stream-turn-phase.ts) (ATO-1027): with `x-atomic-extensions: 1`, a chat stream carries `event: turn_phase` on every change of what the turn is doing, `{ object: "atomic.turn_phase", session_id, phase, step_index?, tool?, phase_elapsed_ms, turn_elapsed_ms, progress? }`. `phase` is `starting`, `loading_model` (the local server answered "Loading model"), `waiting_provider`, `processing_prompt` (`progress: { processed, total, cached, fraction }` when llama-server reports prompt progress), `thinking`, `generating`, `running_tool` (`tool` names the call) or `compacting`. A host counts the seconds itself from `phase_elapsed_ms`. Once per turn, when a local model has produced nothing 45 s after the turn began, `event: slow_first_token` carries `{ object: "atomic.slow_first_token", session_id, waited_ms, phase?, model_id?, lighter_model?: { id, name, file_size_gb, downloaded }, cloud_available }` ([hint](slow-first-token-hint.ts)): what the host may offer instead. Nothing is switched. After every model completion, `event: step_speed` carries `{ object: "atomic.step_speed", session_id, step_index?, prompt_tokens, cached_tokens, prefill_ms, decode_ms, decode_tokens_per_second, draft_tokens?, draft_accepted_tokens? }` (ATO-631): whether a slow step was re-reading its prompt or writing slowly. `decode_tokens_per_second` is `null` and the ms fields `0` for a provider that reports no timings (cloud APIs); the draft fields appear only under speculative decoding.

Next-step suggestion (ATO-1093): `GET /api/sessions` rows and `GET /api/sessions/{id}` carry `nextStep`, the suggested next message after the last answered turn, or `null` (setting `tui.nextStepSuggestions` off, nothing stored, a turn running, or a later turn made it stale). `GET /api/sessions/{id}/next-step` answers `200 { sessionId, suggestion }` with the same value (`404` for an unknown id). With the switch off every route serves `null`, also for a suggestion stored while it was on, and `GET /api/sessions/{id}` leaves `metadata.nextStep` out. Read-only; see [session-next-step.ts](../session/session-next-step.ts).

Step labels in history (ATO-1382): `GET /api/sessions/{id}` adds `done_line` to every `assistant_tool_call` row, built from the stored name and args with the same `describeToolCall` the live `tool_progress.done_line` uses, so a reopened chat reads its steps exactly as they read while the turn ran. It is computed per answer and never stored.

Searching past chats (ATO-1149, [session-search.ts](../session/session-search.ts)): `GET /api/sessions/search?q=…` finds words in the user messages and closing replies of stored sessions with SQLite FTS5 (tool calls and tool output are not indexed). It covers the current working directory, or every folder with `scope=all`; `limit` defaults to 10, max 25, at most 3 hits per session. The answer is `200 { query, hits, pending }`: each hit carries `sessionId`, `title`, `workingDir`, `updatedAt`, `line` (index into the session's chat lines), `kind`, `source` (`chat`, `telegram`, `discord`, `webhook`, `task`, `imported`, for a label) and a `snippet` with the matched words in `«` `»`. Task sessions rank below an interactive chat that matches as well; incognito chats, Fusion workers and sessions stamped `metadata.internal` / `metadata.subagent` are never indexed. The index is filled at search time, not on every write: each search reindexes up to 500 sessions changed since they were last indexed, newest first (transcripts read without the write lock, the index written 25 sessions per transaction), and `pending` counts the rest. `400` for an empty or over-500-character `q`, `503` when the index cannot be created.

[Export route](route-session-export.ts) (ATO-1054): `GET /api/sessions/{id}/export?format=markdown|html|docx[&tools=0]` answers `{ id, format, filename, mimeType, encoding, content }` (`utf8` text, or `base64` for DOCX), built by [exportChat](../session/chat-export-render.ts). PDF is printed by the client from the `html` format. `400` for another format, `404` for an unknown id, `409 incognito_session` for an incognito chat (ATO-586); the CLI's `export <id>` refuses one too.

[Archive route](route-session-archived.ts) (ATO-1150): `POST /api/sessions/{id}/archived` with `{ archived: true | false }` (`400` for anything but a boolean, `404` for an unknown id, `409 incognito_session` for an incognito chat, which keeps nothing durable) archives or unarchives a chat through `SessionStore.setSessionArchived`: `metadata.archived: true`, or no `archived` key once unarchived, stamped with `metadata.archivedSetAt` so a copy read before the change (a turn still running) cannot write the old flag back. `GET /api/sessions` lists `archived` on every row; the desktop's sidebar draws archived chats in their own section and the terminal's rail and session picker leave them out. `updatedAt` is not touched.

[Rename route](route-session-title.ts): `PATCH /api/sessions/{id}` with `{ title }` (trimmed, 1-120 characters, one line; `400` otherwise, `404` for an unknown id) stores the operator's title through `SessionStore.renameSession`. The title is stamped as user-set, so the session namer never replaces it and a turn already running cannot write an older copy back over it.

[Plain completion route](route-complete.ts): `POST /api/complete` with `{ prompt, system?, max_tokens? }` answers `{ text }` from one request to the current model through `runtime.completePlain` (`../runtime/plain-complete.ts`): no tools, no turn, nothing written to a session, its own `complete:` fallback partition, `max_tokens` clamped to 4096 (default 1024), a 60 s deadline. `400` bad body, `501` no plain call in this runtime, `502` model failure or empty answer, `504` deadline. The desktop Studio's "Improve prompt" uses it when present. While any `projects.constraints` entry exists the call is refused (fail closed): its `complete:api` partition names no session, so the provider policy lets no provider serve it ([session policy](../runtime/session-provider-policy.ts)).

`usage` on `/v1/chat/completions` (the body, the extensions-only `usage` frame) reports the tokens every LLM call of the turn reported, summed by the runtime's turn usage meter (`RunTurnResult.usage`; a local llama-server counts by its timings), and zeros when none did. A streaming request with `stream_options.include_usage: true` gets OpenAI's extra chunk before `data: [DONE]`: empty `choices` and the turn's `usage`; every chunk before it then carries `usage: null`, as OpenAI's do ([builders](openai-chunks.ts)).

[Approval route](route-approval.ts): `POST /api/approval/resolve` with `{ approvalId, decision }` takes `allow-once`, `deny` (aliases `approve`, `reject`) and `allow-in-chat`. `allow-in-chat` approves and records the gate's shape grant for the request's own session: later shell calls of the same binary (`commandShape`, `git`) in that chat run unasked (only calls that run that binary alone: a compound line such as `git status && …`, a pathed `./git`, a shell or a wrapper such as `env` has no shape and still asks), other binaries and other chats still ask, and nothing persists. A request without a shape gets `400` and stays pending. `allow-always` (ATO-1142) approves and saves an allow rule in the approval rules file, built by the gate from the pending request and scoped to its project; the response adds `grant: "always"` and the saved `rule`, and a request where `canGrantAlways` is false gets `400` and stays pending. Each `approval_request` on `GET /api/events` carries `canAlways` and, when true, `alwaysLabel` (`Always allow "git status" in this project`), so a client draws the button only where it works. `GET /api/capabilities` lists the accepted decisions as `agent.approvalDecisions`; a client offers "allow in this chat" only when it is listed.

[Question route](route-question.ts) (ATO-489): a question the agent asks with `ask_user` arrives on `GET /api/events` as an `approval_request` with `category: "user_question"` and a `question` object (`prompt`, `options` of `{ label, description? }`, `multiSelect`, `allowOther`), replayed on reconnect like any pending approval. Answer it with `POST /api/question/answer` `{ approvalId, selected?: labels or 0-based indexes, other?: string }`, or `{ approvalId, skip: true }`. An answer the question does not take is `400` and the question stays open; `/api/approval/resolve` refuses to approve one. `agent.questions: true` on `GET /api/capabilities` says the route exists. A chat client is offered `ask_user` only when its `POST /v1/chat/completions` sends `X-Atomic-Questions: 1` together with `X-Atomic-Extensions: 1`; without it (today's desktop app, which has no question card until ATO-1502) the tool is left out of its turns. The TUI, the CLI and Telegram always get it.

[Project route](route-project.ts) (issue #39): a fusion project's gate (brief, plan or a finished milestone) as the [ProjectGateView](../session/project-gate-view.ts) the cards draw. `GET /api/project?session=<id>` returns `{ session_id, view }` (`404` without a project). `POST /api/project/decision` takes `{ session, gate, version, verdict, edits? }`: `gate` and `version` as the view gave them, `verdict` one of `view.allowedVerdicts`, `edits.rows[]` `{ taskId, worker?, reviewer? (null: no review) }` at the plan gate, `edits.decisionStatus` (`{ <decisionId>: "active" | "deferred" | "informational" }`, issue #112, with `edit` at the plan gate; the view's optional `decisions[]` carries `{ id, text, status, citedBy }`), `edits.note` (at most 2000 characters) the person's correction with `edit` at a milestone, `edits.brief` (`what`, `users`, `how`, `successCriteria`: each text or `{ id, text }`) at the brief gate. From issue #54 the view adds `hints[]` (one-line advice to show as is: no reviewers configured, only one worker available, no other team member reachable now), `plan.editable` (false: no row offers a choice, so hide or disable "edit rows") and, per row, `local?` (a local worker priced at $0, shown as "$0.00 (local)"); the [sidecar guide](../sidecar/README.md) lists every field. From issue #40 the view adds `brief.criteria[]` (`{ id, text }`; `brief.successCriteria` stays the texts) and, per milestone, `attachments[]` (`{ path, caption, criteria? }`: screenshots of its result in the run's shots folder under the state dir) and `criteriaFacts[]` (`{ id, state: passed | failed | unverified, why? }`); a client shows the caption and path, and reads an image only through its own safe file read. A malformed body or a verdict the gate does not take is `400`, no project or session `404`, a stale version or another gate `409` (`stale-version`, `wrong-gate`), a running turn `409` (`turn-running`), an open review `409` (`review-open`, issue #98, with the blocks), a hard cap `422` (`over-cap`); refusals carry `error.code` and the current `view`. A successful decision answers `{ session_id, view, continue_message }`: when `continue_message` is not null, send it as the next chat message so the director goes on: the runtime records the decision but never continues the work by itself. A chat runs the project flow (the `project.*` tools and their guidance) only when its first `POST /v1/chat/completions` sends `X-Atomic-Project: 1` with `X-Atomic-Extensions: 1` (`agent.project: true` on `GET /api/capabilities`); the answer is the session's for good (`metadata.projectGates`), and without it the session has no gates and the fan-out asks as before. The runtime (`AgentRuntime.projectDecision`) owns every rule; the route only validates and maps. `GET /api/events` forwards `event: project_gate` `{ session_id, view }` (open gates replayed on connect; the runtime emits one for every decision and every turn that moves the gate; keep the newest `version`), and a chat stream with extensions carries the same view as `event: project_gate` (`object: "atomic.project_gate"`). On a network server a session whose folder lacks `serve` in `allowedEgress` gets `403` and no frames. `POST /api/project/backlog` `{ session, item, state, expectedFingerprint? }` (issue #111) is the person's call on a backlog item (`promoted`, `dropped`, or `open` to take one back) through `AgentRuntime.projectBacklogDecision`: between turns only (`409` `turn-running`), no gate moves; it answers `{ session_id, view }`, a malformed body `400`, no project `404`, an unknown item `400` (`invalid`).

[Project lessons](route-project-lessons.ts) (issue #125)

- `GET /api/project/lessons?session=<id>` returns `{ session_id, panel }` for a chat bound to a saved project. During a turn, the panel remains readable and `panel.blocked` explains why choices must wait.
- `POST /api/project/lessons` requires `atag serve` with an API key and the usual bearer authentication. Send `{ session, lesson, action, fingerprint }` with `approve`, `retire`, or `reopen` and the displayed full SHA-256 fingerprint (`hash` in the row). Include `orphaned: true` to reopen the recorded choice for a missing or invalid file. Approval requires `status: active`. Success returns `{ session_id, panel, notice, view? }`, where `notice` confirms the choice and `view`, when available, is the updated project gate view including any `lessonCoverage`. The HTTP event stream also publishes that view as `project_gate` for the selected session. Clients outside that stream, including a separate TUI process, can refresh their project and lesson views after an external choice. A choice starts no turn.
- `panel` includes `rows`, `problems`, `sectionLimit`, and optional `blocked` text. Each file row includes `promptEnds` per section, with `{ standard, planning }` offsets in UTF-16 code units into the full section for the standard and shared planning prompt cuts. Orphaned rows have no prompt cuts. Skipped file names and reasons show invisible characters as printable Unicode escapes.
- Errors use `{ error, panel? }` without `session_id`. The route can return `400` for malformed inputs or an `invalid` choice, `404 no-project` for an unavailable project (unknown sessions also return `404`), `409 stale-view` with a refreshed panel for a changed fingerprint or record sequence, `409 turn-running`, `409 incognito`, `503 busy` for a locked record, and `500 io` for a write failure. The server applies the shared bearer check before the handler. Network calls follow the project egress policy and can return `403 folder_restricted`.

A milestone’s optional `criteriaBasisSummary` reports totals by basis (`check`, `vision`, `person`, `unrecorded`). Its optional `withReservations` gives the subset of each total that passed with reservations. Missing subset counts are zero. Subtract each subset from its total to display separate counts such as “5 measured, 1 measured with reservations”. The individual fact gives its reason in `reservation`.

A successful milestone decision may include `view.lessonProposalHint` for a bound project. The optional guidance accompanies `continue_message` after a correction or approval over review. At project completion it may supply a final continuation if a milestone was corrected, failed, or approved over review. A routine completion returns null. The continuation is runtime-generated text.

`GET /api/project?session=<id>&evidence=1` may add `view.milestones[].evidenceReceipts` to the active milestone. The object carries `valid`, `unsigned` and `problems` (counts), `folder?` (the project folder), `partial?: true` (a bounded scan) and `archiveUnavailable?: true` (the archive could not be read). The field is absent in incognito, outside a milestone gate, or when a complete scan finds no matching receipts. Verification reads public keys only and reuses cached results for unchanged rows. Ordinary GETs, decision and backlog responses, and `project_gate` SSE frames omit the summary.

Desktop should request `evidence=1` when it displays the milestone card, including when a `project_gate` event opens or updates that card.

Each entry in `view.backlog.items` and `view.backlog.stale` includes a `fingerprint`. Send the fingerprint from the displayed entry as `expectedFingerprint` to bind the decision to that view. The value must be a 64-character hexadecimal string. Malformed values get `400`. If the displayed content, status, plan adoption or stale decision has changed, the route returns `409` with `error.code: "stale-view"` and the current `view`. Show that view and ask the person to decide again. Omitting the field is supported for older clients.

[Local model recheck](route-local-model-recheck.ts) (ATO-873): `POST /api/local-model/recheck`, no body, reads `localModels.url` fresh from the config file, probes it the way saving it does and answers `{ url, verdict, ok, message, portHint }` (`ok`, `loading`, `ollama`, `atomic_chat`, `openai_compat`, `key_rejected`, `not_model_server`, `unreachable`). It never takes a URL from the client and writes nothing. A failed step's and turn's `error` frame carries `code` and plain `advice` for a local server ([fields](failure-reason-frame.ts)): `local_server_not_found` (404/405 at `localModels.url`, the case for a Reconnect button), `local_provider_not_found` (the same at another address), `local_context_exceeded`, `local_tools_unsupported` (a 400 saying the server takes no tool calls: llama-server without `--jinja`, an Ollama model without tool support), `local_request_invalid`, `atomic_chat_key_required` (the `atomic-chat` provider answered 401/403: its API key protection is on, ATO-1274; not reported to Sentry), `local_port_taken` (the managed engine's address answered 401 while our engine's process is not there: another program holds the port, ATO-1277); `local_engine_down` wins over them, and so does `atomic_chat_not_running` (ATO-1278: the Atomic Chat app refused the connection past a short start grace; the user opens it). A per-folder constraint refusal wins over all of them: `code` is `ATOMIC_AGENT_PROVIDER_NOT_ALLOWED` or `ATOMIC_AGENT_EGRESS_NOT_ALLOWED` and `advice` the sentence and hint every surface shows ([constraint-refusal.ts](../runtime/constraint-refusal.ts)); the sidecar's `session_failed` carries the same two fields.

MCP browser sign-in ([route-mcp.ts](route-mcp.ts), flow in [mcp-oauth-flow.ts](../mcp/mcp-oauth-flow.ts)): `POST /api/mcp/servers/{name}/auth/start` answers `{ state: "pending", authUrl }` (the client opens `authUrl`; the agent never opens a browser) or `{ state: "signed_in" }` when a saved refresh token was enough. `GET /api/mcp/servers/{name}/auth` answers `{ state: "signed_out" | "pending" | "signed_in", error? }`; `POST .../auth/signout` deletes the saved sign-in, reconnects the server and answers `{ state: "signed_out" }`. [Fusion team route](route-fusion-team.ts) (issue #71): `GET /api/fusion/team[?session=<id>]` returns `{ configured, mode, directors, workers, reviewers, review, restriction, chat? }`. Each member is `{ ref, providerId, model, usable, reason?, why? }`: `reason` is `folder` (the chat's folder restriction refuses the provider), `unreachable` (not registered, or a subscription CLI known to be signed out or missing) or, for a reviewer, `cli-tools` (a Codex CLI, whose own read-only shell can read outside a restricted chat's folder), `why` a line to show as is. `review` is the config's own answer (`on`/`off`); `chat` (with `session`, `404` for an unknown one) holds the chat's stamped `director`, `worker` and `reviewer` (`"none"`: no review). [Projects routes](route-projects.ts) (issue #109): the fusion projects this machine knows, for a client's projects list; each answer carries `schema: 1`. `GET /api/projects` returns `{ schema, projects, registry_problem }` with the `atomic-agent projects list --json` rows (a missing, damaged or unsupported folder is a row with its `problem`; `registry_problem` when the list file cannot be read, left as it is). `POST /api/projects/forget` `{ folder }` (absolute) answers `{ schema, folder, forgotten }`: off the list, the folder's files untouched. `POST /api/projects/resume` `{ folder }` (absolute, one the list names) is `project resume`: the newest chat on the folder's project or a new one bound to it, `{ schema, folder, name, session_id, created, view }`; a folder not listed is `404 not-listed`, a project that cannot be opened `422 project-unavailable` with the reason. [Skill routes](route-skills.ts): `POST /api/skills/install` with `{ sourcePath, source?, force?, confirm?, acknowledgeRisk? }` security-scans the folder before copying ([install scan](../skills/docs/skill-format.md#install-security-scan)). Auth on the network (ATO-1126): the bearer token is compared in constant time ([secret-equal.ts](secret-equal.ts)); an address that sends 10 wrong or missing tokens within a minute gets `429 auth_throttled` with `retry-after` for a minute ([auth-throttle.ts](auth-throttle.ts)); loopback callers are never throttled. `serve` refuses a network host without a key (ATO-760) or with a key shorter than 16 characters, and on `0.0.0.0` / `::` prints the LAN addresses other devices reach it at. On a network address, sessions of a constrained folder without `serve` in `allowedEgress` are refused ([serve egress](serve-egress.ts), [policy](../llm/docs/provider-policy.md#egress-allowedegress)).

The main listener authenticates every `/api/*` and `/v1/*` route, including model discovery, webhooks and both reads and writes of project choices. A missing or invalid key returns `401` on any host. Non-loopback callers can receive `429 auth_throttled` after repeated failures. The only public routes on this listener are `GET /health` for liveness and `GET /panel` plus `GET /panel/app.js` for the static panel. The separate tunnel listener authenticates provider deliveries at `POST /webhooks/{name}` using the binding's secret or signature. The explicit `unauthenticated: true` server option is used by the test harness.

Loopback `serve` generates and reuses `<stateDir>/serve-api.key` with mode `0600` on POSIX and the shared credential ACL routine on Windows. Serve refuses to use the generated key file if it cannot restrict access. Read the file from your own account. To rotate the generated key, stop the servers using that state directory, remove that file, restart, and give the new key to clients. Send it in `Authorization: Bearer <key>` or `x-api-key`.

For Desktop and other launchers, prefer `--api-key-stdin`. Send one newline-terminated key over a pipe. Serve validates it, closes stdin and starts its runtime afterward. Use a key of at least 16 printable ASCII characters without spaces. The input limit is 4096 bytes and the read times out after 10 seconds. This option is exclusive with `--api-key-file`, `--api-key` and `ATOMIC_AGENT_API_KEY`.

An owner-only file supplied with `--api-key-file <path>` remains on disk by default, including throughout runtime bootstrap. With `--api-key-file-delete`, serve unlinks the file after successful validation and before starting the runtime. The file is still present from its creation until it is read and removed, and remains if the launcher or serve exits before removal. Use a file you intend to discard and directories you control. The final component must be a regular, single-link file. Ancestor directories may be symlinks. On Windows the ACL check uses the path while the key is read from an open handle, so path replacement during the check can race it.

The legacy environment entry still works, and Linux retains it in the process's original environment visible through `/proc/<pid>/environ` to permitted readers. The key is a local defense against accidental exposure and ordinary agent tool calls. The optional [OS sandbox](../../docs/user/os-sandbox.md) also hides agent state from covered child commands and isolates their view of host processes on Linux. A process running as the same OS user outside those controls can read files and process information available to that user. Approval level 5 is full trust and automatically approves state-secret reads. At level 5 the serve key does not protect against actions of the agent. The shell classifier detects the literal file name even in relative paths and search arguments. Shell recognition is best-effort. It recognizes basename glob and brace selectors, procfs process-data paths (including recursive process-directory reads with grep or find), and simple relative reads after literal cd or pushd. Recognizable process argument and environment displays require state-secret approval regardless of how serve received its key. It does not evaluate concatenated variables, ANSI-C quoting or scripts.

Rolling a chat back to any question with its files, and forking it (ATO-1056, ATO-1058, [route-session-rewind.ts](route-session-rewind.ts)): `GET /api/sessions/{id}/rewind-points` lists the questions it can go back to (`turnIndex`, `priorQuestions`, `text`, `at`, newest first). `POST /api/sessions/{id}/rewind/preview` and `POST /api/sessions/{id}/rewind` take `{ priorQuestions, expectText }`, the question by its position (questions before it, steers not counted) and its text; a different stored question answers `409 point_mismatch` and nothing changes. The preview answers `{ turnIndex, text, removed: { questions, replies }, files: [{ path, action: "restore" | "delete" }], notRestorable: [{ path, reason }], incomplete, skipped, uncovered: [{ tool, count }] }` (it takes the same optional `skip` as the rollback, with the same `400`s, and leaves those files out), plus `planHash`: the files that will really change (a saved copy that matches the disk is left out; an entry with `error` is a file that could not be checked now, which the rollback reports in `failed` without touching it, issue #80: any stat or read error other than ENOENT/ENOTDIR, ELOOP and ENAMETOOLONG, such as EACCES, EPERM, EBUSY or EIO; a symlink loop is `notRestorable` `not_a_file` and a name too long `unreadable`; a file the agent created is removed even when it cannot be read; a file to restore whose saved copy no longer matches its recorded sha256 is listed with `error: "saved copy is damaged"`, issue #87: the plan reads and checks the copy of each file it will restore, and the rollback checks it again right before writing, so a damaged copy is never written and is reported in `failed`, answering `409 restore_failed` with the chat and copies kept; `skip` or `acceptFailed` get past it), the ones changed without a copy (`too_large`, `binary`, `not_a_file`, `unreadable`) and `move_source_not_restored`, a file the agent moved there from a source this rollback does not put back (no copy kept, binary, too large or skipped), which stays where it is since deleting it would lose the only copy (issue #87; recorded from now on as `movedFrom` at capture, so copies taken earlier are not paired), whether older copies were dropped to stay in bounds, and the shell, git, archive and Fusion calls whose changes stay. The rollback puts the files back first, then removes that question and everything after it, and answers `{ id, text, restored, deleted, failed, notRestorable, incomplete }` once every planned file went back; when any file fails it answers `409 restore_failed` with `partial: true`, `restored`, `deleted`, `failed`, `notRestorable` and `incomplete` (unlike the other 409s, something changed: the files listed went back), leaves the chat uncut and keeps the saved copies (issue #77), so the same request can be sent again. A retry plans again against the disk: files already back match their copy and are not touched, but a file the person edited between attempts is overwritten with its saved copy, so a client should show the preview again before retrying; and the chat is cut and the copies dropped only on the attempt where nothing fails. A failure that repeats (a folder replaced by a file, a file an editor holds open) is not told apart from a transient one: `acceptFailed: true` in the body rolls back anyway, putting back what it can, cutting the chat, dropping the copies and answering 200 with `failed` listing the files left as they are now; a non-boolean `acceptFailed` is `400`. `skip` (optional, an array of at most 1000 non-empty paths; anything else is `400` on `skip`) lists files the person chose to leave as they are, as after a `restore_failed` (issue #80). A skip path is compared with the saved copies after resolving it against the chat's folder (so `./`, doubled or trailing separators and relative paths match) and, on Windows, ignoring case; a path with no saved copy since that question is `400 skip_unknown` on `skip`, from the preview and the rollback alike, and nothing changes; the body names the paths in the message and carries them as data in a top-level `unknownSkip: string[]` beside `error`, each exactly as it was sent (issue #87: read this rather than the message, which cannot be split for a path containing ", "). Matched files are taken out of the plan before restoring and never read, written or deleted, one already back as it was included, and the answer (200 or 409) carries `skipped` with them as `failed[].path` reports them. Failures on other files still answer `409 restore_failed` unless `acceptFailed` is true; a completed rollback drops every copy since the point, the skipped files' included. `acceptFailed` without `skip` plans every file again, so a file the person edited since the failure is overwritten with its copy if it can be written now; `skip` keeps those edits. `planHash` (issue #83) is a fingerprint of what the rollback would do. Its inputs are the point; sorted, each listed file's key, action, saved copy and what the disk holds now (the sha256 of its contents, for a file to restore or to delete, issue #87; its size, modification time and inode when its contents are not read; or blocked); the files not restorable; the skipped ones; `incomplete`; and the transcript (`transcriptRev`, issue #87). Contents are not read for a file to delete that cannot be read (it is still removed, since rm needs no read) or for any file larger than 64 MiB (hashing it would read it whole into memory); such a preview entry carries `contentUnchecked: true` with `contentUncheckedReason` `unreadable` or `too_large`, and for it a same-size replacement with its modification time put back cannot be told apart. The preview also answers `transcriptRev`, a string fingerprint of the chat's rows from that question on and their count (titles and other metadata are not part of it), and the rollback takes an optional `expectTranscriptRev` (same validation, `400` on `expectTranscriptRev`); a different one answers `409 plan_changed` before anything changes, so a conversation-only rollback (`files: false`) is bound to the messages the preview showed too, and a question and reply another client completed meanwhile is not erased. The rollback takes an optional `expectPlanHash` (a non-empty string of at most 200 characters, otherwise `400` on `expectPlanHash`): it plans the files again inside the turn lock, and a different hash answers `409 plan_changed` before anything changes (a file was edited since the preview, another turn changed more files or added messages, or `skip` differs), so the client should show the preview again; without it nothing is compared. `files: false` takes back only the conversation. The rollback runs under the chat's turn lock (issue #74): a message sent meanwhile waits and then runs on the rolled-back chat; the files are planned again against the disk inside the lock (so a file blocked when the request was checked and free now goes back, issue #80), and the point is planned again from the stored chat inside the lock and again right before the save, where the chat's `transcriptRev` must still be the one checked inside the lock (rows after the point rewritten meanwhile by another process answer `409 plan_changed` with the `partial: true` body, issue #87): a transcript that moved on since the request was checked answers `409 point_mismatch`, any other refusal its own code (`turn_in_progress` for a turn another process runs, `point_compacted`), and a refusal after the restore carries the same `partial: true` body as `restore_failed` (the files went back, the chat was not cut). A write that leaves the transcript alone (a title, a next-step suggestion) neither refuses nor is lost. Editing a sent message is a rollback followed by a normal send of the new text. `POST /api/sessions/{id}/fork` with the same body saves a new chat holding the history through that question's answer, titled "… (fork)", and answers `{ id, title, sourceId }`; the fork has no goal (the source's stays with it), and an incognito chat is not forked (`409 incognito`, issue #74). All refuse with `409 turn_in_progress` while the chat runs a turn and `409 point_compacted` inside a compacted part; `404 session_not_found` is an unknown chat. Only the agent's own file tools are covered: their targets are saved before each call ([checkpoints](../tools/os/fs/fs-checkpoint-store.ts)).

A file the reply created is removed. `200 { path, action: "restore" | "delete" | "unchanged", at, tool }`; `404` with `session_not_found` or `no_snapshot` (that reply kept no copy of the file, or the chat's copies were pruned 30 days after its last one; `incomplete: true` when copies were dropped to stay in the 400-entry / 64 MiB per-chat bounds); `409` with `point_mismatch`, `copy_damaged` (the saved copy no longer matches its recorded sha256, issue #87; the file is left as it is and a retry will not help), `changed_later` (a later reply changed the file too: revert from the latest reply), `not_restorable` (`reason`: too large, binary, not a file) or `turn_in_progress`; `400` for a path that is not absolute or a missing selector. An agent without the route answers 404 without a code.

Continuing a reply a restart cut off (ATO-448, [route-resume-interrupted-turn.ts](route-resume-interrupted-turn.ts)): `POST /api/sessions/{id}/resume` answers `200 { id, text }` when the chat's last turn was cut off by a crash, a kill or an update. `text` is the continuing message: a note that tools that were running may or may not have completed and that side effects must be checked before they are repeated, then the interrupted request. The client sends it through `POST /v1/chat/completions`, the same path as the TUI's `/resume`; nothing is continued without that. The turn is offered once per agent process: a second call to the same process answers `409 resume_queued` while that resume (or one this process's TUI queued) has not started. The mark lives in that process's memory, so another process serving the same state dir (a second `serve`, a TUI on its own runtime) does not see it, and a mark this route hands out lapses after 10 minutes (`RESUME_HOLD_MS`) so a client that crashed holding the text does not block the resume until a restart; a chat whose last turn was not cut off answers `409 nothing_to_resume`. Body `{ "release": true, "text": "<handed-out text>" }` gives it back when the client could not send the message; only the mark with that exact text is freed. `409 turn_in_progress` while the chat runs a turn (checked before a release too), `404 session_not_found` for an unknown chat.

[Model tiers route](route-model-tiers.ts): `GET /api/model-tiers` returns the Cheap / Balanced / Best picks per provider key (`openrouter`, `aimlapi`, `gemini`, `claude-cli`) from the one data file, [model-tiers.ts](../llm/provider/presets/model-tiers.ts) (ATO-32). The TUI pickers list those models first under the same labels.

Anthropic Messages and OpenAI Responses (ATO-1080, [compat-bridge.ts](compat-bridge.ts)): `POST /v1/messages` ([anthropic-messages.ts](anthropic-messages.ts)) and `POST /v1/responses` ([openai-responses.ts](openai-responses.ts)) translate the request into a `/v1/chat/completions` body and run that same handler in-process, so sessions, approvals, client-disconnect cancellation and usage behave exactly as there; only the envelope changes. Streams come out as Anthropic's `message_start` / `content_block_*` / `message_delta` / `message_stop` events, or as Responses' `response.created` ... `response.completed` (`response.incomplete` when the turn ran out of steps, `response.failed` on an error), each with `sequence_number`. The agent runs its own tools: client `tools` are accepted and not offered to the model, so the reply is text (`stop_reason` `end_turn` / `max_tokens`); `tool_use` / `tool_result` blocks and `function_call` / `function_call_output` items already in the history are kept as plain text. `model` is echoed and the active agent model answers. A Responses id is `resp_<random>_<session id, base64url>`, so `previous_response_id` continues that chat, also after a restart. `POST /v1/messages/count_tokens` answers a rough estimate (about four characters a token). Auth also accepts the key as `x-api-key`, the header Anthropic clients send.

[AG-UI route](route-ag-ui.ts) (ATO-694): `POST /api/ag-ui` takes an [AG-UI](https://docs.ag-ui.com) `RunAgentInput` (`{ threadId, runId, messages, state?, tools?, context? }`) and streams the turn as AG-UI events, one `data: <event JSON>` per SSE frame, for web frontends built on AG-UI (CopilotKit, `@ag-ui/client` `HttpAgent`). `threadId` is the session id (a new one starts a chat in the server's folder); the turn's input is the last `user` message, and `tools` / `context` / `state` are accepted but not used. The stream opens with `RUN_STARTED` and ends with `RUN_FINISHED` (`outcome` `success` or `cancelled`, `usage` in tokens) or `RUN_ERROR` (`message`, `code` = the failure category). In between: `STEP_STARTED` / `STEP_FINISHED` per loop step, the reply as `TEXT_MESSAGE_START` / `_CONTENT` / `_END`, reasoning as `REASONING_*`, each tool call as `TOOL_CALL_START` / `_ARGS` (the whole JSON args) / `_END` and its outcome as `TOOL_CALL_RESULT` (`metadata.status`: `ok`, `error`, `denied`, `cancelled`), the plan as `STATE_SNAPSHOT` (`{ plan: { items, updatedAt } }`), and provider waits, switches, long-call progress, fusion workers, steers and retried step errors as `CUSTOM` events named `atomic.<event>` ([mapping](ag-ui-events.ts)). Closing the connection stops the turn. Approvals stay on `GET /api/events` and `POST /api/approval/resolve`. Bearer auth like every `/api` route; `/v1/chat/completions` is unchanged.

[Webhook route](route-webhooks.ts) (ATO-438): `POST /api/webhooks/{name}` turns a hit on a `webhooks.<name>` binding into a task. The binding's `verify` picks how `secret` is checked, always on top of the global API key: `secret` (the default, unchanged) compares the `x-webhook-secret` header; `github` checks `X-Hub-Signature-256: sha256=<hex HMAC-SHA256 of the raw body>`; `standard-webhooks` (the scheme Composio and Svix sign with) checks `webhook-signature: v1,<base64 HMAC-SHA256 of "<webhook-id>.<webhook-timestamp>.<body>">` with the base64 key of a `whsec_` secret, refuses a `webhook-timestamp` more than 5 minutes off, and starts one task per `webhook-id` (a bounded in-memory list per process; a repeat answers `200 { taskId: null, duplicate: true }`). Signatures are computed over the exact request bytes ([readRawBody](request-context.ts), [checks](webhook-signature.ts)), compared in constant time; a failure answers `401` and starts nothing. With a signed scheme the template can use `{{event}}` (`X-GitHub-Event` or the payload `type`), `{{action}}` (GitHub's payload `action`) and `{{delivery}}` (`X-GitHub-Delivery` or `webhook-id`), and `events: ["pull_request.opened", "issues"]` limits which events start a task ([matching](webhook-verify.ts)); an event left out, and GitHub's `ping`, answer `200 { taskId: null, ignored: true }`. Example:

```json
"webhooks": {
  "pr-review": {
    "verify": "github",
    "secret": "<the secret set on the GitHub hook>",
    "events": ["pull_request.opened"],
    "userMessageTemplate": "Review {{event}} {{action}}: {{body.pull_request.html_url}}"
  }
}
```

Not covered here: GitHub cannot send a bearer token, so a server started with `--api-key` still refuses its hits; reaching the agent from the internet needs a tunnel or public address; no Composio subscription and no Slack or calendar presets.

Webhooks from the internet (ATO-625): `verify: "stripe"` checks `Stripe-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>">` with the endpoint's `whsec_` secret used as text, refuses a `t` more than 5 minutes off, and fills `{{event}}` / `{{delivery}}` from the payload `type` / `id` ([checks](webhook-signature.ts)). `atag serve --tunnel` (or `--tunnel-name <n> --tunnel-hostname <h>` for a named Cloudflare tunnel) runs cloudflared from PATH (never downloaded, `--no-autoupdate`) against a second listener on a random loopback port whose [route table](tunnel-route-table.ts) holds only `POST /webhooks/{name}`. Providers send the binding secret or signature to that path. The former tunnel path `POST /api/webhooks/{name}` returns 404. Update existing provider URLs to the new address from `GET /api/webhooks` or the startup notice. Every other path answers 404 there, a binding without a secret answers `403 webhook_secret_required`, and the main API is never the tunnel's origin (there is no option to expose it). On that listener every signed binding (`github`, `standard-webhooks`, `stripe`) gets replay protection: a delivery id already turned into a task (`X-GitHub-Delivery`, `webhook-id`, the Stripe event `id`; the same bounded in-memory list as above) answers `200 { taskId: null, duplicate: true }` and runs nothing, and the timestamped schemes refuse a signature more than 5 minutes old. serve refuses `--tunnel` when cloudflared is missing, tasks are off or no binding has a secret. `GET /api/webhooks` ([list route](route-webhooks-list.ts)) answers `{ tasksEnabled, tunnel: { state, mode, publicUrl, error }, webhooks: [{ name, path, hasSecret, sessionMode, publicUrl }] }`, never the secrets; `publicUrl` is set only while the tunnel is up and only for bindings with a secret. cloudflared is stopped with serve ([wiring](../cli/serve-webhook-tunnel.ts)).

Goal mode (ATO-1040, [route-session-goal.ts](route-session-goal.ts), [chat-goal.ts](chat-goal.ts)): the TUI's `/goal` for other clients. `GET /api/sessions/{id}/goal` answers `{ sessionId, goal, running }`, `goal` being the stored [GoalState](../agent/goal/goal-types.ts) (status, per-criterion marks and reasons, rounds used of `maxRounds`) or `null`; `GET /api/sessions` rows and `GET /api/sessions/{id}` carry the same `goal`. `POST /api/sessions/{id}/goal` takes `{ action: "set", criteria: string[], maxRounds?, workingDir? }` (a new chat is opened in `workingDir`, else the server's folder; the stored goal's shell checks are kept, none are added here), `{ action: "pause" }`, `{ action: "resume" }` or `{ action: "clear" }`, with the TUI's rules: `409` with `code` `turn_in_progress`, `no_goal`, `goal_not_running` or `goal_complete`. `set` and `resume` answer `message`, the text to send next through `POST /v1/chat/completions`; with `x-atomic-extensions: 1`, a chat whose stored goal is active runs that message as goal rounds, and the stream carries `event: goal_progress` `{ object: "atomic.goal_progress", session_id, goal }` after every change. `pause` and `clear` on a goal that is running answer `pending: true` and land after its current round (`runtime.controlGoal`).

[Metrics route](route-metrics.ts) (ATO-646): `GET /metrics` answers the Prometheus text format for a Prometheus or Grafana scrape of `atag serve`: turns (count and duration by origin and outcome), steps, provider failures by category and provider link, tool calls by tool, task and scheduler counters, plus turns running and durable tasks per status read at scrape time. Serve folds the runtime's metric samples in a [PrometheusRegistry](../tracing/prometheus-registry.ts); no label carries a session id. The route is never open without a key: the scrape config sends serve's key (`--api-key`, or the contents of the generated key file) as a bearer token, and a server built with no key at all (`unauthenticated: true`, never `serve`) answers 401 (`metrics_need_api_key`).

Managing bindings (ATO-445): each `GET /api/webhooks` item also carries `verify` (`secret` when unset), `events` (when set), `userMessageTemplate` and `live` (false for a binding saved in `config.json` by hand since start, listed from the file), and the reply adds `presets` (the `verify` values). `POST /api/webhooks` `{ name, verify?, userMessageTemplate, secret?, events?, sessionMode? }` adds a binding ([admin routes](route-webhooks-admin.ts)): the secret is generated unless given (`whsec_<base64>` for `standard-webhooks`, hex otherwise; `stripe` needs the pasted `whsec_` value), the whole file is revalidated and written atomically, the running agent picks it up without a restart, and the reply `201 { webhook, secret }` is the only time the secret is returned. `DELETE /api/webhooks/{name}` removes a binding and its persistent session mapping. Both sit on the main API behind its bearer key; the tunnel listener never serves them.

## Named HTTP tokens

The serve key is the owner credential. It works on every authenticated route, including any route awaiting classification. Desktop launchers can continue passing it through `--api-key-stdin`.

| Role | Scopes | Intended use |
| --- | --- | --- |
| `viewer` | `read` | Read API data. Every POST, PUT, PATCH and DELETE requires another scope. |
| `member` | `read`, `chat` | Run and steer ordinary agent work. |
| `operator` | `read`, `chat`, `decide` | Resolve approvals and questions, make project decisions, change the backlog or lessons, and set project trust. |
| `admin` | `read`, `chat`, `decide`, `admin` | Manage settings, integrations, scheduled tasks and other administrative resources. |

An operator can deny requests, approve ordinary tools once, and grant a supported action for the current chat. Approving `trust_config` or saving a permanent `allow-always` rule requires admin or the owner. The protected token registry is among the targets classified as `trust_config`. An operator can still approve ordinary shell commands. Those commands run as the server user and can affect its files, including the registry, if the best-effort shell classifier does not recognize the access or the runtime auto-approves it. The admin role is therefore an HTTP authorization distinction, not an OS isolation boundary. Grant operator only to callers you trust to authorize code execution. Roles apply across the whole server. A viewer can read and export all chats exposed by the listener, subject to incognito and folder egress restrictions. A member can write to existing chats, including chats opened by the owner. The server uses shared sessions and does not assign them to token identities. A member can also name file paths in prompts and ask the agent to read them. The runtime applies the same file scope, tool approvals, and project policy as it does for other turns. Content read by the agent can appear in replies. Issue a member token only to clients you trust with that access.

Named turn and steer requests carry their token name in runtime attribution and traces. Approval cards show the turn requester and name the tokens that have steered the running turn so far. This does not imply that a particular steer caused an approval.

Use `atag http tokens add <name> --role <role>` from the local CLI. Copy the token from stdout when it is issued and send it as `Authorization: Bearer <token>` or `x-api-key`. Use `atag http tokens list` for names, roles and creation dates, and `atag http tokens remove <name>` to revoke it on the next request without restarting. The approval events, chat completions and AG-UI streams close on their next event or heartbeat after access is revoked. Buffered data already sent cannot be recalled. These management commands refuse agent tool children.

The registry at `<stateDir>/http-tokens.json` stores names, roles, creation times and SHA-256 digests. It is private to the owner (0600 on POSIX, current-user ACL on Windows). OS and shell approval rules protect the file like the serve key. The shell guard also asks for trust approval on recognized token-management commands. These local checks are best-effort and do not isolate processes running as the same user. If an interrupted edit leaves a `http-tokens.json.lock` directory, remove that empty directory after confirming that no token-management command is still running.

A missing, invalid or revoked credential returns HTTP 401 with `invalid_api_key`. The existing failed-attempt rate limit applies to network addresses. A valid credential missing a required scope returns HTTP 403 with `insufficient_scope`. The signed webhook listener uses its binding credentials.
